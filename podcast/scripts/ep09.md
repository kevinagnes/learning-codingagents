## 4. Body beat 1 — Selecting once, loading every step

HOST:
First claim. Building a request happens in two phases, and only one of them is allowed to run again on every step.

CO-HOST:
Two phases. Name them.

HOST:
Selection and loading. Selection fixes the identity of the request. The session, the agent, the list of instruction sources, and a frozen snapshot of the tools. Loading adds the only two things that move between steps, which are the resolved model and the active history.

CO-HOST:
So selection is the expensive half. It reads files, hashes values, asks tool sources for their definitions, and filters by permission.

HOST:
And it pays that cost once per execution instead of once per step, which is the first thing the split buys. Selection also resolves all of that in parallel and then fixes the order of the result. Completion order never decides anything over there. The order is declared, not raced.

CO-HOST:
Hold on. I want to push on this, because one function that resolves everything is easier to write and easier to read. What actually breaks if I fold the two together?

HOST:
Two things, and the second one is not about speed. If you fold them, every step re-reads and re-hashes every instruction file, so a cheap inspection becomes steady state traffic, and the prompt cache gets a new reason to miss on every step. And if selection is not a separate value, a tool registered between two steps can appear in the middle of one execution. The model would see a different tool list from the one its earlier calls were validated against.

CO-HOST:
So one of those is a cost, and one of them is a correctness problem.

HOST:
Correctness first, always. And the two return types are shaped to keep the phases apart. A selection carries no model and no messages at all, so nothing downstream can read them off it. Loading takes the selection and returns it plus the resolved model, the active messages, and the frozen instruction baseline text.

CO-HOST:
And the tool snapshot comes back out of loading unchanged. So the tools the model was advertised cannot shift between the selection and the request itself.

HOST:
That is the invariant the split protects, and I want to name the two guards that go with it. Selection refuses to assemble a request for a session that belongs to a different directory, so it stops instead of building the wrong thing. And the two phases fail differently, which tells you which half broke. Selection fails by not finding an agent, and loading fails when the model cannot be resolved.

CO-HOST:
Small detail, but it pays off at three in the morning. Now the reuse case.

HOST:
Which is the third thing the split buys. A flow that needs a model but no instruction or tool preflight resolves only the capabilities it needs. Naming a session is the example. The rejected alternative is one function that returns everything, and it makes a question like what would this selection look like with a different model impossible to ask cheaply.

CO-HOST:
So resolve identity once, and reload the state as often as it moves.

HOST:
And loading carries one more thing into history. A provenance boundary, so only the parts of the conversation that the selected model can actually replay are included.

CO-HOST:
And is that the whole reason for two phases, or is there something you could not do at all with one function?

HOST:
There is one more, and it is the argument I would put first. A flow that needs a model but no instruction or tool preflight resolves only the pieces it needs, instead of running the expensive half again. And because a selection carries no model, you can inspect one and ask what it would look like with a different model without re-reading the world.

CO-HOST:
So the expensive half is also the reusable half. That survives a fast implementation. Even if selection were free, you would still want the two values apart.

## 5. Body beat 2 — The prompt is parts

HOST:
Second claim. The system prompt is not one string. It is a list of parts, and for an ordinary request there are exactly two.

CO-HOST:
The file on disk looks like one block of prose, with headings and a couple of sections. Where does a second part come from?

HOST:
The file is only the first part. The second is the instruction baseline, which is the frozen text of every instruction source at the current epoch. It is appended after the base prompt, and it is always sent, whatever the first part turns out to be.

CO-HOST:
So one part is the harness voice, and the other is what the project says.

HOST:
And the harness part is not finished text either. It has a placeholder in the middle of it, and that placeholder becomes a list of guidance lines that depend on the tools in this request. That is the next beat, but it means the first part is generated rather than stored.

CO-HOST:
What if the agent brings its own prompt? Plenty of agents do, because they want a different voice from the harness one.

HOST:
Then the base prompt and the guidance are not sent at all. The agent's own prompt is the first part, exactly as its author wrote it, and the instruction baseline still follows it. The failure that prevents is a custom agent being silently prefixed by the harness prompt, which would contradict what its author asked for.

CO-HOST:
So the override is honoured rather than patched. What about the empty cases?

HOST:
Empty parts are filtered out, so a part that would be zero length never occupies a slot in the request.

CO-HOST:
Now the base prompt itself. It is short, and I went through it twice while preparing. It barely mentions the tools, and one of its lines is strange out of context.

HOST:
That line is load bearing. The prompt says the system reminder blocks are harness instructions rather than user authored content, and that the model should read them and follow them. That one sentence is what lets the harness speak inside the conversation without being mistaken for the user.

CO-HOST:
Why does that need saying? Text that arrives in the user turn is text. Who else would write it?

HOST:
That is the ambiguity it resolves. The harness delivers policy notes inside the user turn, in blocks tagged as system reminders. Compaction notes and step limit notices ride in the conversation that way. Without that sentence, a model can treat harness speech as untrusted user text, and ignore it, or argue with it.

CO-HOST:
So one line in the prompt is what lets the rest of the harness speak.

HOST:
It does, and the rest of the base prompt is doing the same kind of work. It says what kind of system the model is inside, so it reasons about running tools instead of apologising for being a chat model. It states the standing objective, so the model optimises for finishing the task rather than answering the last message.

CO-HOST:
And it states a rendering fact, which is the line I would have left out.

HOST:
Which buys correct fences, tables, and lists. Without it, the model writes plain text and the client renders literal asterisks. The last line is a nudge toward parallel tool calls inside one step, because otherwise models serialise their calls and waste steps.

CO-HOST:
So the prompt is parts in a fixed order. The harness voice, then the frozen baseline.

HOST:
And one thing follows from that order, which is the whole of the last beat. The order is chosen for the cache.

CO-HOST:
And where does the baseline come from? Somebody has to decide what counts as an instruction source.

HOST:
Which is next episode, and it is the reason the two parts are separated here. The baseline is a single part, and a single part is what can be replaced by a delta later without touching the first.

## 6. Body beat 3 — Guidance depends on the tools

HOST:
Third claim. The middle of the base prompt is not text. It is a placeholder that becomes a different list of lines depending on which tools are in this request.

CO-HOST:
And if the wrong lines land there, what is the cost?

HOST:
Two failure modes, and one of them is subtle. If you tell the model to prefer a tool that this request cannot call, you have invited a tool call that cannot succeed. And if the same tool set produces different bytes on different days, you have thrown away the cache for the whole prompt.

CO-HOST:
That second one takes some thinking about. How does a list of the same lines change the bytes?

HOST:
Because the lines are joined in a fixed order, and the fixed order is the point. The guidance is built in the order shell, then write, then edit. It is deliberately not derived from the order the tools were registered, because registration order can vary, and the bytes would vary with it.

CO-HOST:
So the deterministic order is a requirement rather than a preference.

HOST:
It is a requirement with an economic consequence. And the lines are emitted per tool, from the effective names in this request's snapshot. If permission narrowed the tool set, the tool is not in the snapshot, so it contributes no guidance at all. The prompt never teaches a tool that this session cannot use.

CO-HOST:
Walk me through the lines. What does each one buy?

HOST:
There are three gates. When the shell is present, two lines are added. One tells the model to prefer the dedicated tools and to fall back to the shell when a tool cannot do the job. The other forbids chaining commands with banner separators, and then explains why, because the output becomes noisy in a way that makes the user's side of the conversation worse.

CO-HOST:
So it is a prohibition with a reason attached.

HOST:
And the reason is what makes it followable. Then a line for the write tool, when it is present, which says to use write to create a file or replace one completely, and to prefer edit for targeted changes. Then a line for the edit tool, when that one is present.

CO-HOST:
Which is the tool contract again, restated as an operating rule. Write for whole files, edit for changes.

HOST:
Restated, because the model reads the prompt and the tool list separately. One is a rule about how to work. The other is a description of a tool. And notice what those two lines do together, because neither tool is wrong on its own. Without them, models overuse whole file writes and lose the surrounding edits.

CO-HOST:
Is any of the guidance about something other than a tool?

HOST:
Only the shape of it. The block is the model facing copy of the harness's own conventions, which is why one of those lines explains the cost to the user's reading rather than the cost to the machine.

CO-HOST:
Guidance is a function of the tool set, and the function has to be deterministic.

HOST:
Same inputs, same bytes, or the cache pays for your indecision. And the same rule runs the other way. Guidance for a tool that was denied is worse than no guidance, because it teaches the model to ask for something it cannot have.

CO-HOST:
One thing I want to check. Are those lines part of the tool definitions, or part of the system prompt?

HOST:
Part of the system prompt, and that split is deliberate. The tool definition says what the tool is. The guidance says how to work with the tools together, which is advice about the task rather than about one tool, so it belongs to the prompt.

CO-HOST:
Where you can also say why, which the argument shape of a tool definition does not allow.

## 7. Body beat 4 — Order is an economic decision

HOST:
Last claim, and it is the one that decides the bill. The instruction sources are ordered for the cache, not for the reader.

CO-HOST:
That is a strange sentence. Put the date and the environment first, and the model knows where it is before it reads anything else.

HOST:
Which is the natural order for a person, and it is backwards for the machine. Providers cache a prefix of the input. If two requests share a byte-identical prefix, the second one is served and billed as a cache hit up to the first difference. So the longest lived, most widely shared content has to sit first.

CO-HOST:
And what is actually shared, across sessions and across directories?

HOST:
The user level catalog and guidance are shared by every session that user starts. The project instructions are shared by every session in this repository. The date and the environment are shared only by requests in the same directory on the same day, so they go last. That is the order the combine call assembles, and the ordering comment states it in the code.

CO-HOST:
So user level first, then project, then environment. Which means the parts that move most often sit at the very end.

HOST:
And the parts that move most often are also the least interesting to a reader, which is the conflict the rejected alternative runs into. The alternative is to rank by importance and put the most important instructions at the top.

CO-HOST:
Which is how you would write a document for a person.

HOST:
It is, and it optimises for how the model reads instead of how the cache works. Those two goals conflict, because the most cache stable content is usually the least session specific. The design chooses the cache order, on the grounds that a cache miss is paid on every step.

CO-HOST:
And this is the point where a reasonable engineer would choose the opposite.

HOST:
Which is why we have someone who has to defend it. Welcome. Why does the date go last?

EXPERT:
Because the date changes every day and the guidance does not. A prefix cache only helps while the prefix is identical, so we order by how long a line can sit still, not by how much it matters to a person reading the prompt.

CO-HOST:
So the cheapest thing to change goes at the bottom.

EXPERT:
And when it does change, we say so. The date renders as a supersession, the date is now this, so the model does not read two dates with no cue about which one wins.

HOST:
Which is the last mechanism, and it applies to both of the tail sources. The date and the environment each render differently the first time and when they change, and the change is worded as a replacement rather than as a second fact.

CO-HOST:
So even the tail of the prompt has a small contract about how it moves.

HOST:
It has to, because the tail is the part that moves most often. And the whole ordering rule is testable, which is the sign that it is a real invariant. Build the system parts twice with the same agent, the same tool set, and the same baseline, and the serialized parts have to be identical.

CO-HOST:
And then change only the date.

HOST:
And assert that the first part is untouched and only the appended tail differs. That is the cache invariant written as an assertion rather than as a comment.

CO-HOST:
So put the least session specific content first, because the cache rewards the longest shared prefix.

HOST:
And keep the order fixed, or you pay for the whole prompt again on every step.

CO-HOST:
What happens if a plugin rewrites the prompt after all of this assembly?

HOST:
Then the cache is whatever the rewritten prompt allows. The assembly ends there, and a hook may still rewrite the draft request before it is sent. Whatever reassembles it owns the cache stability from that point on.

## 8. The artifact

HOST:
The artifact this episode is the base system prompt, and it is short enough to read whole. Here it is, word for word.

HOST:
"You are an A I agent running in opencode, a coding agent harness. Help the user accomplish their goals using the tools you have available. Harness. Responses are rendered as Git Hub flavored Markdown. The system reminder blocks are harness instructions, not user authored content. Read and follow them. Prefer parallelizing independent tool calls."

HOST:
That is the first half. The line in the middle of it is where the tool guidance goes, and every guidance line from the last beat lands in exactly that spot.

HOST:
"Communication. Use clear file paths when referring to files. Keep responses clear and concise, and avoid unnecessary technical jargon. Working in codebases. Keep changes consistent with the structure, naming, style, and patterns of the surrounding code. Treat unfamiliar files or changes as potential user work and investigate before deleting or overwriting them."

[production note: the source file uses hash marks for its section headings, code formatting around the system reminder tag, and its own styling of the product and rendering host names. Those marks are dropped in the spoken read, and abbreviations are spoken as letters. The companion carries the file exactly.]

CO-HOST:
That is the whole prompt. Shorter than most people expect, and there is no code in it at all.

HOST:
And every one of them is about a failure the harness cannot fix at runtime. The rendering line buys correct markdown. The reminder line is what lets the harness speak inside the conversation.

CO-HOST:
And the last section is the one I would have missed.

HOST:
Which is the safety line. The model edits a working tree that may hold uncommitted user work. Treat unfamiliar files or changes as potential user work, and investigate before deleting or overwriting them. It is the prompt half of the snapshot and revert machinery.

CO-HOST:
So it is a guard that lives in prose, which is the right place for it, because the prompt is written for the model to read rather than for a person to admire.

HOST:
It has to be in prose. Nothing in the file system can tell the harness which uncommitted change was the user's work and which was the agent's from last week. Only the model has the context to pause and look.

## 9. Recap

HOST:
Where we landed. One. Every request is built in two phases. Selection fixes the identity of the request, and loading adds the model and the active history.

CO-HOST:
Two. The system prompt is a list of parts. The base prompt with its guidance spliced in, then the frozen instruction baseline.

HOST:
Three. The guidance is emitted per present tool, in a fixed order, so the same tool set produces the same bytes every time.

CO-HOST:
Say the rule, and the ones it stands on. Validate at the boundary, and bound every output. Then assemble the prompt from stable parts, in a cache stable order.

HOST:
And the order runs from the most shared part to the least.
