## 4. Body beat 1 — Durability before concurrency

HOST:
Here is the claim. The build order is not a preference. Durability comes before concurrency, and settlement comes before features.

CO-HOST:
Let me push on that, because I have shipped this the other way. The loop works in a day. Persistence is a week of plumbing that makes the demo slower. Why not add it at the end?

HOST:
Because of what the features assume while they wait. A concurrent system with no durable record has nothing to serialize on. Two fibers race over a transcript in memory, and the transcript corrupts. The rule that one execution owns a session becomes a lock over a structure that a crash dissolves.

CO-HOST:
So the lock is only as durable as the thing it guards.

HOST:
Yes. Once every fact is a row, concurrency becomes a query and a doorbell. Steering becomes an ordered promotion over durable rows. Before that, both are arguments about memory.

CO-HOST:
That is the part I got wrong. I thought the coordinator was the concurrency design. It is a lock over records that already exist. The record came first, and the lock came second.

HOST:
The coordinator is the last mile. The record is the road. That is why the first four milestones build the record and the projection, and only then does anything concurrent appear.

CO-HOST:
And the rest of the order?

HOST:
It follows the same test. The model boundary comes first, because a canonical request and a canonical stream are what make a step something you can settle. Durable state comes before continuation, because continuation is a fold of the record. Tools come after durable history, because a result is only usable once it is written down. Permissions come after tools, because there is nothing to gate until something can have an effect.

HOST:
Compaction and reliability come after the loop, because they are recovery from the two ways a step breaks. Too long, and incomplete. Concurrency comes after durability. Snapshots come after tools, because they read the tree the tools changed. The server comes last, because it is only a view of facts the earlier milestones already write.

CO-HOST:
That last one is a good test of the whole idea. The interface is the least fundamental part.

HOST:
It is the part everyone builds first.

CO-HOST:
And it is the part that teaches you nothing about the record. One more objection. You said each milestone is a gate, not a phase. What does that mean when I am moving fast?

HOST:
The test for a milestone has to pass before the next one starts, and it has to still pass at the end. The tests are chosen so a later milestone does not force you to rewrite an earlier one.

CO-HOST:
So the ladder is a series of promises to your future self.

HOST:
Each milestone introduces exactly one invariant. Later milestones only read what the earlier ones wrote.

CO-HOST:
And what breaks if I skip one because it looks obvious?

HOST:
The feature above it inherits the gap. Skip the projection in the recording transaction, and you get a crash window between admitting work and inserting the message. Skip the sequence rule, and history reorders by the clock.

CO-HOST:
Which is a bug that looks like a display bug for a week.

HOST:
And is a durability bug the whole time. That is the takeaway. Build the record first, because every concurrent feature later is a query over it, not a new argument about who owns what.

CO-HOST:
Fine. Then what is the smallest version of the record that is worth building?

## 5. Body beat 2 — The smallest agent that is correct

HOST:
The smallest correct agent is one streamed model call, two tools, a bounded result, and one continuation decision you can read. That is the claim. It is about ninety lines.

CO-HOST:
Ninety lines is a demo, not an agent. You have spent nineteen episodes telling me the hard parts are records and settlement.

HOST:
They are. The ninety lines are correct for the first two milestones and wrong for the product. Every shortcut is named in a comment, and the comment names the milestone that replaces it.

CO-HOST:
So walk me through it as capabilities, not code.

HOST:
First capability. A stream that must end in a terminal event. You read the events in order. If the stream ends without one, that is a failure. An event after the terminal is also a failure.

CO-HOST:
Why is that first?

HOST:
Because the cheapest bug is treating the end of the stream as success.

CO-HOST:
And a half-written tool call, or a reply stopped by a filter, flows in as if it were complete.

HOST:
Second capability. Tools. Read and write. The set is fixed before the request is sent, and the model only sees that set. When a call comes back, you validate the arguments once, and a bad shape becomes an error the model can correct.

CO-HOST:
And the error should name the tool, the field, and the shape that arrived. It should say how to retry. A stack trace teaches the model nothing.

HOST:
That is the difference between a failure the model can fix and one it repeats.

CO-HOST:
And the result?

HOST:
Third capability. A ceiling on the result. You keep a head and a marker that says the rest is in a file. A command that prints two megabytes must not become two megabytes of context.

CO-HOST:
Now the part I always get wrong. The loop.

HOST:
Fourth capability. One model call per step. You send the request, you read the whole stream, and then you decide. Does the finish say the model wants tools? Do any calls need a result? That decision comes from what came back, not from what you intended.

CO-HOST:
So the finish reason is not a log line. It is an input.

HOST:
It is the input. A clean stop, a tool call, a length cut, a filter, a dropped stream, an unknown reason. Each leads somewhere different.

CO-HOST:
And then you go around again.

HOST:
You go around again, and here is the shortcut. At this size the decision lives in a variable in the loop. That is the in-memory loop, and it is allowed here, as long as you write down that it is temporary.

CO-HOST:
Allowed. That is a strong word for the thing you banned in the first episode.

HOST:
It is allowed at milestone one and removed at milestone two. At milestone one the record does not exist, so there is nothing to read. The moment history is durable, the variable becomes a second place that decides continuation.

HOST:
Fifth capability. History that survives the process. Every message is written down and read back in order, and the order comes from a per-session counter, not from a clock.

CO-HOST:
So what does each shortcut defer?

HOST:
The array of messages defers durable history. Trusting the argument shape defers validation. The provider's default limit defers the budget. Returning a refusal as text defers the permission tunnel. The loop defers continuation from the record.

CO-HOST:
And one of those is a correctness bug, not a deferral. The refusal.

HOST:
Correct. A shortcut you named is a plan. One you did not name is a bug. The refusal returning as text is the one place where the small version is actively wrong.

CO-HOST:
So the takeaway is not build the small thing. It is build the small thing and label the seams.

HOST:
Yes. The minimum agent is a stream that must end, a tool set fixed before the request, a result with a ceiling, and one decision read from what came back.

CO-HOST:
Four boundaries, and each one is a place to be lazy. So what are the mistakes that break them?

## 6. Body beat 3 — Pitfalls, the loop and the record

HOST:
Now the mistakes. There are two families in this half, and each is really one mistake. A loop that decides twice, and a fact treated as true before it is written down.

CO-HOST:
Give me the temptation first, then the symptom. That is how I will recognize them.

HOST:
First. The in-memory tool loop. The temptation is to keep looping over tool results in your caller, because it is fewer lines and it reads like the diagram in your head.

CO-HOST:
And the outer loop looks like the program, so the second one is invisible. There are two deciders, and only one of them is in the file you are reading. And the symptom?

HOST:
After you add retries or compaction, the model is called twice in one step, or a tool result lands after the step has settled. Two places decide continuation. The runner has its own step loop, and your caller has another. The fix is one call per step, with continuation derived from the record.

CO-HOST:
I have seen that. It presents as a duplicate answer, and I spent a day in the prompt.

HOST:
The prompt was fine. Second. Deciding continuation from memory. The temptation is a boolean next to the loop. It is the most natural variable in the program.

CO-HOST:
And the symptom is the crash case.

HOST:
After a crash the agent stops early, or it re-runs a tool it already ran. The boolean died with the process, and the record never knew it existed. The fix is to derive continuation from the tool states plus the finish reason.

CO-HOST:
So the record answers the question the variable used to answer. And it answers it after the process is gone.

HOST:
Third. Non-durable tool results. The temptation is to append the result to an array and write the array later, after the loop finishes. It is one write instead of many.

CO-HOST:
And the side effect already happened.

HOST:
That is the whole problem. The side effect ran with no recorded call. After a restart the call has no result, so the next request is malformed, or the model invents a result to fill the hole. The fix is to publish the call before you execute it, and settle it after.

CO-HOST:
Which is the rule from the crash episode, applied one layer down.

HOST:
Same rule, smaller unit. Fourth. No write-ahead claim. The temptation is to mark work finished in a shutdown hook, because shutdown hooks are the tidy way to clean up.

CO-HOST:
And a hard kill does not run them.

HOST:
So the marker survives, and the next boot cannot tell a dead run from a finished one. A step runs twice, or a finished turn is resumed on every boot until it crash-loops. The fix is a claim written in the same transaction as the started event. A surviving claim with no terminal is the signature of a crash.

CO-HOST:
The shutdown hook is the tell. If your recovery depends on code that runs at exit, you have a recovery plan that a power cut cancels.

HOST:
A hard kill is the only test that matters. If the marker is cleared by a handler, the handler is part of the guarantee, and it will not be there when you need it.

CO-HOST:
Now let me push, because four fixes for four symptoms sounds like a checklist. Why not handle each symptom where I see it?

HOST:
Because the symptom is one layer above the cause. A transcript that duplicates after a crash is a durability bug, not a display bug. A model that re-runs a tool is a record bug, not a tool bug. Fix the layer.

CO-HOST:
And the layer is always below where it hurt.

HOST:
Always. If a decision can be re-derived after a restart, do not keep it in a variable. If a fact has to survive, write it before you act on it.

## 7. Body beat 4 — Pitfalls, context, permission, and crash

HOST:
The second half is about leaks. A size in the window, a refusal in the model's context, and a partial truth in the record when the process dies. Same frame. The temptation, then the symptom.

CO-HOST:
Start with size, because that one bites everyone.

HOST:
Unbounded tool output. The temptation is to return what the tool returned. The symptom is that one command fills the window, and the model loses the middle of its own work. The fix is a head or a tail plus a marker naming the file that holds the rest.

CO-HOST:
And the marker matters as much as the bound. The model has to know it is looking at a partial result.

HOST:
Otherwise it reasons from a truncated file as if it were whole.

CO-HOST:
A confident answer about the wrong half. And then compaction, which is where I have made every mistake available.

HOST:
Two of them. Compaction that drops the newest exchange. The temptation is to shrink until it fits. The symptom is that the model works on the previous instruction and forgets the current one. Keep the newest exchange word for word. If it alone does not fit, fail.

CO-HOST:
And failing is the right answer. A summary that swallowed the current instruction is worse than an error.

HOST:
The error is visible. The summary is confident.

CO-HOST:
Much worse.

HOST:
And compaction that re-summarizes its own summary forever. The temptation is to run the same summarizer again when space runs low. The symptom is a summary that keeps growing, or a summary of a summary after a model switch. The fix is an initial prompt and an update prompt that reconcile.

CO-HOST:
And the cache one belongs here too.

HOST:
It does. If you reorder the system prompt or drop the tool definitions on the final step, every request is billed at full price with no behavior change. The fix is a stable prefix, with the most shared parts first and the tools kept on the terminal step.

CO-HOST:
Now the one I find genuinely surprising. The refusal.

HOST:
Converting a no into model-visible output. The temptation is to catch the rejection at the tool leaf and return a sentence that says the user declined. It looks kind. It is the worst thing you can do.

CO-HOST:
Because the model reads it as a result.

HOST:
It reads it as a tool result, and it tries another route to the same effect. The fix is a tunnel. The decline travels past the fault-tolerant boundaries as a defect, and resurfaces typed at exactly one place. A decline with feedback stays typed.

CO-HOST:
So a decline with feedback is the opposite case. The user is not refusing, they are correcting.

HOST:
Exactly. The bare no is tunnelled. A correction is guidance, and guidance belongs in the conversation. Then the last two, and they are both about bounding work. No step ceiling. The temptation is to let a hard task run. The symptom is an agent that never ends a turn. The fix is a per-turn allowance, and a terminal step that keeps the tools advertised but refuses to run them.

CO-HOST:
And the other?

HOST:
Two executions for one session. The temptation is to start a fiber for every wake. The symptom is two drains interleaving, corrupted history, and duplicated steps. The fix is one execution per session, and a second wake rings a doorbell.

CO-HOST:
The doorbell is such a small thing to carry such a large bug.

HOST:
One field. It closes the gap between the last eligibility check and the moment the session goes idle.

CO-HOST:
Because those cannot be one atomic step. Half of these are not crash problems. Why put the crash in the same beat?

HOST:
Because a crash is what makes a leak permanent. Output you cannot see, a refusal the model argued with, and a partial call all become durable facts the moment the process dies.

CO-HOST:
Fix the layer, not the symptom.

HOST:
And check the layer below the one where it hurt. A retry after a refusal is an error channel bug. A duplicated answer is a loop bug. An overflow is a budget bug.

## 8. The artifact

HOST:
The artifact is the milestone ladder. It is a table, and reading a table aloud is a bad idea, so I will read the two load-bearing columns. The name of each milestone, and the invariant it introduces. Here is the load-bearing part, in order.

HOST:
"Zero. One streamed model call behind a REPL. A mandatory terminal event.
One. Tools plus filesystem read and write. A fixed snapshot and one call seam.
Two. Durable session history. An append-only log ordered by sequence.
Three. Event sourcing and projections. The fold in one transaction.
Four. The inbox with steering and interrupt. Admitting is not delivering, and steering is not starting new work.
Five. Permissions and questions. Ask, allow, deny, and a defect tunnel.
Six. Token budgeting and compaction. Measured plus estimated, newest kept.
Seven. Retries, overflow recovery, and crash resume. Whether output started, and the claim.
Eight. Subagents and jobs. A child session, a depth limit, a durable notice.
Nine. Snapshots, diffs, and revert. Content addressed captures, and stage, clear, commit.
Ten. The server and the live event stream. Durable facts, ephemeral hints.
Eleven. Code mode, the tool protocol, and skills. Replayable dynamic tools and instructions."

CO-HOST:
Twelve entries, and not one is a feature I would demo.

HOST:
Every entry is an invariant, not a feature. All but the last are load-bearing.

CO-HOST:
The tests are the contract. If a later milestone changes an earlier test, the ladder is wrong.

HOST:
That is the build invariant. Each test passes alone, and still passes after the next milestone lands.

CO-HOST:
And no milestone edits an earlier one. It only reads what the earlier one wrote. So what does the ladder buy?

HOST:
Two things. Each milestone is a gate with one test, and later milestones only read what earlier ones wrote. So a milestone you finish stays finished. And the order is a chain with four side branches. The inbox sits on the record. On the inbox sit permissions, subagents, and retries. Snapshots attach to the tools. The server attaches to the record. Nothing attaches to the interface.

CO-HOST:
And the optional one?

HOST:
Dynamic tool and instruction sources. Code mode, the tool protocol, and skills. You can ship without them. You cannot ship without the other eleven.

## 9. Recap

HOST:
Where we landed. One. The order is durability before concurrency, and settlement before features, because every later capability is a query over the record.

CO-HOST:
Two. The smallest correct agent is one streamed call, two tools, a bounded result, and a continuation decision read from what came back.

HOST:
Three. The pitfalls are not separate bugs. Each is a fact written too late, a decision read from memory, or a boundary that leaked into the model's context.

HOST:
And then the list. The ten rules, in the order the season earned them.

CO-HOST:
One. One model call per step, with no in-memory tool loop.

HOST:
Two. Normalize the provider at one door.

CO-HOST:
Three. Record the fact before anyone acts.

HOST:
Four. Admission is not execution.

CO-HOST:
Five. Continuation is read from the record.

HOST:
Six. Validate at the boundary, and bound every output.

CO-HOST:
Seven. A decline never reaches model context.

HOST:
Eight. Decide retry, continue, or recover from the taxonomy.

CO-HOST:
Nine. Compact to a summary plus the newest exchange.

HOST:
Ten. One execution per session.

CO-HOST:
And the rule for this episode?

HOST:
Build durability before concurrency, and settlement before features. The loop is the cheap part.
