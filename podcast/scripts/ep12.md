## 4. Body beat 1 — An agent is a configuration record

HOST:
An agent is not a personality. It is a configuration record that a session points at, and everything in the assembled prompt is built around it.

CO-HOST:
That is a deflating way to describe the thing users pick from a menu.

HOST:
It is accurate, and the record is small. It has an identity. It may have a preferred model. It carries request settings for the provider. It may have a system prompt that replaces the generated one. It has a description, which is what other agents read when they consider delegating to it.

HOST:
It has a mode. Primary, subagent, or both. It has a hidden flag. It may have a step limit. And it carries a permission ruleset, which we come back to next episode.

CO-HOST:
Hold on. The system prompt is in the record. So an agent can throw away the base prompt entirely?

HOST:
It can. The system field is a replacement, not a patch. That is deliberate. A partial override invites two copies of the same instruction, one from the base prompt and one from the agent, and the model reads both.

CO-HOST:
Then what is left of the base prompt when an agent overrides it?

HOST:
Nothing. The agent is the whole instruction layer at that point. Which tells you how much power the field has, and why the default constructor does not use it.

CO-HOST:
So if an agent is a record, why does it need a mode at all? Why not let the caller decide where an agent may be used?

HOST:
Because the roster is shared. The same record is read by three different consumers. The session picks a primary. The subagent tool offers the ones it is allowed to run. The interface lists the ones a person may choose. The mode is how one record answers all three.

CO-HOST:
And hidden is for the ones that exist but should not be advertised.

HOST:
Hidden is for internal work. A title generator. A summarizer. They are real agents with real prompts, and they are not choices.

CO-HOST:
Fine. But this still sounds like a config file with extra steps. Where is the behaviour?

HOST:
The behaviour is in what the record narrows. The agent's ruleset merges with the session's. The merged rules decide which instruction sources are visible, and which skills are offered. They also decide which tool protocol servers are included, and which tools are in the snapshot. An agent is not a prompt. It is the boundary of what the model can see.

CO-HOST:
So the roster and the tool list are the same decision seen from two sides.

HOST:
They are. Who may be chosen, and what the chosen one may reach.

CO-HOST:
So two agents with the same model can behave completely differently because they can see different tools.

HOST:
And because the instructions they see are filtered by the same rules.

CO-HOST:
What does a brand new agent start with? A blank policy?

HOST:
No. The default constructor starts with a broad allow, then an ask for secret environment files, then an allow for the example file beside them. The ordering is the lesson. The broad rule is the floor, and the narrow rule appended after it is the one that wins. We come back to that next episode.

CO-HOST:
And the step limit. That is the field I have never set.

HOST:
It bounds one execution. When the limit is reached, the next request goes out with tools not offered. A reminder asks the model to write a conclusion instead of calling another tool. It is the difference between an agent that stops and an agent that keeps going until something else stops it.

CO-HOST:
So the record shapes the run at the start and at the end.

HOST:
That is the first takeaway. An agent is the bundle of decisions a session runs under. The prompt is one of those decisions, not the whole thing.

## 5. Body beat 2 — Who gets chosen

HOST:
Which agent answers your first message is decided by an ordered rule, and the rule filters before it orders.

CO-HOST:
Meaning what, in the failure we opened with?

HOST:
Meaning a subagent can never be the default. Neither can a hidden agent, even if one of them is first in the list. The filter is the same check at every step of the walk.

HOST:
The walk is short. First the configured default, if it is selectable. Then the agent named build, if it is selectable. Then the first agent in the map that passes the filter.

CO-HOST:
And selectable means what?

HOST:
The agent exists, its mode is not subagent, and it is not hidden. That is the whole gate.

CO-HOST:
So the helper in the cold open was selectable. It was a subagent by intent, but nobody wrote the mode down.

HOST:
Or it was primary and hidden and the flag was missing. Either way the roster said it was a candidate, and the resolver believed the roster.

CO-HOST:
Here is my pushback. Special-casing a name is not a rule. Why does build get a turn in the walk?

HOST:
Because the order is a promise. Your configured choice wins. A known generalist is the fallback. An arbitrary entry is the last resort. Without the middle step, deleting one config line changes the default. It becomes whatever happens to be first in a map, which is not a decision anyone made.

CO-HOST:
And the last resort is still needed, or a fresh install has no agent at all.

HOST:
A fresh install has no configured default and may have no build agent. The last resort is what keeps the product usable. It is also the step that needs the filter most.

CO-HOST:
What happens if every agent is a subagent or hidden? No selectable agent at all.

HOST:
Then selection returns the build identifier with no record attached, and context assembly fails the step. That is deliberate. An unconfigured prompt is worse than a visible error, and promoting an internal agent to the front door is how a roster leaks.

CO-HOST:
There is one more case I want to check. An agent marked as both primary and subagent. Does the filter skip it?

HOST:
No. The filter only excludes subagent mode. An agent marked both is selectable as a primary and offered as a subagent. The mode widens where an agent may be used. It never narrows the filter.

CO-HOST:
Now the part I did not expect. The explicit identifier path skips the filter.

HOST:
It does, and that is the point. The subagent tool has to reach subagents. A user can name an agent directly. Selection by name is a lookup, and selection without a name is a policy.

CO-HOST:
So the same function has two personalities.

HOST:
One function, two entry points. A name resolves or fails. No name resolves the default or fails. In both cases the caller gets a selection, and a missing agent becomes an error rather than a silently unconfigured prompt.

CO-HOST:
Why fail the step? Why not fall back?

HOST:
Because falling back means running with an agent the user did not choose, and a prompt nobody wrote. A failed step is visible. A wrong agent is not.

CO-HOST:
And an explicit name that does not exist?

HOST:
The lookup returns no record, and the caller turns that into a not-found error. Naming an agent is a promise that something with that name exists. Resolving a default is a policy. They fail differently because they mean different things.

CO-HOST:
And the list the interface shows?

HOST:
All of them, with the selected one first. The list is for people. The filter is for policy. They are different questions, so they get different answers.

CO-HOST:
Which is the takeaway, I think. Selection is not a sort. It is a filter with a fallback order.

HOST:
And the filter is the only thing standing between an internal helper and your front door.

## 6. Body beat 3 — Inheritance and the ceiling

HOST:
A subagent inherits from its parent in a fixed order, and the chain of inheritance has a hard ceiling.

CO-HOST:
Start with the model, because that is the one that shows up on a bill.

HOST:
The child's model is the explicit model argument if one was given. Otherwise the chosen agent's configured model. Otherwise the parent's model.

CO-HOST:
So an agent can carry its own model, and the parent is the last resort rather than the first.

HOST:
Yes. And the same order decides what happens when you continue an existing child with a different agent. The agent changes. The model changes with it, unless you passed a model explicitly.

CO-HOST:
Why does the explicit argument outrank everything?

HOST:
Because it is the only one a person typed for this call. The agent's model is a preference. The parent's model is a default. The explicit argument is an instruction.

CO-HOST:
Fine. Now the ceiling.

HOST:
Before a child is created, the tool walks the parent chain and counts how deep the conversation already is. The limit comes from configuration and defaults to one.

CO-HOST:
One level. So a subagent cannot spawn a subagent at all by default.

HOST:
Unless you raise the limit. Which is the right shape for this. Depth is a property of a conversation, so two conversations nest independently. A global counter would let one branch exhaust the budget for another.

CO-HOST:
And the check is before creation, not after.

HOST:
Before. Refusing after you have built the child is a cleanup problem. Refusing before is a message.

CO-HOST:
What else is checked before creation?

HOST:
Permission. Spawning is an action called subagent, and the resource is the agent being spawned. So a ruleset can allow one kind of helper and deny another, by name.

CO-HOST:
Which means the roster the model sees is already filtered by what the parent is allowed to run.

HOST:
It is. The model cannot even name a subagent the parent could not spawn.

CO-HOST:
What does the child actually receive?

HOST:
The task, with one sentence in front of it. You are a subagent spawned by another session. A fresh child has none of the parent's framing, so the role is restated rather than assumed.

CO-HOST:
And the continuation. If I pass an identifier for a child that belongs to another conversation?

HOST:
The tool refuses. Continuing requires the child to be a child of the calling session. Otherwise one conversation could drive another's work.

CO-HOST:
One more thing I want to push on. You keep saying child session. A function call would be cheaper and simpler. Why a session?

HOST:
This is the part where the choice looks wrong, so here is the person who made it. The obvious objection is cost. Defend the session.

EXPERT:
A nested call is cheaper. It is also invisible. We need the child to have its own context, its own permission check, its own written record, and its own interruption.

CO-HOST:
You could pass a smaller context into a function and get most of that.

EXPERT:
You could pass the context. You cannot pass the record. If the parent process is interrupted, a stack frame vanishes with it. A child session can outlive the tool call that started it, be continued later by its identifier, and be looked at on its own.

CO-HOST:
So the tool call is a handle rather than a call.

EXPERT:
The tool call waits on a job. The work is a session. That separation lets the foreground wait and the background return share one lifecycle. It also means one set of concurrency behaviour to get right, not two.

HOST:
Thank you. That is the design in one sentence. The tool call is a handle. The work is a session.

CO-HOST:
Which gives me the takeaway. A subagent is a session because a function call cannot be observed, resumed, or stopped on its own.

## 7. Body beat 4 — Foreground, background, and the notice

HOST:
Foreground and background are the same job with two different waits.

CO-HOST:
That sounds like a distinction without a difference. One returns now, one returns later.

HOST:
One returns now and one returns when the child is finished. The difference is who is waiting, and what happens if nobody is.

CO-HOST:
So what breaks if you skip the notice and let the parent forget?

HOST:
Fire and forget. The parent finishes without the result, and the work is lost. Or worse, the parent duplicates it, because it never learned that the child was already doing it.

HOST:
When the tool starts a child, it registers a job with a completion signal. In foreground mode the parent blocks on that signal. The block races two outcomes. The child finishes, or the parent is told to put the work in the background. Losing that race does not cancel the child.

CO-HOST:
So a person can watch a foreground subagent and decide they do not want to wait.

HOST:
And the work keeps going. The wait is released, the child is not.

CO-HOST:
Which means the parent can lose interest without losing the work.

CO-HOST:
What does the foreground parent get when the child is done?

HOST:
The child's final text. And if the child failed, a tool failure that still carries the child's identifier. The parent can continue that conversation or go and look at it. The identifier comes back either way.

CO-HOST:
What does the parent model get in background mode?

HOST:
A short text with the child's identifier and three instructions. Do not sleep. Do not poll for progress. Do not ask the subagent for status. Then a prohibition on duplicating the work or touching the same files, and an alternative. Work on something else, or tell the user what you launched and stop.

CO-HOST:
Why does the model need to be told not to poll?

HOST:
Because a model with an asynchronous job and nothing to do will check on it. It will burn steps asking for status, or it will start editing the same files. The prompt names the anti-pattern and then gives it something to do instead, which is what makes the prohibition stick.

CO-HOST:
Now the notification. Where does the result go?

HOST:
Into the parent session, as a synthetic message. It carries the child's identifier, the child's state, and the child's final text. A background parent is woken to read it. A parent that is itself suspended stores it without waking.

CO-HOST:
Why a message? Why not return the value when it is ready?

HOST:
Because when it is ready, the parent may be idle, suspended, or running in another process. A return value needs a caller who is still on the stack. A message is durable. It is written into the parent's history and it replays.

CO-HOST:
So the child reports by writing to the parent, not by returning.

HOST:
Which is the same move as the rest of the season. The fact is written down before anyone acts on it. The parent does not remember that it is waiting. It reads that the child finished.

CO-HOST:
And if the child fails or is cancelled?

HOST:
The same notice, with a different state. Completed, failed, and cancelled all report. The parent is never left with a job that silently disappeared.

CO-HOST:
What stops two notices for the same child? A restart, a sweep, a retry.

HOST:
The notification identifier. Admitting the notice clears the durable marker exactly once. So a sweep that finds orphaned background work acknowledges it instead of announcing the same completion twice.

CO-HOST:
Which is the takeaway. Background work reports by admitting a message into the parent, not by returning a value.

HOST:
One lifecycle. Two waits. One durable notice at the end.

## 8. The artifact

HOST:
The subagent tool is described to the model in six lines. Here it is, word for word. I am speaking two code identifiers as plain words, and the companion carries the source exactly.

HOST:
"Spawns an agent in a child session to work on the specified task. The output includes a session identifier you can pass back later to continue that specific conversation with the subagent. New child sessions start with fresh context, so include all relevant context and instructions when you don't pass a session identifier. Foreground, the default, runs the subagent to completion and returns its final response. Background mode launches it asynchronously and returns immediately. You are notified when it finishes. Use background only for independent work that can run while you continue elsewhere."

[production note: the source writes a session identifier and a flag name as code, and marks the foreground default in parentheses. The companion carries all six lines exactly.]

CO-HOST:
The third sentence is the one that changes behaviour.

HOST:
It is. A fresh child has none of the parent's history. If the description did not say so, the model would launch a subagent with a one-line task and get back an answer built on nothing. The sentence exists because that failure is common.

CO-HOST:
And the second sentence teaches an affordance.

HOST:
The model would not discover that it can continue the same child. So the description tells it, and the input field repeats it.

CO-HOST:
The last line is a scoping rule.

HOST:
It is. Background is for independent work. Everything else is foreground, because a parent that backgrounds work it needs next will stall.

CO-HOST:
And the list of available subagents is appended after this text.

HOST:
Per request, filtered by permission, with a fallback sentence for the agents nobody described. That fallback says the agent should only be called when explicitly requested. It stops a thin description from becoming an invitation.

CO-HOST:
So the description is generic and the roster is specific.

HOST:
And both are prompt. The tool's documentation is part of the model's interface, which is why it is written with this much care.

## 9. Recap

HOST:
Where we landed. One. An agent is a configuration record. Identity, model, request settings, instructions, mode, visibility, step limit, and permissions.

CO-HOST:
Two. Selection is a filter with a fallback order. Configured default, then build, then the first selectable agent, and a subagent or hidden agent is never selectable.

HOST:
Three. A subagent is a child session. The model resolves as explicit, then the agent's, then the parent's. Depth is counted along the parent chain and defaults to one.

CO-HOST:
And four. Foreground blocks and background returns, but both end with a durable notice in the parent.

HOST:
Say the rule.

CO-HOST:
An agent is configuration, and a subagent is a session. Record the fact before anyone acts on it.
