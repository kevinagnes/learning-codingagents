You build the obvious thing first. A loop. It calls the model, looks at what came back, runs whatever tool the model asked for, drops the result into an array, and calls the model again. Around and around, until the model stops asking.

## 4. Body beat 1 — An agent is five things

HOST:
Strip away the interface and the choice of model, and an agentic coding tool is five things wired together.

CO-HOST:
Five. Go.

HOST:
One. A loop. Something repeatedly decides whether to continue, and what to send next.

HOST:
Two. Tools. Callable capabilities the model is allowed to invoke. Read a file. Edit a file. Run a command. Hand work to another agent.

HOST:
Three. A filesystem. This is a coding agent, so changing the repository is the whole point. Reads and writes are first class effects, not a side channel.

HOST:
Four. Persistence. Every fact that matters is written down before the next decision is made, so a crash, a restart, or a second process can pick up where the first one stopped.

HOST:
Five. Permission. The effects that can hurt your machine are gated on a decision, and that decision cannot be something the model manufactures for itself.

CO-HOST:
That last one is doing a lot of work. Why is permission on the list with the engine parts?

HOST:
Because a coding agent writes to your disk and runs commands on your computer. If the gate is not part of the design at the beginning, it becomes a check you sprinkle on later. And every path you forget is a quiet hole in the policy.

CO-HOST:
So the five are not features. They are load bearing.

HOST:
They are. And here is the thing nobody says out loud. Four of the five exist because things go wrong. Tools exist because the model needs to act. The filesystem exists because the action has to land somewhere real. Persistence exists because the process can die. Permission exists because the action can be harmful.

CO-HOST:
And the loop?

HOST:
The loop is the only one that is about the task. The other four are about surviving the task.

CO-HOST:
Hold on. I want to push on the framing. You are describing a program. A loop with some tools is a program. What makes this an agent and not a script that calls an interface?

HOST:
Two things. The model chooses which tool to call, and what to pass to it, at runtime, from the conversation. You did not write that control flow. And the loop can go around an unknown number of times.

CO-HOST:
So the shape of the program is decided while it runs.

HOST:
The control flow is generated. That is the whole trick, and it is also the whole problem. You are running a plan you did not write and cannot read in advance.

CO-HOST:
Which is why four of the five are about surviving it.

HOST:
The more freedom you give the loop, the more solid the other four have to be.

HOST:
There is one more thing to name, because it comes back all season. A tool is not a plugin bolted onto the side. For the purposes of the request, a tool is part of the model's interface. Its name, its description, and the shape of its arguments all travel with the request.

CO-HOST:
So the model is choosing from a menu you printed.

HOST:
The menu is half the prompt. If you have ever wondered why a tool does not get used, or gets used badly, the description is usually the answer.

CO-HOST:
That is a strange place for a design decision to live. In a sentence of description.

HOST:
It is. But a coding agent is mostly a conversation about what is possible. The tools are what is possible. A vague description is a vague agent.

CO-HOST:
Noted. One loop, four things that keep it survivable, and a control flow nobody wrote.

## 5. Body beat 2 — Why the obvious loop fails

CO-HOST:
Let me defend the obvious loop for a moment, because it genuinely works.

HOST:
It does. In a demo.

CO-HOST:
It calls the model, runs the tools, appends the results, calls again. Simple. Fast to write. Easy to read.

HOST:
And it fails in exactly five ways. Each one maps to an ingredient we named.

CO-HOST:
Go.

HOST:
One. The loop has no memory of itself. The decision to keep going lives in a local variable. Kill the process and the loop dies with it. There is nothing to resume from.

CO-HOST:
What does that look like in practice?

HOST:
A user watches the agent work for six minutes, loses the connection, and starts over. Not from the last completed step. From the beginning.

HOST:
Two. Tools run without a gate. There is no seam between the model asking and the effect happening. Add the gate afterwards and every tool path needs its own check.

CO-HOST:
And that failure is silent.

HOST:
The worst kind. One path forgets the check, a destructive command runs with no prompt, and nobody notices until it matters.

HOST:
Three. The transcript grows without limit. You append every result forever, and one day the request is larger than the window the model accepts, and the provider rejects it.

CO-HOST:
And there is no number anywhere. You have no idea how large it is until it fails.

HOST:
Right. It fails as an error in the middle of a task, with half the work already done.

HOST:
Four. Nothing is observable. There is no record to stream to anybody. The only window into the agent is the process itself.

CO-HOST:
Which means you cannot build an interface on top of it.

HOST:
You cannot build an interface, you cannot write a test that inspects what happened, and you cannot answer what the agent did last Tuesday. All three come from the same gap.

CO-HOST:
And that gap has a cost that shows up later.

HOST:
It does. Somebody asks why the agent changed a file, and the honest answer is that nobody can reconstruct it, because the reasoning lived for a few seconds inside a process that has since exited.

HOST:
Five. Nothing can be steered. You cannot change the plan of a loop that keeps its state in a private variable. The plan is the variable.

CO-HOST:
So you can watch it go wrong and do nothing.

HOST:
You can cancel. You cannot steer. Cancelling ends the work. Steering changes work that is already in progress, and you can only change something you can see.

CO-HOST:
Hold on. I want to point at something. Those are five different complaints, and I think they are one complaint.

HOST:
Say it.

CO-HOST:
The state is in the wrong place. All five of them.

HOST:
That is the whole episode. In the naive design, the state of the run lives in memory, in a closure, on a stack. And every property you want later is a property of where the state lives.

CO-HOST:
Resumability, safety, observability, steering.

HOST:
Four properties, one cause. And there is a fifth, which is the one that actually costs money. If the loop decides from memory, then a retry cannot tell the difference between work that happened and work that did not. So it does it again.

CO-HOST:
So you do not add those four things. You move the state, and they fall out.

HOST:
That is the claim. The rest of the season is the proof.

## 6. Body beat 3 — One call per step, and the part that looks wrong

HOST:
opencode's answer is to make the step the unit. A step is one call to the model, and the durable record that call produces.

CO-HOST:
What goes in the record?

HOST:
The request that was sent, every event that streamed back, and how it finished. That last part is the interesting one. The finish is not only success or failure. It says whether the model stopped, whether it hit the output limit, whether it wants to call a tool, or whether the provider gave up.

CO-HOST:
And that becomes the input to the next decision.

HOST:
It becomes the entire input to the next decision. The loop reads what finished, and chooses whether there is another step.

CO-HOST:
So the model asks for a tool, you run it, and you loop back to the next call.

HOST:
You do not. And this is the part where the choice looks wrong, so here is the person who made it.

HOST:
Welcome. You are the one who has to defend this in code review.

EXPERT:
Happy to. We do not run a loop over tool results. Each step is a single call to the model. Then we stop, and we decide again from what was written down.

CO-HOST:
That sounds slower. You are paying for a round trip through your own code where a normal loop would keep going locally.

EXPERT:
It is the same number of model calls. What changes is where the decision to make the next one lives. In the naive loop it lives in a variable. Here it lives in the record.

CO-HOST:
So you are trading some bookkeeping for the ability to crash.

EXPERT:
We are trading bookkeeping for resumability, for steering, and for permission. All three need the same thing. A seam between the model asking and the effect happening. An in memory loop does not have that seam. It erases it, because asking and doing become the same line of code.

HOST:
And when a tool result comes back, you do not branch on it.

EXPERT:
We write it down, and the next step reads it from history. That is what lets us die in between the two.

CO-HOST:
What is the alternative you rejected?

EXPERT:
The tempting one is to let the model library run the loop for you. It calls the model, runs the tools, and hands you a final answer. It is a few lines. But it hides the exact seam we need, so permissions, persistence, and steering all become things you cannot reach.

HOST:
And the other one.

EXPERT:
Treating each model call as stateless, and letting the caller decide when to stop. That moves the continuation decision into a stack in your program. Then the caller decides, not the record, and the caller is the part that dies.

CO-HOST:
So you keep two things at once. The call itself is stateless, and the decision to continue is durable.

EXPERT:
Yes. That combination is the whole design.

[music sting, short]

HOST:
Thank you. That is the rule, and the project writes it down as a rule it protects. We will read it in a moment.

CO-HOST:
Before that, one practical question. What is the smallest version of this that is actually correct?

HOST:
One call to the model, one written record of it, and a decision to continue that reads from that record. That is the whole requirement. Everything else in the season is a detail hung on it.

CO-HOST:
Before that. What goes wrong if you get continuation wrong?

HOST:
Duplicate edits. A retry re runs a tool that already ran. Or a tool gets skipped, because the only thing that knew it had run was a variable that no longer existed.

CO-HOST:
Which one is worse?

HOST:
The duplicate. It is quiet. The model does the work twice and reports success.

## 7. Body beat 4 — The map, and the scope question

HOST:
So you have a loop with durable state. Now, how do you build it without the pieces collapsing into each other?

CO-HOST:
Which is where most projects of this shape turn into a knot.

HOST:
The dependency rule is one direction. Contracts at the bottom. Implementations depend on the contracts, and nothing depends on the layer above it.

HOST:
There is a package for the wire and storage shapes. Nothing depends on it except the effect library. There is a package for the model boundary, the canonical request and the stream of events. It sits beside the runtime, not underneath it.

CO-HOST:
Why does the model boundary sit beside the runtime?

HOST:
Because a model call knows nothing about sessions. It takes a request and returns a stream of events. Keeping it beside means the runtime can change freely without touching it, and the boundary can be tested with no session anywhere in sight.

HOST:
Then the runtime builds the agent on top of both. Then the package that describes the network surface, and finally the server that wires the runtime to it.

HOST:
There is one more consequence of that direction, and it is easy to miss. The contracts are the shared identity. The runtime does not redefine the shape of a session. It reuses the same definition from the contracts package. So there is exactly one session type in the whole process, not a copy per layer.

CO-HOST:
Why does that matter?

HOST:
Because two definitions of the same thing is a classic bug. An event validates at one boundary and fails at the next, because the two boundaries disagree about what a session is. One definition, one truth.

CO-HOST:
Fine. Now the part I get wrong every time. There are these services, and some are built once and some are built per directory, and nothing in the code says which.

HOST:
So the design declares it. A service is either built once for the whole process, or built for one working directory. The event bus and the database are process wide. The runner, the tools, the permissions, and the filesystem belong to a directory.

CO-HOST:
Why not make everything process wide. It would be simpler.

HOST:
Because the filesystem belongs to a directory, and the tools and permissions belong to it too. Share them, and two projects start reading each other's state. That is not a performance problem. It is a correctness problem.

CO-HOST:
And where do the two meet?

HOST:
One process wide coordinator. When a run starts, it routes that session to the services for its directory. One seam. That single line is the entire story of scope.

HOST:
And one detail about the process wide pieces that pays off later. When durable work is written down, the things that read it run inside the same database transaction. So nothing can ever read a half written fact.

CO-HOST:
Which we come back to.

HOST:
Two episodes from now.

CO-HOST:
There is one more thing I keep getting wrong. The words. You say step, I hear turn. You say execution, I think step.

HOST:
Then let us fix it now, because this season is strict about these. A step is one model call. An execution is one busy period for a session, from the moment work starts until the session would go quiet. To drain is to make one pass over the work that is eligible to run. And a turn is the whole stretch from taking new input until the session would go quiet, which is a sequence of steps.

CO-HOST:
So a turn contains steps, and an execution is the running of them.

HOST:
And a single step is never a turn. That sounds like pedantry until you are debugging a session that ran for four minutes, and you need to know whether it made nine calls or one.

## 8. The artifact

HOST:
The project keeps one sentence as a rule it protects. Here it is, word for word.

HOST:
"Each step is one explicit model stream call that continues from reloaded history. Do not add an in memory tool loop."

[production note: the source contains a code identifier where these words say "model stream call". The companion carries the source line exactly.]

CO-HOST:
It is short.

HOST:
It is doing a lot of work. One explicit call, that is the step. Continues from reloaded history, that is the resumability. And then the last sentence, which is a rule for the future, not a description of the present.

CO-HOST:
Why reloaded history, though. Why not keep the history you already have.

HOST:
Because the loop may be continuing in a different process than the one that started it. Reloading means the next step is built from what was written down. Not from what this process happens to be holding.

CO-HOST:
And what does in memory mean, for a listener who has not hit this yet.

HOST:
It means the state exists only while the program is running. Nothing wrote it anywhere. When the program ends, or crashes, or is replaced, the state ends with it.

CO-HOST:
So the phrase is doing exactly what the design does.

HOST:
Every word of that sentence is load bearing. And then there is the prohibition.

CO-HOST:
Because a year from now somebody will want to add the loop back.

HOST:
Somebody will want to batch a few tool calls into one pass to save a round trip. That sentence is what stops them. The reason it is written as a prohibition is that the argument for adding it will sound reasonable. It always does.

CO-HOST:
That is a rule with a memory.

HOST:
The best rules in a system like this read that way. They name the thing someone will want to do anyway, and forbid it.
