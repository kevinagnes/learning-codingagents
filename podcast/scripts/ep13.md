## 4. Body beat 1 — Order is the whole rule

HOST:
A permission decision is a pure function of three things. An action, a resource, and an ordered list of rules. The last matching rule wins.

CO-HOST:
That sounds tidy until two rules match. Then it is a coin flip with extra confidence.

HOST:
It is not a coin flip. It is position. There is no priority field, no nesting, and no negation. To decide a request you walk the list from first to last. You keep the last rule whose action and resource both match, and you take its effect.

CO-HOST:
Why last rather than first?

HOST:
Because rulesets are composed by appending. A built-in default is broad. It allows everything. Then an agent disables a tool. Then a project asks about secrets. Then a session narrows further. Then a person says always allow this exact command.

HOST:
Each layer is added after the one it wants to override. So the natural rule is that the most recent, most specific layer wins.

CO-HOST:
First match would force every broad rule to be written last.

HOST:
Which is backwards. The broad rule is the floor, so it goes first.

CO-HOST:
And merging is concatenation.

HOST:
Concatenation that preserves order. It does not deduplicate. Two identical rules are both kept, and the later one is the one that answers.

CO-HOST:
What if nothing matches?

HOST:
The answer is ask. Not allow, and not deny. An unconfigured action reaches a person rather than failing quietly or running unchecked.

CO-HOST:
So the safe default is to bother a person.

HOST:
It is the only default that cannot be wrong in the dangerous direction.

CO-HOST:
Allow would run unchecked, and deny would break working configurations.

HOST:
Exactly.

CO-HOST:
Now the matching itself. Is it a glob library?

HOST:
No. It is a small translation. A star becomes any run of characters. A question mark becomes exactly one character. Everything else is escaped, so a rule is never accidentally a regular expression. Backslashes are normalized to forward slashes, so a path rule reads the same on every platform.

CO-HOST:
So a rule cannot smuggle in a wildcard the author did not intend.

HOST:
That is the reason for the escaping. The pattern language is deliberately tiny. If it were a real expression language, every rule would be a small program, and reading a ruleset would require a parser in your head.

CO-HOST:
And it is anchored at both ends.

HOST:
So a pattern matches the whole resource. Without the anchors, a rule about one kind of secret file would match a path that merely contains it. There is one special case. A pattern ending in a space and a star also matches the bare prefix. So a rule for git with arguments also covers git alone.

CO-HOST:
That is a convenience with a cost.

HOST:
It is. But it means one rule covers the command and its arguments, which is what people mean when they write it.

CO-HOST:
Now the part I always get wrong. Deny is checked in a separate pass.

HOST:
Before the saved rules are even appended. The configured rules are the agent's and the session's, concatenated. If any resource in the request is denied there, the request is blocked and the later layers never get a vote.

CO-HOST:
So an always allow cannot undo a hard deny.

HOST:
Cannot. That is the point of the separate pass. Deny is the one effect that short-circuits. A saved grant is the one thing that must never resurrect what an agent or a session forbade.

CO-HOST:
And the saved grant is durable.

HOST:
A row keyed by project, action, and resource, appended to the ruleset as an allow. Project scoped, because always means always for this project. Repeated grants are idempotent, because the key is unique.

CO-HOST:
Which is why saved rules end up last in the walk. They are the decisions made after the config was written.

HOST:
They are the last word, by construction. And the deny pass runs before they are even in the list, which is what keeps them from being too powerful.

CO-HOST:
So the takeaway is about authorship. Order is the entire precedence mechanism, so the most specific rule goes last.

HOST:
And the broad rule goes first, where it belongs.

## 5. Body beat 2 — The no that cannot be read

HOST:
A refusal is not a result. In this implementation it is carried as a defect, and that is the whole point.

CO-HOST:
I want to stop you there, because that sounds like a category error. A defect is a bug. A person clicking reject is not a bug.

HOST:
Agreed. The channel is being used for a property, not for a meaning. The property is that no ordinary error handler can see it.

HOST:
Start with the three effects. Allow is silent. Deny is a typed error the model reads, so it can adjust. Ask suspends the tool, because the answer is not known yet.

CO-HOST:
So suspending is not a refusal. It means the answer is still coming.

HOST:
The decision is deferred, not made.

CO-HOST:
What does suspending mean mechanically?

HOST:
A pending request is registered. The request, plus a one-shot awaitable signal, keyed by request identifier. The request is published to clients. The tool waits on the signal. A client replies, and the reply either succeeds the signal or fails it.

CO-HOST:
Does the waiting tool hold anything else open?

HOST:
Only the pending request and the signal. No timer, no polling loop. A slow person costs nothing. And that is what lets a person take a minute without the agent burning anything.

CO-HOST:
Now the reject. Why not fail the signal with an error like everything else?

HOST:
Because every tool wraps its body in a blanket error mapper. That wrapper turns any typed failure into a tool failure. A tool failure becomes a tool result, and a tool result is text the model reads. The model reads permission denied as an obstacle, and it routes around the obstacle.

CO-HOST:
Which is the cold open. It reads like the command was wrong, not like the person said no.

HOST:
Exactly. So a plain decline is raised as a defect. In this runtime it dies instead of failing. Error mappers only rewrite failures, so the decline flies through every tool's error handling untouched.

CO-HOST:
Then who catches it?

HOST:
One place. The boundary that produces tool results inspects why the tool stopped. It finds the decline inside the cause and re-raises it typed. From there the step marks the tool aborted, and it interrupts the step.

CO-HOST:
So the no ends the step.

HOST:
The no ends the step. It does not become a message the model can react to.

CO-HOST:
And the reject with a message?

HOST:
That one stays typed. The user said no, and then said do it this way instead. The message is information, so the tool wrapper converts it into a tool failure. The model reads the feedback, and the step continues.

CO-HOST:
So the split is by information content.

HOST:
A plain no says nothing the model can use, so it never becomes model text. A no with feedback says something, so it does.

HOST:
This is the part where the choice looks wrong, so here is the person who made it. You carry a user's refusal as a defect, and a defect normally means the program is broken. Defend that.

EXPERT:
We need the refusal to be un-swallowable. A defect is the one channel that every ordinary handler agrees not to touch. We use it to mean that this must never be converted into text.

CO-HOST:
But that makes the tunnel load bearing. If one layer misses the recovery, the whole execution dies with a stack trace.

EXPERT:
It does, and that is the trade. The tunnel is opened in exactly one place and closed in exactly one place. Everything below the tool boundary may die, and one layer above converts it.

CO-HOST:
Why not a special error type, with a rule that nobody may catch it? That is a convention.

EXPERT:
A convention is what fails when a new tool is added by someone who has never seen the convention. A defect cannot be caught by the wrappers that already exist. The safety does not depend on the next author remembering.

CO-HOST:
And why not let the model know it was denied, so it can choose something else?

EXPERT:
Because then it negotiates. A model that is told the user denied it will explain why the action was reasonable. Or it will try a neighbouring action. If you want it to know why, type a message. That path is deliberate, and it is the one that keeps the step alive.

HOST:
Thank you. That is the rule of the season, and it is the hardest one to believe. A decline never reaches model context.

## 6. Body beat 3 — One reject, one batch

HOST:
One reject settles the whole batch. One always settles only what its new rule covers.

CO-HOST:
Give me the case.

HOST:
The model proposes four independent edits in one step. All four ask. The user sees four prompts stacked up. They approve the first and reject the second.

CO-HOST:
And the third and fourth are still sitting there.

HOST:
Which is the failure. A step with a rejected call in the middle and two prompts pending is a state nobody can reason about. So the reply is applied to the session's whole batch.

HOST:
On reject, the handler fails the targeted request and deletes it. Then it walks every other pending request in the same session. It publishes a rejection for each, and fails each one with the same error. The same message, if there was one.

CO-HOST:
Why the same message?

HOST:
Because the feedback applies to the batch. If the user typed a correction, every call in that batch gets the correction attached to its failure.

CO-HOST:
And the fan-out is filtered by session.

HOST:
By session, not by tool and not by action. Pending asks in another session are somebody else's decision.

CO-HOST:
Does the batch boundary follow the step?

HOST:
It follows the session. A step can run several calls, and a session can have work from more than one step in flight. Session is the boundary that keeps another conversation's prompts out of your decision.

CO-HOST:
What about the once path? The person approves this one call and nothing else.

HOST:
Then only the targeted request settles. Nothing fans out, because nothing was learned that applies to the siblings. Once is a decision about one call. Always is a decision about a rule.

CO-HOST:
And what if two clients answer at the same time?

HOST:
The reply is uninterruptible, and settling removes the request from the pending map. The second answer finds nothing to settle, so it fails as not found rather than failing the batch twice.

CO-HOST:
Now always. That one is conditional.

HOST:
It writes the saved rule first, then re-evaluates every other pending request against the updated rules. If the re-evaluation now resolves to allow, that request is released. If it still asks, it stays pending, waiting for a person.

CO-HOST:
So always allow git releases the other git calls and leaves the remove command alone.

HOST:
That is the shape of it. The grant covers what the grant covers. Coverage is decided by the same evaluation function, not by comparing strings.

CO-HOST:
Which is why the saved rule has to be written first.

HOST:
Otherwise the sibling check reads stale rules and releases nothing. The order inside the handler is part of the semantics.

CO-HOST:
And the whole handler is uninterruptible.

HOST:
So a client reply cannot be interrupted halfway through failing a batch. The batch settles completely or not at all.

CO-HOST:
Here is my pushback. Why not let each prompt settle on its own? Some people want to answer one at a time.

HOST:
Because the step is one unit. A half-decided step is a state the model cannot see and the person cannot clean up. A batch reply is the smaller surprise.

CO-HOST:
And if the fan-out is skipped?

HOST:
The step hangs on the remaining prompts until somebody answers each one. And a rejected call sitting in the middle of a running step is a state with no good explanation.

CO-HOST:
So the same error that ends the step for one call ends it for the batch.

HOST:
One reject, one ending.

CO-HOST:
And a reject with no message is the same defect in every sibling.

HOST:
The same defect, repeated.

CO-HOST:
So reject is total and always is conditional.

HOST:
A rejection is a statement about the whole batch. An always is a statement about one rule, which may or may not cover its siblings.

CO-HOST:
That is the takeaway. The batch boundary is the session. A no is total, and a yes is conditional.

## 7. Body beat 4 — The question tool

HOST:
Asking a person is itself a permissioned action. And dismissing a question means the same thing as declining one.

CO-HOST:
Why would asking be permissioned? The dangerous part is the tool, not the question.

HOST:
Because a child session that stops to ask a person can stall work nobody is watching. The general subagent denies the question action outright. The title and summary agents deny everything. Asking is a capability, so it is on the list.

CO-HOST:
Now the case where asking is the right move.

HOST:
The agent is about to scaffold a project. It needs three decisions. Which package manager, whether to include tests, and which license. It could guess and be wrong, then do the work twice. Or it could ask.

HOST:
The primitive underneath is a form. A form has an identifier, a session, a title, and a list of fields. A field has a key, a type, and constraints. Options, a length, a pattern, a minimum, whether it is required.

CO-HOST:
And conditional fields?

HOST:
A field can be visible only when earlier answers say so. The conditions may reference earlier fields and nothing else, so visibility is a single forward pass. There is no cycle to resolve.

CO-HOST:
That is a small rule with a large effect.

HOST:
It means the form can be rendered in one pass.

CO-HOST:
What are the states?

HOST:
Pending, answered, or cancelled with an optional message. A reply is validated against the field definitions. Required fields, option membership, patterns, active conditions. A bad answer returns an error instead of being stored.

CO-HOST:
So a client cannot submit an option the form never offered.

HOST:
It cannot. The form is the contract, not the rendering.

CO-HOST:
And the form does not disappear while the person thinks?

HOST:
No. A pending form never expires. A form that has been answered or cancelled is kept for a short while, so a client that reconnects can still read the outcome. The lifetime is keyed on the state.

CO-HOST:
Now the question tool itself.

HOST:
It wraps a form. Each question becomes a field. The options become the value space, and free-form input is always enabled. The description tells the model not to add its own free-form option, because the client already adds one.

CO-HOST:
And the answer comes back as model text.

HOST:
A sentence that pairs each question with its answer, plus a closing line. You can now continue with the user's answers in mind. That closing line exists because models otherwise treat the answer as a new question and ask again.

CO-HOST:
Now the dismissal, which is the interesting part.

HOST:
A dismissal with no message dies as a cancellation, through the same tunnel as a permission decline. The step ends. A dismissal with a message becomes an ordinary tool failure carrying that message, so the model reads it and continues.

CO-HOST:
So closing a prompt is not the same as answering no to every question.

HOST:
It is not. Closing means the asker gets nothing. A no would be an answer.

CO-HOST:
One more thing. If the model asks three questions in one call, does the person answer them together?

HOST:
It is one form with several fields.

CO-HOST:
And a reply that is valid for one field and invalid for another?

HOST:
Rejected. Validation checks every field before any answer is stored.

CO-HOST:
And what happens if the person presses stop while the form is open?

HOST:
Interrupting the wait cancels the form. The wait is interruptible. The settle is not. So stopping leaves no zombie prompt on screen for a request nobody is waiting on.

CO-HOST:
The wait can be cancelled and the settle cannot be half-written.

HOST:
Which is the same split as the permission wait. One primitive, two consumers.

CO-HOST:
So the takeaway is about reuse. A form is the general way to ask a person, and the question tool is one consumer of it.

HOST:
Permissions are the other. They differ in presentation, not in lifecycle.

## 8. The artifact

HOST:
The question tool's description is model-facing guidance. It opens with a numbered list of four purposes. I will describe that list rather than read it, because the numbering does not survive speech. Then the usage notes, which I will read word for word, with one code identifier spoken as words.

CO-HOST:
Go ahead.

HOST:
"A Type your own answer option is added automatically. Do not include a separate option for free form answers. Set the multiple flag to allow selecting more than one option. If you recommend a specific option, make that the first option in the list and add Recommended at the end of the label."

[production note: the source writes the free-form option name and the multiple flag as code. The read drops quotation marks and parentheses, expands one contraction, and speaks that identifier as words. The companion carries the description exactly, including its numbered list.]

CO-HOST:
The first line is a fact about the interface.

HOST:
And a fact the model cannot discover by itself. Without it, the model adds its own free-form option, and the form shows two.

CO-HOST:
The second is a convention with a renderer behind it.

HOST:
The recommended label is a contract across layers. The model writes the word, the client displays it, and the person sees a suggestion rather than a neutral list. That is how the model expresses a preference without a separate field.

CO-HOST:
So the recommendation travels as text inside a label, not as a field of its own.

HOST:
Which means the client does not need to understand what a recommendation is. It renders labels, and the convention does the rest.

CO-HOST:
And the numbered list above it?

HOST:
It tells the model when asking is appropriate. Preferences, ambiguity, implementation decisions, and direction. Without it, models either never ask, or they ask about trivia.

CO-HOST:
Which is the same lesson as the subagent description. The tool's documentation is part of the interface.

HOST:
And the answer string is part of it too. Pairing each question with its answer keeps the mapping when several were asked at once. The closing line restarts the work.

## 9. Recap

HOST:
Where we landed. One. A rule list is ordered. The last matching rule wins, wildcards are translated and not globbed, and the default answer is ask.

CO-HOST:
Two. Allow is silent. Deny is a typed error the model reads. And ask suspends the tool on a one-shot signal until a person replies.

HOST:
Three. A plain decline is carried as a defect, so no error handler can turn it into tool output. It is recovered in one place, and it ends the step. A decline with feedback stays typed.

CO-HOST:
And four. A reject settles the session's whole batch. An always releases only what its rule covers. And dismissing a question follows the same tunnel.
