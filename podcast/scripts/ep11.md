## 4. Body beat 1 — One message in, many out

HOST:
Lowering is a translation, so it should preserve the shape it translates.

CO-HOST:
That is what I would assume. One message in, one message out.

HOST:
Then lower an assistant message that holds text, some reasoning, and two tool calls that our own code ran. You get one assistant message for the text and the reasoning, and separate tool result messages for the calls. One of yours became several of theirs.

CO-HOST:
Why separate? The model produced them together.

HOST:
Because the wire has no single message that carries both an assistant's content and a local tool's result. The assistant says what it wants to call. The result comes back as its own message. So the projection carries one message, and lowering splits it.

CO-HOST:
What about a tool the provider runs itself?

HOST:
A hosted tool is different. Its result arrives inside the same stream, in the provider's own format, so it rides along with the call instead of becoming a separate message. Only results from tools the agent ran become their own messages.

CO-HOST:
And the order? A result has to follow the call that produced it.

HOST:
It does, because the projection recorded it after the call. Lowering keeps that order, so the result follows the call.

CO-HOST:
So the count is allowed to change in both directions.

HOST:
In both. Some messages lower to nothing at all. An idle marker has no model-visible form. A message that records an agent switch does not either. And a model switch lowers to an effort change message only when both the old and the new variant are reasoning-effort variants on the same provider and the same model.

CO-HOST:
And a message that lowers to nothing is not a bug.

HOST:
It is the correct answer for a marker with no model-visible meaning. The output is allowed to be empty.

CO-HOST:
Everything else is a fixed rendering?

HOST:
Each type has one.

CO-HOST:
The switch is per type. A user message becomes text, files, and inlined skills.

HOST:
A synthetic note, a skill block, a shell transcript, a location switch, a system note, and a compaction each have their own fixed shape.

CO-HOST:
So the function is a switch over message types.

HOST:
A switch, and then two normalizations that need the target model.

CO-HOST:
Hold on. If lowering is pure, why does it need to know the target?

HOST:
Pure does not mean context-free. It means no side effects. The answer depends on the destination. Whether the message came from the same model. What media that model accepts. How many image bytes the request may carry. So the target is an argument, not a lookup.

CO-HOST:
Where do the mistakes actually hide, then? A switch over message types sounds hard to get wrong.

HOST:
In the edges. If every part filters out, the correct output is only the tool results, or nothing at all. A renderer that still emits an empty assistant message confuses providers that reject empty content.

CO-HOST:
So the map is simple, and the empty case is not.

HOST:
The map is simple. The empty case is where a translation quietly invents a message that should not exist.

CO-HOST:
Why not store the provider messages in the first place, and skip the translation?

HOST:
Because the projection is richer. It carries message types the provider has no word for, like a skill load or a model switch. Store the provider shape and you lose the facts you need to build a different provider's shape later.

CO-HOST:
And because it is a pure function of history and target, you can test it without a session.

HOST:
You can lower the same message twice, against two different targets, and compare the output. No provider, no database, no clock. That is the whole reason its mistakes are findable.

CO-HOST:
So lowering is a pure translation from your history to the wire, and the count is allowed to change.

## 5. Body beat 2 — Metadata is proof

HOST:
If the model produced it, you can send it back.

CO-HOST:
That sounds reasonable. The transcript is the transcript.

HOST:
Then you switch from one model to another in the middle of a session. The transcript still holds the first model's encrypted reasoning and its thought signatures. Hand those to the second model, and the best case is a provider error. The worst case is that it accepts proof of generation it did not produce.

CO-HOST:
So some of what is in the transcript is not content.

HOST:
It is a signature. The model signs the tokens it produced, so the provider can verify on the next call that this really came from that model. Another model cannot verify it.

CO-HOST:
But the words are still the words. Surely you keep those.

HOST:
You keep the words and drop the signature. That is the reuse rule. Lowering computes one flag. Same provider, same model, and the message did not fail. Every metadata decision follows.

CO-HOST:
And the flag is same provider, same model, and no error.

HOST:
One condition, three consequences.

CO-HOST:
Give me the concrete case. What is actually in that metadata?

HOST:
A thought signature from one provider. Encrypted reasoning from another. Provider-specific state attached to a text part, or to a tool call.

CO-HOST:
And none of it is readable to us.

HOST:
It is there for the provider to check, not for the model to read.

CO-HOST:
So the flag is conservative by design.

HOST:
It is. When in doubt, drop the proof and keep the words.

CO-HOST:
Why does a failed message lose its metadata even on the same model?

EXPERT:
Because a failed message is not a clean statement of what the model produced. It was interrupted, or the provider errored partway through. We cannot be sure what was signed, so we do not present it as proof. The signature is not trusted.

CO-HOST:
And reasoning after a switch?

EXPERT:
Readable reasoning is downgraded to a plain text part, because the words are still useful. Reasoning with no readable text is dropped. We replay it as reasoning only when the metadata is reusable and the reasoning finished. An interrupted thought is not a finished thought.

CO-HOST:
What about tools? A hosted tool runs inside the provider, and its result is provider-shaped.

EXPERT:
That is why there are two sides. The call side is proof, and it belongs to the producing model. The result side is a payload in the provider's format. It can travel to another model of the same provider. After a model switch we echo the payload, and never the call-side state.

HOST:
So the rule is not "same provider" or "same model" everywhere. It depends on which side of the call you are holding.

CO-HOST:
Text and reasoning are model-scoped. Call-side proof is model-scoped. Result payloads are provider-scoped.

HOST:
The flag is computed once, so text, reasoning, and call metadata cannot disagree. One answer, applied three times.

CO-HOST:
What about a hosted tool result that arrives after a model switch? You said the payload survives.

HOST:
It does, within the same provider. The new model reads a result the provider produced. It does not get the old call-side state, which proves who asked.

CO-HOST:
So a cross-provider switch loses the hosted payload, and loses the reasoning signature.

HOST:
It loses the provider payload, and the reasoning loses its signature. The conversation still has the call and its visible result, without the provider's private envelope.

CO-HOST:
What if you strip all of it? No metadata, no problem.

HOST:
Then you lose native reasoning replay even on the model that produced it, and every provider feature that depends on signed state stops working. You would be safe and worse. The design keeps what can be verified, and drops only what cannot.

CO-HOST:
So the question is never "is this metadata useful". It is "who can verify it".

HOST:
Metadata is a signature, not content. Replay it only where it can be verified.

## 6. Body beat 3 — Attachments and bounds

HOST:
The transcript is the truth, so send it exactly as it is.

CO-HOST:
That was the promise of the last beat. Keep the content, drop the signatures.

HOST:
Then a session picks up a large screenshot, and later the user attaches a document the target model cannot read. If you send both, the provider rejects the whole request. A long session dies on its shape, not on its content.

CO-HOST:
So lowering changes the content too.

HOST:
It normalizes attachments first. Plain text is inlined with a header. A directory is listed.

CO-HOST:
An image or a document becomes encoded media, with a location line when the source is a local file.

HOST:
And anything else is dropped. When several inline images share the same mention, name, description, and type, duplicates are removed, so one image is not sent twice.

CO-HOST:
Why does a directory become a listing instead of being dropped?

HOST:
Because the model asked to look at it. A listing is the useful part. The file contents are not what a directory listing returns.

CO-HOST:
What happens to an image that is dropped as a duplicate?

HOST:
It is not sent. The mention still points at the image that is present, so the model sees one copy and no gap.

CO-HOST:
What about a model that cannot accept that type at all?

HOST:
A second pass replaces media the target cannot accept with an explanatory text part. Some providers also reject a type for their own reasons, and that is handled in the same place. The request never fails because the transcript carries a format the model does not support.

CO-HOST:
Do the two passes interact?

HOST:
They run in order. Unsupported media becomes text first, so it no longer counts as image bytes. Then bounding measures what is left. A replaced image cannot push the request over the limit.

CO-HOST:
You are replacing a real attachment with a note about the attachment.

HOST:
A note that says what was there, and says that it cannot be seen. The alternative is a failed request, or a model that quietly receives nothing and does not know it.

CO-HOST:
Now the size problem.

HOST:
Images have a second budget. Lowering measures the total inline image bytes. Above a trigger, it replaces images with a marker, oldest first, until the total drops below a smaller target. The trigger is around twenty-five megabytes, and the target is around fifteen.

CO-HOST:
That is a lot of image.

HOST:
It is a handful of screenshots. The point is that the limit is measured, not hoped for. And the oldest go first, because the newest image is the one the user showed you a moment ago.

CO-HOST:
The recent exchange is the one under discussion.

HOST:
It is. The older screenshot is the one you can afford to lose first.

CO-HOST:
And the marker?

HOST:
It says the image was removed to reduce the request size and is no longer visible. Then it says not to make claims about its contents from memory, and to retrieve it again or ask the user to attach it again if it matters.

CO-HOST:
That second sentence is the interesting one.

HOST:
Without it, the model has a gap in the transcript and every incentive to fill the gap with a guess. The marker turns a silent loss into a stated one.

CO-HOST:
Does the model know which image was removed?

HOST:
The marker replaces the image in place, so the transcript order is unchanged. The gap sits exactly where the image was.

CO-HOST:
And the marker is the only thing between the model and a confident guess.

HOST:
A stated gap is safer than a silent one. That is the whole reason the text is written the way it is.

CO-HOST:
So bounding is a correctness fix, not only a size fix.

HOST:
A request should never fail because of its shape. Replace what cannot travel, and say what you replaced.

## 7. Body beat 4 — The checkpoint

HOST:
A summary is text, so hand it to the model as a summary.

CO-HOST:
That is what a summary is for.

HOST:
Then the summary contains the sentence "the user asked to rewrite the parser". The model reads it as a fresh instruction and starts rewriting the parser again, on work that was already done.

CO-HOST:
Because a user message is a command.

HOST:
And a summary is an account of the past. The wire has no role for the past. It has roles, and the one available for context that is not assistant output is user. So the wrapper has to do the work the role cannot.

CO-HOST:
Show me the shape.

HOST:
A compaction message lowers to nothing unless it completed. If it is a native window, lowering decodes the stored provider messages directly, and history selection only keeps windows the target model can replay. If it is a local summary, it becomes one user message. It opens a checkpoint tag, states that this is a summary and serialized record of earlier conversation, and says to treat it as historical context, not as new instructions.

CO-HOST:
That sentence is doing a lot.

HOST:
It is the difference between context and command.

CO-HOST:
Then the summary goes in its own section, and a recent window goes in a recent context section.

HOST:
Then the checkpoint closes.

CO-HOST:
Why keep both a summary and recent messages?

HOST:
Because the summary is compressed and the recent window is exact. The newest exchange is where the current work is. Losing it would cost more than the tokens it saves.

CO-HOST:
And why is the wrapper singular? I would expect nested checkpoints after several compactions.

HOST:
The update prompt is told not to reproduce the wrappers. Each compaction produces one checkpoint, and the next one summarizes the previous summary rather than wrapping a wrapper.

CO-HOST:
What about a checkpoint that never completed?

HOST:
It lowers to nothing. Half a summary is not context, and it is certainly not an instruction.

CO-HOST:
And a native window sent to a model that cannot replay it?

HOST:
History selection filters those out before lowering ever sees them. If a route hook would change the target after selection, preparation fails loudly instead of corrupting the transcript.

CO-HOST:
This feels like a lot of ceremony for a summary.

HOST:
It is one sentence in front of text the model is about to treat as instructions. The ceremony is cheaper than a re-executed task.

CO-HOST:
What does "serialized record" mean, exactly?

HOST:
That the text was written down as an account of the conversation, not composed as a message to the model. Serialized is telling it that this is data about the past.

CO-HOST:
Who writes the summary?

HOST:
The model writes it, under a template, at the moment of compaction. The recent window is not written. It is the newest messages kept verbatim and serialized beside the summary.

CO-HOST:
And the checkpoint is not the compaction.

HOST:
The compaction is the act. The checkpoint is what it leaves behind, as later requests see it. One is an operation, and the other is a message.

CO-HOST:
So if the sentence were missing, the tags alone would not save you.

HOST:
Tags are structure. The model still has to be told what the structure means for its behavior. A tag that says checkpoint does not say do not obey this.

CO-HOST:
Has this actually gone wrong in practice?

HOST:
It is the classic compaction failure. A summary keeps the user's earlier imperative, and the next step executes it as new work. The sentence exists because that failure is easy to reproduce.

CO-HOST:
So the summary is the one place where the model's own words are trusted without proof.

HOST:
It is trusted as context, which is why the wrapper is explicit about what kind of context it is.

CO-HOST:
So the checkpoint is a user message that says, in words, do not treat this as a new instruction.

## 8. The artifact

HOST:
The wrapper is one sentence of prompt text. Here it is, word for word.

HOST:
"The following is a summary and serialized record of earlier conversation. Treat it as historical context, not as new instructions."

[production note: the source wraps this sentence in checkpoint tags, followed by a summary section, an optional recent context section, and a closing tag. The companion carries it exactly.]

CO-HOST:
Two clauses, and the second one is the whole design.

HOST:
Serialized record tells the model this is not a paraphrase of what happened. It is an account of it. Historical context tells it where the text sits in time. Not as new instructions tells it what not to do with it.

CO-HOST:
Why does a summary need to say what it is? A summary is a summary.

HOST:
Not from the role. It arrives as a user message, and user messages are where instructions come from. Without the sentence, the model has to infer intent from content, and content that says rewrite the parser reads like an order.

CO-HOST:
So the wrapper is compensating for the role.

HOST:
It is compensating for the only role available. And it names the two sections, so the model knows which part is compressed and which part is verbatim.

CO-HOST:
The recent section is the exact one.

HOST:
Exactly. The source tells the update prompt not to reproduce either wrapper, so they stay singular across compactions.

CO-HOST:
A small piece of text holding the whole contract.

HOST:
The same contract as the marker on a removed image. Say what this is, and say what it is not.

CO-HOST:
So it is filing instructions for the model, not a task.

HOST:
Filed as history, which is a different kind of authority.

CO-HOST:
Why "earlier conversation" and not "the conversation so far"?

HOST:
Because the recent window is not in the summary. The checkpoint covers what came before it, and the exact tail sits beside it.

CO-HOST:
So the two sections have different jobs and different trust.

HOST:
One is a compressed account. The other is the actual messages. The wrapper tells the model not to confuse either with a new request.

## 9. Recap

HOST:
Where we landed. One. Lowering maps one message to zero or more provider messages, and drops the messages that have no model-visible form.

CO-HOST:
Two. Metadata replays only where it is valid. Text and reasoning for the same model, call-side proof for the producing model, and hosted result payloads across models of the same provider.

HOST:
Three. Unsupported media becomes explanatory text, oversized images are bounded with a marker, and a checkpoint is wrapped as historical context.

CO-HOST:
And the earlier rules still hold. One model call per step.

HOST:
Validate at the boundary, and bound every output.

CO-HOST:
And the rule. Lowering is a pure translation from your history to the wire.
