## 4. Body beat 1 — The request is intent, not the wire

HOST:
Here is the claim. A good model boundary sends the provider's own request shape, because anything else is a copy you have to maintain.

CO-HOST:
That sounds efficient. Every provider publishes a client library. Why not let its request type be the request?

HOST:
Because then every caller is coupled to one provider. And every feature you add next has nowhere to live.

HOST:
Think about what you actually want to say. Here is a model. Here is an ordered list of system parts. Here are the messages so far. Here are the tools the model may call. Here are the sampler settings. None of that is any provider's format. It is the intent of the call.

CO-HOST:
But the provider needs bytes, not intent.

HOST:
So the boundary compiles it. One step turns the canonical request into the provider's own body and checks that body against the provider's shape. A second step prepares the transport. The loop never sees the body.

CO-HOST:
Why split those two? Compiling and preparing sound like one job.

HOST:
Because you can test the body without a network. And a provider that speaks over a different transport still compiles the same way.

HOST:
Now the parts that look small and are not. The system prompt is a list of parts, not one string. Providers disagree about whether there is a privileged system role, and where cache markers go.

CO-HOST:
So a part is not a paragraph. It is a unit the boundary can move.

HOST:
A unit it can move, and a unit it can attach something to. One string would have to be cut apart again to find the place for a cache marker.

HOST:
The request is also immutable. Every layer that enriches it returns a new request instead of changing the one it was given.

CO-HOST:
That sounds like extra copying for no reason.

HOST:
It is the opposite. Three layers touch it on the way out. If they mutate a shared value, the last writer wins and the other two vanish.

CO-HOST:
And the same input produces the same request twice.

HOST:
Which is a property you can test.

CO-HOST:
And two spellings of the same request would break that property. A copy per provider would drift too.

HOST:
Now the message itself. A message is a role plus a list of typed content parts. Text. Media. A tool call. A tool result. Reasoning. A compaction marker. An effort marker. Seven kinds, and the list is exhaustive on purpose.

CO-HOST:
Seven feels like a lot for one message.

HOST:
Each one is a different thing a provider can carry. Media is not text. A tool result is not a tool call. If you flatten them, every translator has to guess.

CO-HOST:
Why does exhaustive matter?

HOST:
Because adding an eighth kind becomes a compile error in every translator. That is the cheapest bug you will ever fix. The alternative is a part that silently disappears on the way out, and a model that never sees a tool result.

CO-HOST:
Fine. What about tools?

HOST:
A tool definition is a name, a description, a shape for the input, and an optional shape for the output. The name the model sees is the name the registry uses. If those two drift, the model calls something that does not exist.

CO-HOST:
I want to push here. All this canonical shape is a second shape to keep in sync with the first. Why is that not more work than the branches?

HOST:
It is more work up front. The payoff is one vocabulary. A new provider is a translator, not an edit to the loop. Fallback replays the same intent through a different route.

CO-HOST:
So the request is the thing you keep, and the body is disposable.

HOST:
The body is a translation. The request is what you meant. Describe the call once, in your own words, and compile it per provider.

## 5. Body beat 2 — The stream has to end on purpose

HOST:
Here is the claim. When the stream stops, the answer is finished.

CO-HOST:
That is how every stream reader I have written behaves. The loop ends, and you continue.

HOST:
And that is the bug. A stream can stop because the network dropped, because the provider died, because a proxy timed out, or because the model finished. Those are not the same event, and only one of them means you have a usable answer.

CO-HOST:
What does the failure look like in practice?

HOST:
Half a tool call. The arguments stream in as text, the connection ends, and your code assembles what it has. The JSON does not parse. Or worse, it parses, because the truncation happened at a convenient brace, and you send a tool call the model never finished asking for.

HOST:
So the boundary makes the ending explicit. A stream is a sequence of canonical events, and it must contain a terminal event. A finish, or a provider error. If the stream ends without one, the boundary fails it. If anything arrives after one, the boundary fails it too.

CO-HOST:
So end of stream is not success. End of stream is a missing ending. And the provider cannot tell you the difference after the fact.

HOST:
Exactly. Inside the stream, the model's output arrives in four shapes. Text arrives as a start, some deltas, and an end. Reasoning arrives the same way. Tool input arrives as a start, deltas of raw text, and an end. And the tool call itself arrives once, with the input already parsed.

CO-HOST:
Why parse it twice? The deltas are already JSON.

HOST:
The deltas are a partial JSON string, and partial JSON is not a value. The boundary keeps a best-effort parse of the accumulated text for display, so a user can watch the arguments appear. But the value you execute comes from one parse at the end.

CO-HOST:
So the display is allowed to be optimistic, and the execution is not.

HOST:
The display can lag. The execution cannot. And if the final parse fails, you get an explicit tool input error, not a half object.

CO-HOST:
So the display can show a value the tool never receives.

HOST:
There is one lovely edge case. A tool that takes no arguments may produce no deltas at all. An empty string is treated as an empty object. Without that line, every zero-argument tool fails.

CO-HOST:
That is a one-character fix for a whole class of bugs.

HOST:
It is. The last piece is the finish reason. It is a closed set. The model stopped. It hit the output limit. It wants tools to run. A content filter refused. The provider errored. Or nobody knows.

CO-HOST:
Nobody knows is a strange value to ship.

HOST:
It is the honest one. And it has a rule. Unknown is treated as an incomplete stream, not as a stop. A provider that cannot say why it stopped cannot be trusted to have stopped cleanly.

CO-HOST:
What does the loop do with the rest of the set?

HOST:
It turns each one into a decision. Wants tools means the tools ran, and whether there is another step comes from what they recorded. Hit the output limit means the budget ran out. A content filter is a policy refusal, and the boundary keeps the provider's category and explanation so you can tell it apart from an ordinary stop.

CO-HOST:
So the finish reason is not a label on the response. It is the input to the next decision.

HOST:
It is the only thing the loop has to branch on. A provider-specific value would leak into the loop, and the loop would need a branch per provider again.

CO-HOST:
Which is the whole thing we were trying to avoid.

HOST:
Which is the whole thing. A branch per provider is exactly where the quiet bugs live. A stream is finished only when it says so.

## 6. Body beat 3 — Some provider state is proof

HOST:
Here is the claim. Provider metadata is opaque, so the safe move is to strip all of it before the next request.

CO-HOST:
That was my instinct. If I do not understand a field, I do not send it back.

HOST:
That instinct is half right, and the half it gets wrong is expensive. Some of that opaque state is proof that this model produced this content. Strip it and the provider rejects the replay, or accepts it and behaves strangely.

CO-HOST:
Give me the case.

HOST:
A session runs for an hour on one model. The user switches models. The next request contains a signature the old model attached to its text. The new model did not produce it. The provider rejects the request, and the transcript looked fine the whole time.

CO-HOST:
So the safe move is not strip. It is decide per part.

HOST:
Three kinds of state cross the boundary, and each has its own rule. Call-side metadata is a signature on generated content. It is model-scoped. Only the model that produced it may replay it.

CO-HOST:
Not the same provider. The same model.

HOST:
The same model. A provider can serve several models, and a signature from one is not valid for its sibling.

HOST:
Reasoning is the second kind. Readable reasoning can go back to the model that produced it. Send it to a different model and it must be dropped, or downgraded to ordinary text. Never presented as the new model's own reasoning.

CO-HOST:
Because the model would defend a thought it never had.

HOST:
It would contradict it, or refuse it, and you would spend an hour debugging a prompt that was never the problem.

CO-HOST:
And you would blame the model for your own replay.

HOST:
The third kind is a hosted tool. That is a tool the provider runs itself. Its result payload is provider-format data, not proof of authorship. So it stays replayable across models of the same provider. Its call-side metadata does not.

CO-HOST:
So results travel further than signatures. And your runner never dispatches a hosted tool, because it already ran.

HOST:
Exactly. Dispatching it gets you an error about a tool that already returned a result.

CO-HOST:
Which is a confusing error for a tool that worked.

HOST:
There is one more detail that shows how carefully this is drawn. An interrupted reasoning block, one with no completion time, is not replayed as reasoning even to the same model. It becomes text. The model must not inherit a thought that was cut off mid-sentence.

CO-HOST:
Let me push on the simple version. Why not strip all of it and take the loss?

HOST:
Because most calls go back to the same model that produced the last message. For those calls, the signature is what lets the provider reuse what it already computed.

CO-HOST:
So the metadata is not decoration. It is what makes the next call cheap and correct.

HOST:
Both. It is also namespaced, under the provider's own key, so two providers cannot overwrite each other in the same message.

CO-HOST:
That is a small detail with a large failure behind it.

HOST:
Two providers writing the same field, and one reading the other's value as its own. The transcript looks fine, and the request is nonsense.

CO-HOST:
So the namespace is part of correctness, not storage. And the rule is not same model, replay everything.

HOST:
The rule is per part, and the decision lives in one place. Lowering sees the source message's model and the target model side by side. It is the only place that has both facts, so it is the only place that can decide. Scatter that check through the loop and the copies will disagree.

CO-HOST:
So replay proof only to the model that produced it, and let results travel no further than their provider.

HOST:
That is the takeaway.

## 7. Body beat 4 — The door knows providers, not sessions

HOST:
Here is the claim. The model boundary should sit underneath the runtime, as the bottom layer of the agent.

CO-HOST:
It is the lowest thing in the system. It talks to the network. Why is it not the foundation?

HOST:
Because it is not a foundation. It is a peer. The runtime depends on the boundary, and the boundary depends only on the shared contracts.

CO-HOST:
That still sounds like a distinction without a difference. The arrows point one way either way.

HOST:
This is the part where the choice looks wrong, so here is the person who made it.

EXPERT:
The temptation is to make the boundary the bottom layer and let the runtime configure it. We did the opposite. The boundary depends only on the contracts, and it never imports the runtime.

CO-HOST:
What breaks if you do it the other way?

EXPERT:
The boundary starts knowing about sessions. A cache key here. A session header there. An image budget because the session is large. Each one is reasonable. Together they mean you cannot call a model without building a session, and you cannot test the translation on its own.

CO-HOST:
So you keep the session out of the one place that talks to the network.

EXPERT:
We keep it one layer up. The boundary takes a request and returns a stream. That is the whole contract, and it is why a provider can be tested with no database and no session anywhere in sight.

CO-HOST:
That also means you can test a provider route you have not finished writing.

HOST:
Thank you. That is the shape. The request gets enriched above the boundary, the provider quirks live inside the route, and the boundary stays a library.

HOST:
Now the route. A route has a body builder that turns canonical intent into the provider's body, a transport that knows how to send it, and a decoder that turns frames into canonical events. Everything provider-specific is inside the route.

CO-HOST:
So adding a provider is writing a route, not editing the loop.

HOST:
And switching providers mid-session is rotating the route and replaying the same request. The fallback does not rebuild your call. It re-sends it.

CO-HOST:
You keep saying one call. Is that a real constraint, or a slogan?

HOST:
It is the signature. The boundary takes a request and options, and returns a stream. It has no way to ask for a second call, and no place to keep the answer while it waits.

CO-HOST:
So it cannot loop even if it wanted to.

HOST:
It cannot loop, and it cannot remember. Those two limits are what make it safe to put a permission gate above it. The gate needs a pause between the ask and the effect, and a component that can loop would swallow the pause.

CO-HOST:
That is the same seam from last week, moved down one layer.

HOST:
It is the same seam, and it is why the boundary ends at the ask.

CO-HOST:
I want to push on the no-sessions part. Real calls need retries, and a retry needs to know what already happened.

HOST:
A retry of one call is still one call. It either re-sends the same request or it does not. What it must not do is run a tool. The boundary has no tools to run. It has tool definitions, which are text the model reads, and it has a stream that may contain a tool call, which is data it hands upward.

CO-HOST:
So the boundary can describe a tool without being able to execute one.

HOST:
That separation is the whole reason the runtime can put a permission gate between the model asking and the tool running. The boundary ends at the ask.

CO-HOST:
That is a better answer than I expected.

HOST:
The takeaway is this. The door knows providers, not sessions, and that is what keeps it testable.

## 8. The artifact

HOST:
The canonical request is the artifact for today. Here it is, field by field, in the order the request declares them.

HOST:
"An optional identifier. A model reference. An ordered list of system parts. An ordered list of messages. A list of tool entries. An optional tool choice. Generation options. Provider options. HTTP options. A cache policy. A prompt cache key. Metadata."

[production note: the source is a schema declaration. The companion carries it exactly, with identifiers and types.]

CO-HOST:
That is a short list for something doing so much work.

HOST:
Count what is missing. No provider name. No endpoint. No wire field. Every entry is something the caller means.

CO-HOST:
The system parts again. Why is that not a string?

HOST:
Because the boundary has to decide where each part goes. Some providers have a system role. Some want it as the first message. Some attach cache markers to a prefix. A string forces that decision early.

CO-HOST:
And the tool entries?

HOST:
A name, a description, and the two shapes. The request carries definitions, not implementations.

CO-HOST:
So a tool can be described in a request and still be refused later.

HOST:
It can. The cache policy and the cache key are the other surprise. They sound like session concerns, and they are. They are on the request because the request is what travels. The layer above fills them in.

CO-HOST:
So the request is the contract between the session and the door.

HOST:
It is the only thing they share. Everything above it can change, and everything below it can be replaced, as long as this list keeps its meaning.

CO-HOST:
And the messages inside the request. Are they the same shape as the history?

HOST:
No, and that distinction matters next week. A message here is a role and a list of content parts. The history is a log of typed entries with sequence numbers.

CO-HOST:
So the request is already a translation of the history.

HOST:
The request is the last canonical shape before the provider. It is near the wire, and still not the wire.

## 9. Recap

HOST:
Where we landed. One. The request is canonical intent, compiled into a provider body by a route, so the loop never branches on a provider name.

CO-HOST:
Two. The stream is a canonical event union, and it must end in a terminal event. End of stream is not an ending.

HOST:
Three. Some provider state is proof of authorship. Replay it only to the model that produced it, and keep hosted results inside their provider.

CO-HOST:
And four. The boundary sits beside the runtime. It knows providers, not sessions, so it can be tested on its own. And the loop never has to know which provider answered.

HOST:
Say the rule.

CO-HOST:
Normalize the provider at one door.
