## 4. Body beat 1 — Work is tied to a place

HOST:
A session is not a customer of the process. It is a customer of one directory.

CO-HOST:
That sounds like a filing convention. What breaks if I ignore it, and why can I not fix it later with a check?

HOST:
Two projects open in one editor. In the first, a config file says the test command is one thing. In the second, it says something else. Now a tool runs in the wrong one.

CO-HOST:
And it does not fail loudly. It runs the other project's tests, or reads the other project's files.

HOST:
Or gets permission-checked against the other project's rules. That is the failure that matters. The isolation has to be structural, so no tool has to remember it.

HOST:
So the services split in two. Some live once per process. The event bus, the database, the session store, the job registry, and the map from directories to their service graphs.

CO-HOST:
And the rest?

HOST:
The rest live once per directory. Config, agents, permissions, the tool registry, the filesystem, the model transport, snapshots, and the runner itself.

CO-HOST:
Why the runner? That is the loop. Why does the loop belong to a directory?

HOST:
Because a step reads and writes files. The runner is where the filesystem gets used, so the runner has to stand on the same directory the files do.

HOST:
A location is a directory plus an optional workspace identity. Resolving it gives you a project. An instance is one compiled copy of that per-directory graph, standing on one location.

CO-HOST:
Compiled once, or rebuilt per request? Rebuilding sounds expensive.

HOST:
Built lazily and kept. The map is keyed by a canonical form of the location, so two spellings of one path land on one entry. A healthy graph stays. Only an explicit invalidation or a failed boot evicts it.

CO-HOST:
And routing a session to it is one call.

HOST:
One call. Look up the session's location in the map, provide that graph, and everything the step needs comes from there. That single seam is the whole story of scope.

CO-HOST:
And if the graph is expensive to build, you paid for it on the first step.

HOST:
You did, and you pay once. Rebuilding per request would be unusable latency. The map keeps healthy graphs for the life of the process.

CO-HOST:
What happens to a step that is running when the graph is invalidated?

HOST:
Invalidation detaches the routing first, then closes the graph. A step that already borrowed it finishes on the graph it borrowed, and only the next step sees the new one.

CO-HOST:
Hold on. I want to push on the canonical path. Why is that not a detail?

HOST:
Because a raw path is not an identity. A relative path, an absolute path, and a symbolic link can name one directory three ways. Key the map by the raw string and you get three graphs, three watchers, and three permission sets that drift apart.

CO-HOST:
So it is the same bug as two projects, one directory over.

HOST:
It is the same bug with one project. There is one more piece, and it is not about isolation at all. Related sessions share a provider cache route.

CO-HOST:
Meaning what?

HOST:
A subagent gets its parent's route. A fork gets its source's route. Everything else gets its own. That key is the parent id, else the fork source, else the session's own id.

CO-HOST:
So a child conversation rides the parent's cache.

HOST:
It does, and that is a cost decision, not a safety one. Keep the two apart in your head. Location decides what a session may touch. Affinity decides what it pays for.

CO-HOST:
So the takeaway is not isolation. It is that scope is a property of the place, not of whatever code happens to be running.

HOST:
Scope by location. The graph follows the directory, and the session names only its directory.

## 5. Body beat 2 — One execution, and the doorbell

HOST:
Now the second problem. One session, one run at a time. And the way that is enforced is a doorbell.

CO-HOST:
I would have written a lock. Take a mutex, drain, release it.

HOST:
That is the obvious design, and it is wrong in a specific way. Picture a step streaming. The user hits enter with a follow-up.

CO-HOST:
So the follow-up is written down durably, and something has to notice it.

HOST:
Something has to drain it. But a fiber is already draining this session. If a second one starts, two model calls run against the same history and the writes interleave.

CO-HOST:
Fine, so the lock stops that. The running fiber already holds it.

HOST:
And then the running fiber finishes. It checks for work, finds none, and exits. The follow-up was written a microsecond after that check.

CO-HOST:
So the lock was held correctly the whole time, and the message still sat there.

HOST:
That is the gap. The last eligibility check and the transition to idle cannot be one atomic step. A lock only tells you who may run. It does not tell you that someone is waiting.

CO-HOST:
This is the part where the choice looks wrong, so let us hear from the person who made it.

EXPERT:
We do not lock the session. We give the running execution a doorbell.

CO-HOST:
A doorbell is a lock with a nicer name.

EXPERT:
A lock decides who may run. A doorbell records a request. When work is recorded during an execution, we set a field on that execution instead of starting a second fiber. After the drain returns, the loop reads the field, takes the scope, clears it, and drains again.

CO-HOST:
So the wake is never a second run.

EXPERT:
It is a fact the current run reads before it decides to stop. And if the loop has already decided to end, the surviving field starts a successor, so a wake is never lost.

HOST:
Thank you. And that field carries a scope, which matters in the next beat.

CO-HOST:
Let me make sure I have the shape. An execution is one busy period. It starts on a wake or on an explicit request to run. It coalesces many drains.

HOST:
And a follow-up prompt does not start a second execution. It rings the doorbell of the running one. A caller that asks to run either starts an execution or joins the active one, and waits for its exit.

CO-HOST:
What about two different sessions?

HOST:
Different keys. They never block each other. One execution per session is not one execution per process.

CO-HOST:
So forty open sessions are forty keys.

HOST:
Forty keys, and nothing serializes them against each other. The coordinator's job is one key at a time, not one key at all.

CO-HOST:
And the scope on the wake. Why does a wake carry one?

HOST:
Because the wake has to say how much work it is allowed to promote. If one wake needs new input and another only needs a steer, the runner takes the wider one. Widening is safe. Narrowing would hide work that was legitimately ready.

CO-HOST:
And the scope on the wake is not a priority.

HOST:
No. It says which kind of work is allowed through, not which work matters more.

CO-HOST:
So a field that holds a scope, and the widest scope wins.

HOST:
Yes. And there is one more party in the room. Every execution carries a signal that resolves when it ends, so anyone who joined it gets that execution's exit. It is resolved after the settlement hook runs, not before, so a waiter never reads a half-finished terminal.

CO-HOST:
And if a successor started?

HOST:
Then the waiter gets this execution's exit, and a caller that wanted the session idle waits again.

CO-HOST:
So two questions, and the interface keeps them apart.

HOST:
Two questions, and two different callers.

CO-HOST:
So the takeaway is not "serialize the session". Something sharper.

HOST:
One execution per session, and a wake is a field on it, not a second run.

## 6. Body beat 3 — Steering, queued work, and the order of promotion

HOST:
Now the input itself. Every item in the inbox has a delivery mode, and the mode decides when it is heard.

CO-HOST:
There are two, and I bet people swap them.

HOST:
Constantly. A steer influences work that is already in progress. A queued prompt starts new work, and it is heard only when the session would otherwise go idle.

CO-HOST:
Give me the case that makes it concrete.

HOST:
The model is three steps into a long refactor. The user types, actually, use the staging database. If that is queued, it waits until the refactor ends. By then the refactor is wrong.

CO-HOST:
So steering is the default for a normal prompt.

HOST:
It is. And a steer is promoted at the next safe step boundary, not mid call. You cannot change a request that is already on the wire.

CO-HOST:
So promotion takes the pending steers at a boundary. What is hard about that?

HOST:
Two things. A compaction is also a steer, and a move is also a control item. Both change what "the next boundary" means.

CO-HOST:
Start with compaction. I thought that was the previous episode.

HOST:
It is, and this is where it collides with steering. Suppose a compaction and a steer are both waiting, and the compaction arrived second.

CO-HOST:
So arrival order would compact after the steer.

HOST:
And the compaction summarizes the history the steer has joined. The user's correction gets folded into a lossy summary. The model never sees the words.

CO-HOST:
So the compaction has to go first.

HOST:
Among the waiting steers, a compaction is moved to the front. It summarizes the history before the later steers, and then those steers sit verbatim after the checkpoint.

CO-HOST:
But only locally. I remember that phrase.

HOST:
Only within the run of pending steers, and never across a move. A move changes the session's location. The context changes wholesale. Summarizing files from one directory into a checkpoint for another is not a summary, it is a mistake.

CO-HOST:
So the rule is a boundary, not a sort.

HOST:
A boundary. Promotion stops at a move and never pulls anything from the other side of it. The move itself is delivered like a control. The item is consumed, the event is published, and the drain hands off to the new location's instance.

CO-HOST:
Now the queued case. When does queued work get in?

HOST:
At an idle boundary, with no steers waiting, exactly one queued item is promoted. One. Not the whole backlog.

CO-HOST:
Why one?

HOST:
Because a queued prompt starts new work, and batching them changes the shape of the context the model sees. The user asked for one thing next, not four things at once.

CO-HOST:
And steers that arrived while that one was being promoted?

HOST:
They go in after it, up to the next control. So the order is steers first, then one queued item at idle, then any steers that arrived in the meantime.

CO-HOST:
Why not process input in the order it arrived? That is what users expect from a message list.

HOST:
It is what they expect from a message list, and it is wrong for a control channel. The queued task was admitted first only because the user typed it first. It was not meant to interrupt the run. Processing in arrival order lets unrelated work hijack a step that is already going.

CO-HOST:
So the delivery mode carries the intent, and the ordering rules protect it.

HOST:
One more piece. If the first pending steer is a control, promotion returns nothing at all, and the runner has to handle the control first. That is how a control owns a boundary.

CO-HOST:
So "nothing promoted" is a signal, not an empty result.

HOST:
A signal. Empty means nothing to promote. Nothing means the runner has an obligation first.

CO-HOST:
Steer changes the work in progress. Queued work starts the next thing. And compaction goes ahead of the steers it would eat.

## 7. Body beat 4 — A second session, and a narrow stop

HOST:
So one session is serial. Now open four of them and press stop on one.

CO-HOST:
And this is where a naive design kills three unrelated tasks, or freezes the screen waiting for one of them to die.

HOST:
Or freezes the interface. Interruption has three requirements that pull in different directions. It has to be narrow. It has to return fast. And it has to be safe against a wake that arrives during the cleanup.

CO-HOST:
Narrow first. What does a stop actually target?

HOST:
The active execution for that session, and nothing else. The coordinator is keyed by session id, so two sessions are two keys and run concurrently. One session is one key and is serial. Concurrency falls out of the keying, and so does isolation from a stop.

CO-HOST:
And the coordinator is global while the work is not.

HOST:
Global keying, scoped work. The instance is found when a drain starts.

CO-HOST:
And if the session is idle?

HOST:
Nothing to stop. It is a no-op, and it does not touch another session or another key.

CO-HOST:
Now the fast part, which I suspect means "we did not really finish".

HOST:
It means the interrupt returns when the interruption is accepted, not when the cleanup is done. The answer is whether an execution was active. The fiber runs its finalizers and its settlement hook on its own time.

CO-HOST:
So the interface is honest about what it is telling you.

HOST:
It has to be. The endpoint has to acknowledge even when the finalizers are slow. Waiting would freeze the screen on somebody else's cleanup.

CO-HOST:
And the third requirement. The wake during cleanup.

HOST:
The interrupt clears the pending wake. Those recorded wakes belonged to the intent that was stopped, so settlement must not start a successor for abandoned work.

CO-HOST:
And a wake that arrives after the interrupt?

HOST:
That is a new admission, and it restarts normally at settlement. The distinction is not the clock. It is whether the wake was recorded before or after the interrupt claimed them.

CO-HOST:
So there are two ways to wait. Tell me the difference.

HOST:
One waits for the interrupted execution to settle. The other waits until the session is quiet, and that one follows successors. If you want "this work stopped", use the first. If you want "the session is idle", use the second.

CO-HOST:
Now the resume question. I stop a run, and I had already typed a correction.

HOST:
If resumption is requested, the session reads its inbox. If the next promotable item is a steer, a compaction, or a move, it wakes the session with steer scope, so the remaining steering work runs as a successor.

CO-HOST:
And a queued prompt?

HOST:
Stays parked. A steer-scoped drain never promotes queued work. The user asked to stop, not to start the next task.

CO-HOST:
Let me push on the terminal instead. What does a stop leave behind?

HOST:
One of three things. Success, interrupt with a reason, or failure. And the reason decides what happens to the claim that marks work in flight.

CO-HOST:
Which claim?

HOST:
The claim a run writes before it does anything.

CO-HOST:
And a user stop or an inactivity stop releases it, and cancels the job keyed by the session.

HOST:
While a shutdown interrupt keeps it, so the next boot resumes the work. That is the distinction the recovery path depends on, and we get to it in a later episode.

CO-HOST:
And child sessions?

HOST:
Separate keys. Stopping a parent does not by itself stop a foreground child. The subagent tool wraps its wait so that interrupting the parent interrupts the child and cancels its job. A child is its own session, and the job that started it owns its lifecycle.

CO-HOST:
So the shape of the whole thing. One key per session, one execution per key, a wake that is a field, and a stop that is narrow, fast, and honest.

HOST:
And that is why the doorbell beats the lock. A lock has no memory of who knocked.

## 8. The artifact

HOST:
The coordinator's own source comment is the best statement of this design. Here it is, word for word.

HOST:
"One execution is a busy period for one key. One fiber that drains from the first wake until the key would stay idle. The pending wake field is the doorbell. Work recorded during the execution rings it with the scope that work needs, and the execution loop drains again instead of ending. The doorbell closes the gap between a drain's last eligibility check and the idle transition, since those cannot be one atomic step. The done signal resolves joiners with this execution's exit."

[production note: the source names two code fields where these words say "the pending wake field" and "the done signal". The companion carries the comment exactly.]

CO-HOST:
It is a comment that admits the race.

HOST:
It does, and that is the most useful sentence in it. "Those cannot be one atomic step." Once you say that out loud, the doorbell stops being a trick. It is the only honest answer left.

CO-HOST:
Walk me through the first sentence. Why "busy period"?

HOST:
Because an execution is not a request and it is not a step. It is the stretch from the first wake until the key would stay idle. Many steps live inside it. Many drains live inside it. One fiber owns all of them.

CO-HOST:
And "the key would stay idle" is doing work there.

HOST:
It is conditional. Not until the key is idle, but until it would stay idle. That word is the doorbell.

CO-HOST:
Then the last clause. Joiners get this execution's exit.

HOST:
So a caller that asked to run does not get an answer about the backlog. It gets the outcome of the execution it joined, and a successor belongs to somebody else.

CO-HOST:
That is a subtle thing to put in a comment.

HOST:
The comment is where you put the thing that will look like a bug in six months. Somebody will read that loop, see it drain twice, and try to simplify it. This paragraph is the reason they cannot.

## 9. Recap

HOST:
Where we landed. One. Work is scoped to a location, and the session names only its directory. The graph follows the directory.

CO-HOST:
Two. One execution per session. A wake is a field on the running execution, not a second fiber, and not a second lock.

HOST:
Three. Steering is heard at the next safe step boundary, queued work waits for idle, and a stop settles later on its own time.

CO-HOST:
Say the rule this episode is named for.

HOST:
One execution per session. It sits beside the older ones. Record the fact before anyone acts. Admission is not execution. And decide retry, continue, or recover from the taxonomy.
