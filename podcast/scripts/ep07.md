## 4. Body beat 1 — The reply is the room the prompt leaves

HOST:
The output limit is a number you choose for the model.

CO-HOST:
I do choose it. It is a field in the request. I set it to the model's maximum and move on.

HOST:
That works until the prompt is large. Then the field is a wish, and the provider decides whether to grant it.

CO-HOST:
What does the provider do instead?

HOST:
One of two things. It rejects the request, because the input plus the requested output is larger than the window. Or it accepts, and the model runs out of room mid-answer, sometimes in the middle of a tool call.

CO-HOST:
So the number in the field is not the number I get. That is the first time I have heard it put that way. It also means the same code asks for a different amount on every step, and the field is a lie we tell ourselves.

HOST:
Two numbers come from the model catalog. The size of the window, and the model's own cap on output. Two numbers describe the prompt. One is measured, and one is estimated.

CO-HOST:
Measured by whom?

HOST:
By the provider, at the end of the last response. Input, cache reads, cache writes, output, and reasoning. That is the part we do not have to guess.

CO-HOST:
And the estimated part?

HOST:
Everything since that response. New messages, tool results, system updates, counted at about four characters per token and then padded with a margin, because dense text such as code runs heavier than that.

CO-HOST:
Four characters per token. That is a rough rule to hang a request on.

HOST:
It is a rough rule, and it undercounts exactly the thing this product produces. The margin is the correction. It is not precision. It is honesty about the error.

CO-HOST:
Then the arithmetic. Show me where the reserve comes from.

HOST:
Take the window, subtract the measured part and the padded estimate. What remains is the room for the reply. The limit is the smaller of the model's own cap and that room, and never below a floor.

CO-HOST:
So you decide how much room the answer gets by measuring how much the question took.

HOST:
That is the whole design, and it inverts the intuition. The output limit is not a preference. It is the leftover.

CO-HOST:
What happens when the model hits it anyway?

HOST:
The step finishes with a specific reason, and the runner does not pretend it completed. It adds a message for the next step, and here is what it says. Your last response hit the output limit. Do not apologize, recap, or repeat yourself. Break the remaining work into smaller pieces.

CO-HOST:
Three instructions in one message.

HOST:
Each one prevents a specific waste. The first tells the model why it was cut, so it does not think the user interrupted. The second stops it restating the part it already wrote, which spends the budget that ran out. The third gives it an action, so the next attempt is smaller instead of identical.

CO-HOST:
What about the floor you mentioned?

HOST:
The floor matters more than it looks. Automatic compaction keeps the window from filling this far, so the floor is only reachable when compaction is off. Without it, a nearly full window would ask for zero tokens and fail before the provider saw the request.

CO-HOST:
And a hard ceiling? Because a catalog is a claim, not a measurement.

HOST:
The ceiling is there because catalogs overstate. A model that claims a huge output limit should not be asked for all of it in one request.

CO-HOST:
What about thinking? That spends the same budget.

HOST:
It does, so an explicit thinking budget is capped at half the output limit. A thinking budget near the limit leaves the answer, or the tool call, with nothing.

CO-HOST:
So the model can think itself into silence.

HOST:
It can, and that failure looks like a model that stopped talking for no reason.

## 5. Body beat 2 — Measured and estimated are a trust boundary

HOST:
You can count the prompt yourself, exactly, with a tokenizer.

CO-HOST:
That is what I would do. A tokenizer is deterministic. Why estimate at all?

HOST:
Because your tokenizer counts the text you wrote. The provider counts the request it received, including its cache reads and writes and its reasoning, and that is the only count that describes its window.

CO-HOST:
So you take the last report and trust it.

HOST:
You take the last report, and only if it came from the same provider. A count from a different provider describes a window this model cannot replay, so it is ignored.

CO-HOST:
That is a strange failure. You switch models and the budget goes wrong.

HOST:
It does. The window is different, the tokenizer is different, and the old number is confidently wrong. So the anchor is the most recent response from the current provider, and everything after it is estimated.

CO-HOST:
Why keep the two apart? Add them and you have one number, and one number is easier to pass around. That is the version I would have written.

HOST:
Because they have different trust. A single number hides which part came from the provider and how much margin was added on top. Keeping them apart also lets compaction do something clever, which we will get to.

CO-HOST:
Go on. I want to see where the two numbers stop being interchangeable.

HOST:
The estimate is characters per token, and the margin is added when the room is computed, not when the estimate is made. That separation is what lets a summary count its input as measured.

CO-HOST:
Why would a summary get to skip the margin? That sounds like the one place you would want to be careful.

HOST:
Because compaction aims at about ninety percent of the window. Add a fifteen percent margin on top and every summary gets clamped to the floor. It would come back as three lines, every time, on a full session.

CO-HOST:
So the margin is a correction you apply in one place and not another. That sounds like the kind of thing that quietly breaks.

HOST:
It is exactly the kind of thing that quietly breaks, which is why the two numbers stay separate all the way to the arithmetic. The margin is a correction for an estimate, and it is not applied where the number is not an estimate. Know which number you are holding.

CO-HOST:
What happens when the estimate is wrong anyway?

HOST:
Then the request overflows, and compaction is the backstop. The margin lowers the chance. It does not remove the failure.

CO-HOST:
And the first request of a session? There is no report yet.

HOST:
Then measured is zero and everything is estimated. Without that path, the first request would ask for the model's full output cap and overflow a short window immediately.

CO-HOST:
Give me the failure this prevents.

HOST:
A long session switches models halfway. The new model has a smaller window. If the budget trusts the old report, the request asks for more room than exists, and the provider rejects it. The symptom looks like a provider problem. It is a bookkeeping problem.

CO-HOST:
And the fix is to ignore the old anchor, even though it is the only real measurement you have.

HOST:
Ignore it, fall back to an estimate, and let the floor keep the request alive.

CO-HOST:
Does the estimate ever run low?

HOST:
It runs low on dense text, which is most of what a coding agent reads. The margin is the cheap correction, and the overflow path is the expensive one.

CO-HOST:
So the estimate is not there to be right. It is there to be conservative, and the provider's report is the only thing that gets to be exact.

HOST:
It is there to be honest about what it does not know.

## 6. Body beat 3 — Every result has a size

HOST:
A tool result is whatever the tool returns.

CO-HOST:
It is data. I cannot know how big a command's output will be before I run it.

HOST:
You cannot know the size. You can decide the shape and the limit before it arrives. A result is normalized into content, and content has two kinds. Text and file.

CO-HOST:
What if the tool returns a string?

HOST:
One text part. A list of parts passes through. If it returns only a structured output, that becomes text, because the model needs something to read.

CO-HOST:
And an image?

HOST:
A file part that is an image is decoded, checked against the configured limits, and resized. If it cannot be decoded or resized, it is dropped and replaced by a note that says how many were omitted and why.

CO-HOST:
Why the reason? A note that says the image is gone would be enough.

HOST:
Because the reason tells the model whether a retry helps. Could not be decoded means the file is broken. Could not be resized means a smaller image might work.

CO-HOST:
And the note is visible to the model.

HOST:
It has to be. A vanished image invites the model to describe it from memory.

CO-HOST:
Now the text. That is where my two megabytes live.

HOST:
Text is measured. If it fits under the line and byte limits, it passes through unchanged and is marked as not truncated. If it does not fit, the whole text is written to a file under a managed directory. The model gets a head, plus a marker.

CO-HOST:
What does the marker say?

HOST:
It says which lines you have, how many there were, and where the rest is saved. It appears once, after the retained text, even when the content came in several parts.

CO-HOST:
And the metadata? Something has to remember the file, or the marker is a dead end.

HOST:
It records that the result was truncated, and where the file is.

CO-HOST:
Here is my objection. The result was correct. Why not deliver it and let the model deal with the size?

HOST:
Because more is not the same as better.

CO-HOST:
So a model handed more than it can use does not read more carefully. It reasons confidently over a partial view and never notices the gap.

HOST:
That is the part where the choice looks wrong, so here is the person who made it.

EXPERT:
We bound the result on purpose. A complete result is only better if the model can use it, and past a point more text makes the answer worse, not better.

CO-HOST:
That is a hard claim. More information should not hurt.

EXPERT:
It hurts when the budget is fixed. A result that fills the window pushes the model's own earlier work out of view, and the model loses the middle of it. A head plus a marker keeps the option to fetch the rest, and it tells the model that the rest exists.

CO-HOST:
So the marker is what makes the cut honest.

EXPERT:
The marker is what makes it recoverable. The model can open the file. What it cannot do is pretend it saw the whole thing.

HOST:
Which is the difference between a short answer and a wrong one.

CO-HOST:
You said there were two layers of bounding.

HOST:
There are, because one limit cannot serve every producer. A shell command can print far more than a shared limit should hold in memory, so the shell tool bounds its own output first. It keeps the tail, because the interesting part of a build is at the end. Read keeps the head, because the model asked for a region.

CO-HOST:
So the generic bound is the backstop, not the only bound.

HOST:
It is. And it runs inside settlement, so the bytes the model sees and the bytes written to the record are the same. A truncated result cannot be lost to an interrupt after the model has read it.

## 7. Body beat 4 — Fit the reply to the request you send

HOST:
You compute the output limit once, when you prepare the request.

CO-HOST:
Once is enough. The request is the request. I build it, I send it, nothing changes in between.

HOST:
It is not the same request by the time it is sent. Preparing sizes the output for a planned input. Then the conversation turns out to be too large to shrink any further, and the request that goes out is bigger than the one that was planned.

CO-HOST:
So the limit was fitted to a request you did not send. Which means the number you carefully computed was about a different request entirely.

HOST:
So it is fitted again, right before the send. Lower the output limit to the room the actual request leaves, so input plus requested output cannot exceed the window by your own arithmetic. Two fits, one number, and the second one wins.

CO-HOST:
Why not skip the first fit? If the second one is always tighter, the first looks like decoration.

HOST:
Because the first fit is what prepares the request. The second exists because the request can grow after preparation, and a limit computed from a smaller input is a promise you cannot keep.

CO-HOST:
And compaction is where this matters most, because the summary is the thing that is supposed to save the session.

HOST:
Compaction is a request like any other, with one difference. It deliberately counts its input as measured, with no estimate margin, because the margin would clamp every summary to the floor. It also caps summaries separately from ordinary replies. A model that allows a huge reply should not be asked for a huge summary.

CO-HOST:
Why cap it at all? The model will stop when it is done, and a cap is a number you have to defend.

HOST:
A summary never needs the full cap, and a request that asks for more cannot be shrunk to fit a window the catalog overstates. The cap is a safety valve, not an optimisation.

CO-HOST:
Now the cost I keep hearing about. Cache.

HOST:
Providers cache a prefix of the request, usually the system prompt and the early messages, and a cache read is cheaper than fresh input. Compaction rewrites the early history. So the next request's prefix is different, and the cache misses from the point of the change onward.

CO-HOST:
Every time you compact, you pay full price again. So compaction is supposed to make the session cheaper, and it starts by making one request expensive.

HOST:
Once. Then the new prefix is stable and caching resumes, until the next threshold. The design cannot avoid the miss, because the context really did change. It can bound the damage.

CO-HOST:
How?

HOST:
Three ways. The checkpoint goes in as a single message at the front, so everything after the newest exchange is unchanged and stays cached. The system prompt is assembled in a stable order, and compaction does not reorder it. And a cache key travels with every request, derived from the session, so lookups stay per session.

CO-HOST:
So the goal is one miss, not zero.

HOST:
One miss, then stop rewriting until the next threshold. Compaction that runs every step invalidates the prefix every step, and that is worse than the context it saved.

CO-HOST:
And the concrete failure behind the second fit? I want the version that ships a useless summary.

HOST:
You compact to save room, and the summary comes back as three lines. Not because the model had nothing to say, but because the prompt nearly filled the window and the provider granted a sliver of output. The request was legal. The allowance was not.

CO-HOST:
So the summary was starved, not stupid.

HOST:
Starved by arithmetic. The floor keeps that from being zero, and the second fit keeps the request from being rejected.

## 8. The artifact

HOST:
Two markers do the work in this episode. Here is the one with the strongest wording, word for word.

HOST:
"This image was removed to reduce the request size and is no longer visible. Do not make claims about its contents from memory. If needed, retrieve it again with an available tool or ask the user to attach it again."

CO-HOST:
That is a warning, not an error. It is addressed to the reader, not to the system.

HOST:
It is a warning with a job. The image is gone because the request grew past a size limit.

CO-HOST:
And the middle sentence is the one that would never occur to me.

HOST:
That sentence is the whole point. A dropped image that nobody mentions is an invitation to invent. A model that saw a picture earlier in the session will happily describe it later, from a memory of a picture it can no longer see.

CO-HOST:
And the third sentence gives it a route back.

HOST:
Retrieve it, or ask for it again. A warning without an action leaves the model stuck.

CO-HOST:
What about the other marker, the one on a truncated result?

HOST:
I am describing that one, because it carries a count and a file path. It says showing, then the range of lines you have, then how many there were, then where the full output was saved. Four pieces, and the fourth makes it recoverable. The exact template is in the companion.

CO-HOST:
So both markers do the same job in different words.

HOST:
Both turn a silent loss into a stated one. The image says what was removed. The truncation marker says what is missing and where it lives. The rule underneath is the same. Never let the model believe it has the whole thing when it does not.

## 9. Recap

HOST:
Where we landed. One. The output limit is the room the prompt leaves, measured where the provider measured it and estimated everywhere since, with a margin.

CO-HOST:
Two. Every result has a shape and a size. Text and images are bounded, and what is dropped is named.

HOST:
Three. The reply is fitted twice, once to the planned request and once to the one actually sent, and compaction pays for rewriting the front of the prefix.

CO-HOST:
Say the rule, and the ones we are carrying.

HOST:
Bound every output. Validate at the boundary. One model call per step. Continuation is read from the record.
