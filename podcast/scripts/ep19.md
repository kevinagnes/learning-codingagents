## 4. Body beat 1 — Write it down before you do it

HOST:
The honest way to know a run was interrupted is to ask the run, at the end, whether it finished.

CO-HOST:
That only works if the run gets an end. The process was killed while a model call was streaming. There is no end.

HOST:
Then the answer has to exist before the work does. So the project writes a claim when a turn starts. It is a durable marker that a turn is in flight, and it is written in the same transaction as the started event.

CO-HOST:
In the same transaction. So the record of starting and the record of being busy are one write.

HOST:
One write. There is no window where the event exists and the claim does not.

HOST:
When the turn ends, a terminal event releases it, in that same transaction. Succeeded, failed, interrupted. On a graceful end, the claim is gone. On a crash, no terminal runs, so the claim stays set.

CO-HOST:
Why write it at the start? Write completed at the end, and treat its absence as a crash.

HOST:
Because absence is ambiguous. A completion flag written at the end cannot tell the difference between a turn that crashed halfway and a turn that never started. The session that never ran looks exactly like the session that died.

CO-HOST:
So the claim is positive evidence.

HOST:
Presence is the evidence. That is the whole trick. The claim is written before the work, so its existence is a fact the database holds, not a fact you infer from something missing.

CO-HOST:
What is the marker, concretely? A flag, a timestamp, a row?

HOST:
It is a field on the session that is either set or clear. Claimed or idle. And the session carries a count of resume attempts beside it, which we come back to.

CO-HOST:
And claiming a session that is already claimed?

HOST:
It is a no-op. A resumed turn claims through the same started hook, and the guard makes the second claim change nothing.

HOST:
One more detail that matters to a user. Claim bookkeeping never counts as user activity. The update time is pinned, so a client's list of sessions only moves on real changes.

HOST:
The mechanism is deliberately small. One field, set or clear, and a guard that makes a repeated set harmless.

CO-HOST:
So a resume does not jump the session to the top of my list, as if some phantom message had arrived.

HOST:
It does not. The marker is housekeeping, not activity.

CO-HOST:
Write-ahead. The same move as recording the fact before anyone acts.

HOST:
The same move at a different scale. There, the fact was that work exists. Here, the fact is that work is in flight. Both are written before anyone depends on them.

CO-HOST:
Let me say the state machine back to you. Idle, claimed, and claimed with nobody left to release it.

HOST:
Idle, claimed, and orphaned. Three states, and only the last one needs attention at boot.

CO-HOST:
And the claim is not a note to the client. It is a note to the next boot.

HOST:
To the next boot, specifically. The client learns from events. The next process learns from the claim.

CO-HOST:
Does a normal restart leave it too?

HOST:
A clean shutdown keeps it, which is the next beat. A crash leaves it. Either way, the next boot sees the same thing.

CO-HOST:
And the started event is the same event a client sees, so the marker and the live feed agree on when the turn began.

HOST:
They agree because they are one fact. The claim rides along with the started event.

CO-HOST:
So what ends the in-flight fact?

HOST:
A terminal. And which terminal ends it is more interesting than you would expect.

## 5. Body beat 2 — A clean stop and a hard stop

HOST:
When the server shuts down cleanly, it should clean up after itself and release the claim.

CO-HOST:
That sounds obvious. A clean shutdown is not a crash. If the server got to say goodbye, it should leave things tidy.

HOST:
That is the reasonable instinct, and the project does the opposite. A graceful shutdown keeps the claim on purpose.

CO-HOST:
Why would it do that?

HOST:
Because the turn was interrupted by the server going down, not by the user. The resumed execution is a continuation of the same turn. So the claim survives, and the next start resumes it as the same work.

HOST:
The terminal hook draws the line. A success releases the claim. A failure releases the claim. An interruption releases it only when the reason is not shutdown.

CO-HOST:
So every terminal releases it except the one that fires because the machine is going down.

HOST:
Except shutdown. A deliberate stop, from the user or from inactivity, releases it. Those are choices about the work. A shutdown is not.

CO-HOST:
And what about a turn that fails? Why does a failure resume nothing?

HOST:
Because a failure is terminal. The error is recorded, the turn is over, and resuming it would repeat a known failure. So a failure releases the claim.

CO-HOST:
So success, failure, and a deliberate stop all clear it. Only shutdown keeps it.

HOST:
Only shutdown, and only because shutdown is the one case where the intent was to continue.

CO-HOST:
So the whole difference is one reason value on one event.

HOST:
One reason value, and it decides whether the next boot resumes the work or forgets it.

HOST:
So the two cases converge. A clean shutdown and a hard crash leave the same claim, and one recovery path handles both.

CO-HOST:
Do they really converge? A shutdown is orderly. A crash is chaos.

HOST:
At the point that matters, they are identical. Both leave a claim with no terminal, and the next boot cannot tell them apart. That is the design. Make the survivable case look like the crashed one, so you write the recovery once.

CO-HOST:
What does a client see in the two cases?

HOST:
An interrupted event either way. The reason on that event is different. Shutdown keeps the claim, so the next boot resumes. A user stop releases it, so nothing resumes.

CO-HOST:
So the event and the claim are two records of the same decision.

HOST:
And the claim is the one the next process reads. The event is for the client.

CO-HOST:
But that means every restart resumes work the user may have walked away from. That is a surprise, not a feature.

HOST:
If the user wanted it stopped, they pressed stop, and that releases the claim. A shutdown is the server saying I am going down. It is not the work saying I am done.

HOST:
And the cost of the other choice is worse. If shutdown released the claim, the turn would look complete, and the user's in-flight request would be dropped in silence. Nobody would know it died. It would be gone.

CO-HOST:
So the marker prefers a resurrected turn to a lost one.

HOST:
It does. And a resumed turn does not write a fresh idle marker, because it is the same turn continuing. The history does not grow a second beginning.

CO-HOST:
Which is the same instinct as the inbox. The work exists once. You resume it, you do not re-admit it.

HOST:
Exactly. And that instinct is what the next boot leans on when the process did not get to say goodbye.

CO-HOST:
Which is the case we keep dancing around.

HOST:
Next. The case where nobody said goodbye.

## 6. Body beat 3 — The claim is not a lock

HOST:
Recovery needs the dying process to cooperate. A shutdown hook, a finalizer, a last wish.

CO-HOST:
It is dead. It cannot tell you anything. And a shutdown hook does not run on a hard kill.

HOST:
Then recovery cannot ask the process. It has to ask the database. And a claim that survived with no terminal is the crash record. You never need the dying process to cooperate.

CO-HOST:
So the crash writes its own evidence, whether it meant to or not.

HOST:
It does. The absence of a terminal is the signature. And it is the same signature for a crash, a hard kill, and an eviction.

HOST:
At the next boot, the sweep looks for claims that are still set and are not already active in this process, and it resumes them.

CO-HOST:
And it ignores sessions that are already running here.

HOST:
It filters those out. A child session owned by a background job is handled through its own durable job record, not by this sweep.

HOST:
And the sweep never clears the claim itself. Only a terminal clears a claim. So if the process dies again during the resume, the same orphaned claim is waiting for the next boot.

CO-HOST:
So resurrection can also die.

HOST:
Which is why there is a budget. Every resume durably increases a per-turn counter, and it is written before the resume runs, so a crash inside the resumed turn is still counted. The budget cannot be dodged.

CO-HOST:
Written before, not after. Otherwise a crashed resume escapes the count.

HOST:
A crashed resume is the exact case the counter exists for. Past the limit, the turn is failed with a durable terminal, and the release clears the claim and resets the counter.

CO-HOST:
Per turn, not per session.

HOST:
Per turn. A session that had a hundred healthy turns is not punished for one bad one.

CO-HOST:
How many times will it try?

HOST:
A small fixed budget. The exact number is in the companion. What matters here is that it is bounded, and that the count is durable before each try.

HOST:
There is one assumption under all of this, and it is worth saying plainly. The sweep assumes every orphaned claim's owner is dead.

CO-HOST:
And that is safe how?

HOST:
It is safe under a managed server, which starts a successor only after confirming the previous process died. A registration lock admits one managed server at a time, and an unregistered process sharing the database never sweeps.

HOST:
The sweep is also inert until it is called. A managed server calls it at boot. An embedder calls it from its own start-up.

HOST:
And the contract puts at-least-once in the comment itself, beside the sweep, not in a footnote somewhere.

CO-HOST:
So the claim is doing ownership work here. It sounds like a lock.

HOST:
It is not, and this is the part I want to hand to the person who wrote it. It looks exactly like a lock, and it is not one.

EXPERT:
We keep it as a recovery marker. It is not clustered ownership, not fencing, and not an exactly-once promise. It answers one question at the next boot. Was this turn in flight and never finished?

CO-HOST:
But while it is set, does it stop a second worker?

EXPERT:
No. Local coordination stops concurrent drains inside one process. It does not stop repeated side effects after a crash. Recovery is at-least-once, and the contract says so. If two processes swept one database, they would both resume the same claim and run the turn twice. If you need real ownership, you need real ownership, not this marker.

CO-HOST:
So the marker tells you the turn is unfinished. It does not tell anyone to stand down.

EXPERT:
That is the distinction. And it is why we say at-least-once. A side effect that ran before the crash may run again. The record is honest about that.

HOST:
Thank you. That is the honest version of recovery. It does not promise more than a database can promise.

CO-HOST:
Which leaves the half-written step underneath the claim.

## 7. Body beat 4 — Settling the half-written step

HOST:
The claim is the only thing a crash leaves behind.

CO-HOST:
The model call was mid-stream, and a compaction was summarizing. There is more half-finished than one marker.

HOST:
There is. A step is only settled when its terminal events are written, and a crash between the start and the terminal leaves half-written rows.

CO-HOST:
Which shapes can be left hanging?

HOST:
Two. A compaction message, and any tool call on any assistant message. Those are the two the sweep knows how to close.

HOST:
Settlement has three parts. Stale compactions: a compaction still marked running is failed with an interrupted error, so a checkpoint is never half applied. Stale tool calls: a tool call still streaming or running is failed with an aborted error. And if the call was a subagent, the child session identifier travels into the failure, so the crash is visible against the child.

CO-HOST:
Why visible against the child?

HOST:
Because the child has its own history, and someone reading it needs to know why it stopped. The failure carries the child's identifier so the two records line up.

CO-HOST:
And the third part?

HOST:
Resume. The sweep finds sessions whose claim was never released, admits a continue notice, and wakes them, under the same budget.

HOST:
Here is the part that makes it cheap. Settlement is not a separate recovery service. It is the first thing a fresh drain does, before it considers new input. Any drain settles whatever the last process left running.

CO-HOST:
So a normal reload pays the same small tax as a crash recovery.

HOST:
It does, and it is the same code path. That is what makes recovery a property of the database instead of a special mode.

CO-HOST:
Why not delete the half-written rows and start clean?

HOST:
Because you would erase the record of what happened. You fail the call with a terminal, so the history stays truthful. The conversation is not corrupt. It is ended.

CO-HOST:
And order matters.

HOST:
Order is the whole thing. Settle before you read new input, or the model sees a tool call with no result and either stalls or invents one.

HOST:
And because settlement reads projected state, it sees exactly what a reader sees, not a private memory of what was in flight.

HOST:
The project names the alternatives it rejected. A recovery hook that runs on shutdown, which never runs on a hard kill. A cleanup sweep owned by the dying process, which is dead. Trusting the model to notice the gap, which confuses it. And resuming every orphaned turn forever, which turns one bad turn into a crash loop.

CO-HOST:
So the claim is the coarse marker, and settlement is the fine one.

HOST:
Coarse and fine. The claim says a turn was in flight. Settlement closes the individual tool calls and compactions the turn left open.

CO-HOST:
And the notice to the model. What does it say?

HOST:
It tells the resumed turn that the server restarted while it was working, and to continue without repeating completed work. The model sees its own full history, so without that sentence it tends to redo the last call or rewrite the last paragraph.

CO-HOST:
Three ways to be interrupted, then. A dropped stream, an output limit, and a restart.

HOST:
You have been listening. All three notices say the same thing. Resume, and do not redo.

CO-HOST:
And after settlement, does the model know why the tool failed?

HOST:
The failure carries an aborted error and the tool's name, so the record explains the gap. The model does not have to guess what happened to a call it never watched finish.

CO-HOST:
So the history reads as a call that was interrupted, not a call that vanished.

HOST:
Which is the difference between a truthful record and a clean one.

CO-HOST:
And that sentence is the difference between a cheap recovery and a duplicated side effect.

HOST:
Which is the risk recovery accepts everywhere. It minimizes it, and it does not deny it.

## 8. The artifact

HOST:
The project writes the claim's story as a comment at the point the claim is created. Here it is, word for word.

HOST:
"Write-ahead claim. Starting records the durable intent that a turn is in flight, in the same transaction as the started event. Terminals release it, except shutdown interruption, which preserves the claim so the next server start resumes the turn. A claim that survives with no terminal is the signature of a process that died without teardown. Recovery is a property of the database, never of a shutdown hook that may not run."

[production note: the source follows "died without teardown" with a parenthetical naming a kill signal and an eviction. The companion carries the source lines exactly.]

CO-HOST:
"Never of a shutdown hook that may not run." That clause decides the design.

HOST:
It is the whole argument. Everything else in the comment is mechanism. That clause is the reason.

CO-HOST:
Why write this as a comment in the code, and not in a design document somewhere?

HOST:
Because the person about to edit this function is the person who needs to know why the shutdown branch skips the release. A comment travels with the trap.

HOST:
Read the first sentence again. In the same transaction as the started event. There is no window where the event exists and the claim does not. The two are one write.

CO-HOST:
And "resumes the turn" is doing work too. It resumes, it does not restart.

HOST:
Which is exactly why the notice says continue without repeating completed work. The claim says this is the same turn, and the notice tells the model to treat the history as its own.

CO-HOST:
So one comment names the marker, the release rule, the crash signature, and the guarantee.

HOST:
Four things, in five sentences. That is what a good invariant comment looks like. It says what is true, and it says why the obvious alternative was rejected.

CO-HOST:
And the phrase died without teardown covers a crash, a hard kill, and an eviction, all in one phrase.

HOST:
It covers every death where nobody ran the ending. That is the only thing the next boot needs to know.
