## 4. Body beat 1 — Four phases, not one function

HOST:
Here is the claim. The agent loop is one function with a while statement in it.

CO-HOST:
That is how I would write it. Call the model, run the tools it asked for, append the results, go around.

HOST:
And in a demo it works. Then you add a retry, and the whole thing starts lying to you.

CO-HOST:
Lying how?

HOST:
A retry re-runs the same step. A continuation starts a new one. If one function does both, it cannot tell which it is doing. So it cannot tell whether new input may be promoted, or whether promoting it would deliver the same sentence twice.

CO-HOST:
I would have written the retry inside the same loop. Three more lines.

HOST:
And those three lines are where the record stops matching reality.

CO-HOST:
Give me a second failure.

HOST:
Cached context. Build the request once and reuse it across steps, and the model never sees a correction that arrived mid-turn. It also never sees the assistant message it produced one step earlier.

CO-HOST:
So it forgets while it is working.

HOST:
It forgets the correction and its own work at the same time. The loop looks busy and is blind.

CO-HOST:
So the naive loop holds a photograph of the conversation while the conversation keeps moving.

HOST:
That is a fair way to say it. The request was built once, and the world moved under it.

CO-HOST:
And a third?

HOST:
Cancellation landing between a check and its effect. Delivering an item and publishing its event are two effects. Interrupt the process between them and the check says one thing while the record says another. A row is consumed and no message appears, or a message appears twice.

CO-HOST:
A race between a check and its effect. That is the kind of bug you cannot reproduce on purpose.

HOST:
So the loop is four named phases, and each one owns exactly one decision.

CO-HOST:
Name them.

HOST:
The drain. It asks whether there is eligible work, then loops over steps. Preparing the next step. That one serializes the inbox, handles a pending control, promotes what this boundary may consume, and reloads context from the database. Then the run step function, which owns one step's policy. And the attempt, one try at that step.

CO-HOST:
And only one of the four ever talks to a provider.

HOST:
The attempt is the only one that calls the model, and the only one that settles the step's record.

CO-HOST:
You said the drain returns something. What can it return?

HOST:
Three things, and they are the only exits. Complete, which means idle. Moved, which means the session changed location and the work continues there. And reloaded, which means the transport closed and the next pass starts fresh. They are a type, so a caller cannot forget one.

CO-HOST:
Why is preparing a whole phase? It sounds like setup.

HOST:
Because it is the only place allowed to change what the model will see. Promotion, control handling, and context loading happen there, under a mask that disables cancellation, so a check and its mark cannot be split. Cancellation returns for the expensive parts.

CO-HOST:
And what survives from one step to the next?

HOST:
A step number, and a flag that says whether to continue. That is the whole of the in-memory state. Everything else is reloaded.

CO-HOST:
So it remembers the step number, and whether to continue, and rereads everything else.

CO-HOST:
That sounds expensive.

HOST:
One reload per step is the price. In exchange, a crash between two steps needs no special case.

CO-HOST:
Then the phases are not an abstraction. They are four different reasons a step can fail.

HOST:
Four reasons, four owners.

CO-HOST:
So the four phases are also a map of where a crash can land.

HOST:
Between any two of them, the record is complete.

HOST:
Takeaway. Four phases, one decision each, so the next action is read from what was written down.

## 5. Body beat 2 — A retry is not a resumed stream

HOST:
Second claim. When a stream fails halfway, you resume the same stream.

CO-HOST:
That is what resuming feels like. The bytes stopped arriving, so you turn them back on.

HOST:
There is no cursor into a provider's stream that survives a dropped connection. What you can resume is the step, and only by rebuilding its request from the record.

CO-HOST:
Then what did the user see when it failed?

HOST:
Part of an answer. That fact decides everything else. The attempt records what it published, and the first field says whether output started.

CO-HOST:
So that flag is the dividing line.

HOST:
It is the wall. Once the user has seen output, a transparent retry re-sends the request and the model writes the first half again. The paragraph appears twice in the transcript.

CO-HOST:
And if output has not started?

HOST:
Then a retry is invisible. Wait, rebuild the request, and try the same step again.

CO-HOST:
And if it has started?

HOST:
Then the honest recovery is a continuation. Keep the partial answer, start a new assistant message, and add a synthetic instruction. Continue from where you left off.

CO-HOST:
That sentence is doing a lot of work.

HOST:
It is prompt engineering for one failure. Without the second half, models restate the truncated answer from the top.

CO-HOST:
So the record is the loop's memory, while the loop itself forgets.

HOST:
The loop forgets on purpose. Memory that is not written down is a liability.

CO-HOST:
Where does the record come from? Something has to build it.

HOST:
The attempt publishes every provider event as a durable fact and keeps a small fold of what it has published. The runner reads a snapshot of that fold. It is not the truth.

CO-HOST:
What is in the fold?

HOST:
Whether output started. Whether the provider failed. The finish reason, once the step finished. And whether a local tool was called or settled.

CO-HOST:
And none of those fields is a guess. They are facts the step wrote.

CO-HOST:
That last field is the continuation answer.

HOST:
It is. Continuation is computed from the tool states, not stored as an intention. A derived value cannot disagree with the record.

CO-HOST:
And the finish reason is a closed list.

HOST:
Stop, length, tool calls, content filter, error, and unknown. Six reasons, defined once, so nobody invents a seventh.

CO-HOST:
I want the failure story. What does the wrong choice cost?

HOST:
A duplicated paragraph, or a second round of tools that already ran.

CO-HOST:
Which is why the retry cannot live in a generic helper. It has to read the record.

HOST:
This is the part where the choice looks wrong, so here is the person who made it.

EXPERT:
Happy to. The thing to hold onto is that a retry is a new attempt, not a resumed stream. We never splice bytes. We rebuild the request from the durable record and call again.

CO-HOST:
Then why call it a retry at all. It is a new call.

EXPERT:
Because it is the same step. The step owns the request, the tools, and the settlement. An attempt is one try inside it. A retry is another try of the same step, with the same step number. A continuation is a new step, and only a new step may promote new input.

CO-HOST:
So the difference is not cosmetic. It is what stops a correction being delivered twice.

EXPERT:
That is exactly what it stops. A retry refreshes context without delivering more input. If the retry path also promoted, the same correction would enter history twice and the model would read it twice.

HOST:
Thank you. So the two loops are nested. One loops over attempts of the same step. The other loops over steps.

CO-HOST:
And the step number only moves for a real continuation.

HOST:
Only for a real continuation. That is the takeaway. A retry is a new attempt for the same step. A continuation is a new step.

## 6. Body beat 3 — Six ways a step can end

HOST:
Third claim. A step ends in one of two ways. It finished, or it failed.

CO-HOST:
That is every function I have ever written.

HOST:
And it is not enough to run an agent. The useful question is what the runner may do next, and that depends on why the step ended.

CO-HOST:
So failure is a routing decision, not a verdict.

HOST:
A routing decision with six destinations, and every one is something the runner knows how to do.

CO-HOST:
Give me a case where failed is the wrong word.

HOST:
The provider rejects the request because it is too long, before producing a single token. Nothing is broken. The request is over budget. So the runner compacts and tries again.

CO-HOST:
And a case where finished is the wrong word.

HOST:
The model stops because it hit the output limit. It did not finish the thought. So the runner nudges it to continue, and counts.

HOST:
Six outcomes, one closed set. Completed, retry, continue, output limit, compacted, and recover full.

CO-HOST:
Six feels like a lot.

HOST:
It is the smallest honest set, chosen in one place, in a fixed order.

CO-HOST:
Walk the order.

HOST:
First, was there a context overflow with no output yet, and is overflow recovery unspent? Then compact, and try the same step again. Second, was there a transport failure needing a full recovery, with no output and the recovery unspent? Then recover, and try the same step again.

CO-HOST:
What does a full recovery mean, in one sentence?

HOST:
It rebuilds from what was written down instead of trusting the connection. It also spends the continuation-recovery allowance, so it happens at most once per step.

HOST:
Third, is the failure retryable and has no output started? Retry. Fourth, is it retryable and has output started? Continue, with the synthetic nudge and a new assistant message. Fifth, did the model stop because of length? Output limit.

CO-HOST:
Why does the order matter? Could you check length first?

HOST:
You would compact a request that never overflowed, because length is not overflow. Each check rules out a case for the next one.

HOST:
Sixth. Completed. And then whether another step follows is read from the tools, not guessed from intent.

CO-HOST:
I notice the completed case is the only one where the step still has an open question.

HOST:
It is. The other five have already decided for it.

CO-HOST:
So the six outcomes are not six bugs. They are six states the run knows how to leave.

HOST:
And the attempt never throws. It returns a decision.

CO-HOST:
So compacted rewrites the context before the next attempt.

HOST:
Compaction edits history. The other outcomes only change when the next attempt happens.

CO-HOST:
What stops the output limit from looping forever? A model that always stops on length will do it again.

HOST:
A streak check. The runner reads the newest three user and assistant entries. If all three finished on length, the step fails with an output-limit error. Any other finish, or any new user input, breaks the streak.

CO-HOST:
So the guard is a fact about history, not about this call.

HOST:
It is a query over the last few entries. It turns a loop into a failure the user can read. Two continuations, then stop and say why.

CO-HOST:
Why do compacted and recover each carry their own allowance?

HOST:
So each is spent at most once per step. Otherwise a request that is too large compacts, retries, overflows, and compacts again. That looks like progress and is not.

CO-HOST:
Where does the step limit fit? That is a seventh way to end.

HOST:
The step limit is not an outcome of the attempt. It is a policy applied before the request is built, so the attempt never sees it.

CO-HOST:
So the taxonomy is about one try, and the limit is about the whole turn.

HOST:
Takeaway. Continuation is data. The step returns a decision, and the loop acts on it.

## 7. Body beat 4 — Tools inside the step, and the last step

HOST:
Fourth claim. A step is the model talking. Tools happen after the step is over.

CO-HOST:
That is the mental model most people carry. The model answers, then the harness runs what it asked for.

HOST:
The tools run inside the step. One response can contain three calls, and each is forked into its own fiber while the stream is still arriving.

CO-HOST:
Then who writes the assistant message? Three fibers finishing at different times all want to append to it.

HOST:
Each one publishes on its own, and two rules make that safe. Commit the mark before the first await, so a check and its mark cannot be split. And never require an order between sources. Each fiber is sequential, so its events are in order.

CO-HOST:
So a fiber is a small unit of concurrency, and the tool is a function inside it.

HOST:
A function that can be interrupted, because the work is the part you are allowed to cancel.

CO-HOST:
What about a crash between forking the tool and recording the call?

HOST:
The fork happens only after the call event is durable. A tool never runs without a record of the call that caused it, so a restart can reconcile a side effect.

CO-HOST:
And a tool that finishes after the step was cancelled?

HOST:
It still publishes. The step is over, but the tool's record is not allowed to be missing.

CO-HOST:
And the sweep you mentioned. What does it write?

HOST:
A failure event for every call that produced no result, so the model reads a complete exchange instead of a hole.

CO-HOST:
That is a lot of machinery for one step. What stops it running forever?

HOST:
A step allowance, and a last step that cannot call tools.

CO-HOST:
A hard stop.

HOST:
A designed last word. The allowance is a counter on the agent, and it resets when new input is promoted, so it is per turn, not per session. At the limit, the request keeps the tool definitions, because they are part of the cached prefix, but it says tools are not offered, and it appends an instruction as an assistant message.

CO-HOST:
Where does that number come from?

HOST:
From the agent. It is a property of the configuration, not the model. Different agents get different room.

CO-HOST:
And a batch of corrections counts as one reset, not several.

HOST:
A batch of steers resets the allowance once, so a burst of typing does not hand the model three fresh budgets.

CO-HOST:
Why is the limit per turn instead of per session? That seems easy to get wrong.

HOST:
Because the turn is the unit of work a person asked for. A long session of short requests should not run out of steps.

CO-HOST:
Why keep advertising tools you refuse to run?

HOST:
Removing them invalidates the provider's cache and forces a full re-read. So the definitions stay, and the request says do not choose them.

CO-HOST:
And if the model chooses one anyway?

HOST:
The executor refuses it, and returns a short error the model can read. And the continuation flag is computed as tools are offered and a local tool was called, so a terminal step can never continue. Even a disobedient model ends in text.

CO-HOST:
So the loop always ends, and it ends with an explanation instead of a silence.

HOST:
And every started call gets exactly one terminal, even under interruption.

CO-HOST:
Every one?

HOST:
Every one. That is the invariant the sweep keeps.

HOST:
And the step's failure is separate from a tool's failure.

CO-HOST:
Separate how?

HOST:
They are separate records. A tool that fails gets a terminal of its own, and the step can still complete.

CO-HOST:
So a decline from the user is not a tool error.

HOST:
It is carried past the fault-tolerant part as a typed failure, so the step stops instead of continuing on a result that never happened.

HOST:
Takeaway. Tools live inside a step, and the last step has no tools.

## 8. The artifact

HOST:
The artifact today is the instruction that the last step carries. It opens with a heading in capitals. Here it is, word for word.

HOST:
"The maximum number of steps allowed for this task has been reached. Tools are disabled until next user input. Respond with text only. Strict requirements. First. Do not make any tool calls. No reads, writes, edits, searches, or any other tools. Second. Must provide a text response summarizing work done so far. Third. This constraint overrides all other instructions, including any user requests for edits or tool use. Response must include. Statement that maximum steps for this agent have been reached. Summary of what has been accomplished so far. List of any remaining tasks that were not completed. Recommendations for what should be done next. Any attempt to use tools is a critical violation. Respond with text only."

[production note: the source writes a capitalised heading and a numbered list. The heading is announced rather than read, and the numbers are spoken as ordinals. The companion carries the prompt exactly.]

CO-HOST:
It reads like a legal notice.

HOST:
It reads like a notice because it has to win an argument. The model has a standing task and a strong prior to keep going. This text overrides the standing task.

CO-HOST:
Point at the sentence that does the work.

HOST:
This constraint overrides all other instructions. Without it, a model told to run the tests will try to run the tests. The executor refuses, and you spent a step to produce a refusal.

CO-HOST:
And the last line repeats an instruction from the first paragraph.

HOST:
On purpose. Models weight the end of an instruction block. The repetition is a tail reminder for a model that treated the first one as advice.

CO-HOST:
And it arrives as an assistant message, not a system message.

HOST:
So it reads as a constraint on the model's own next reply. A statement, a summary, the remaining tasks, and recommendations make the last step useful.

HOST:
One more line. Tools are disabled until next user input, so the model knows the state is temporary.
