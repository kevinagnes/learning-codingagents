## 4. Body beat 1 — The toolkit is a prompt

HOST:
Here is the claim. A tool description is not documentation for humans. It is a policy document, and the model reads it before it decides anything.

CO-HOST:
Policy is a strong word for a paragraph of text.

HOST:
Then test it. The model needs to look at a file. It has a read tool and a shell. Which one does it reach for?

CO-HOST:
The shell, most of the time. Running a command is what it saw most in training.

HOST:
And you cannot take the shell away, because sometimes a command is the only way. So you cannot remove the habit. You can only tell the model when not to reach for it.

CO-HOST:
Tell it where? The tool list is names and argument shapes.

HOST:
The description. Every tool arrives at the model with a name, a shape for its arguments, and a paragraph about what it does. That paragraph is the model's only documentation for that tool, and it ships in every request.

CO-HOST:
What are the paragraphs doing?

HOST:
Four jobs, and they hold across the toolkit. First, state what the tool returns and in what shape, because the model plans its next move from that. The read tool says every text line comes back prefixed with its line number. Then it adds the sentence a careless author would leave out. The prefix is for reference and is not part of the file content.

CO-HOST:
Why does that second sentence have to exist?

HOST:
Because the edit tool tells the model to omit that prefix, and it cannot detect a copied prefix. It can only fail to find a match.

CO-HOST:
So the rule is taught in prose, in two places, or the model hits the same error three times and blames the tool.

HOST:
Which is a constraint the code cannot check. It exists only as a sentence. And that is the third job, the one people forget.

CO-HOST:
What are the other two again?

HOST:
The first is the output shape. The second is naming the preferred alternative, and the toolkit does that everywhere. The shell description tells the model to prefer the dedicated tools. The read description sends content search to another tool. The write description sends partial changes to edit.

CO-HOST:
So the descriptions point at their neighbours. The toolkit defends itself.

HOST:
And the model is steered without the harness policing it. The fourth job is the subtle one. Describe the failure the phrase prevents. The edit description does not only say the match must be unique. It says what happens when it is not, and then it gives the remedy.

CO-HOST:
Because a rule without a remedy is a rule the model will hit, and then hit again.

HOST:
The description is written as the error message the model would otherwise generate for itself.

CO-HOST:
What is in the toolkit?

HOST:
Nine tools carry the core workflow in four families.

CO-HOST:
Discovery and mutation, then the shell, and two tools that reach outside the repository.

HOST:
Discovery finds files, contents, and paths. Mutation changes them. A surgical replacement, a whole file, and a multi-file envelope for the models that do better with it.

CO-HOST:
And the longest description in the toolkit belongs to the replacement tool, by a wide margin. Not an accident, I assume.

HOST:
Not an accident. The longest descriptions belong to the tools with the sharpest edges, and every sentence in that one is answering a failure the model would otherwise hit. You do not trim it, because the sentence costs less than the retry it prevents.

HOST:
One more property, and it comes back in a minute. Some descriptions are not static text. The shell description is assembled per request so it can name the shell and the operating system the command will really run on. The web search description interpolates the current year, so the model does not assume a stale cutoff.

CO-HOST:
So a description can carry facts that would otherwise go stale. Interpolate those, and keep the rest fixed so the prompt stays cacheable.

HOST:
Now the takeaway.

CO-HOST:
A tool description is where you fix behaviour you cannot fix in code.

HOST:
Say it more usefully. Every sentence in a tool description either prevents a specific failure or buys nothing.

## 5. Body beat 2 — The tools that can hurt you

HOST:
Second claim. Three tools are dangerous, and the danger is not the tool. It is the contract you left out.

CO-HOST:
Three? A coding agent can run any command on my machine.

HOST:
The multi-file edit, the shell, and the background shell. They are dangerous in three different ways. The multi-file edit because not every model is good at it. The shell because it can hang, and because its output can grow without limit. The background shell because it keeps running where the model cannot see it.

CO-HOST:
Start with the multi-file edit.

HOST:
A model that mangles the envelope can delete a file it meant to edit. So the harness does not decide once for all models. It decides per model.

CO-HOST:
Per model how? The tool list is one list.

HOST:
A session hook. Before the request is built, the hook inspects the model and deletes one of the two editing families. If the model is the kind that does well with the patch envelope, the edit and write tools are removed. Otherwise the patch tool is removed.

CO-HOST:
So the model never sees both families.

HOST:
Never. And the same hook runs on every kind of request the session makes, not only the ordinary step, so the choice cannot flip halfway through a run. A tool list that changes between steps can invalidate a cached prompt.

CO-HOST:
Then the shell. What does the contract buy?

HOST:
Three bounds. A foreground command gets a default timeout, and when it fires, the result is not a bare failure. It names the limit and tells the model to retry with a larger timeout.

CO-HOST:
So the model gets the remedy, not only the error.

CO-HOST:
The second bound is output. A command that logs without end does not pour into the conversation. The full text goes to a backing file, and the model receives a bounded tail plus a path to the rest.

HOST:
Which is the budget rule from two episodes ago, applied to the tool with the widest mouth. It is also why the shell description tells the model not to re-run a command for more output, and not to trim the output by hand.

CO-HOST:
And the third bound is time. A command can be moved to the background.

HOST:
One instruction, and it is unusually emphatic. The model is told it will be notified automatically when the command finishes, that the notification will include the output, and that it must not poll for completion even if it needs the result to continue.

CO-HOST:
And the harness can make that promise, because when the job settles it delivers a synthetic message carrying the output. So if the command is still running, the model does not have to sit there asking whether it is done.

HOST:
That is the trade. The model gives up waiting, and in exchange it stops burning steps. The instruction repeats itself on purpose. It names the exact bad pattern, sleeping and then reading the output file, because a bare prohibition is easy to ignore.

CO-HOST:
Does it carve anything out?

HOST:
One thing. Unless the user explicitly asks otherwise. That keeps the model able to obey a user who genuinely wants the current output. And the instruction gives the model something that is not waiting. It says that if there is nothing else to do, end the response, and it will be resumed when the command finishes.

CO-HOST:
So the instruction is followable because it names an action.

HOST:
That is the difference between a rule and a wish. And one quiet detail. When the shell job starts, it records enough about itself that a crashed process can bring the command back. A command still running after the process died is its own kind of danger.

CO-HOST:
So the dangerous tools are the ones with the most prose.

HOST:
Almost. Say it the useful way. A tool that can hurt you does not get a warning. It gets a contract. One editing family at a time, a bounded command, and a notification instead of a wait.

## 6. Body beat 3 — One tool that runs code

HOST:
Third claim, and it sounds like a mistake. You can take the entire native tool list out of the request and put one tool in its place.

CO-HOST:
One tool, and the model can still do everything?

HOST:
The model writes a program.

CO-HOST:
So there is one tool called execute, and its input is code. Inside that code it calls the other tools.

HOST:
Exactly. Now the case that forces it. An external tool server, the kind that speaks M C P, contributes a hundred and eighty tools. Their definitions alone are tens of thousands of tokens before the user has said a word. The model chooses between a hundred and eighty names, many of them near twins. And a job that needs six of them takes six steps, because one step is one model call.

CO-HOST:
And each of those steps re-sends everything.

HOST:
It does. Now the pushback I expect. The loop already runs independent tool calls in parallel inside one step. Why does the model need code?

CO-HOST:
That is the part I do not follow. Parallel calls are already there.

HOST:
Because parallel calls cannot feed each other. A batch goes out together and the results come back separately. Nothing in that batch can consume another call's result, because it does not exist yet. A program can. The second line uses what the first line returned.

CO-HOST:
So the difference is composition, not speed.

HOST:
Composition across calls inside a single step. That is why this is a real change and not a wrapper. And it is the point where the choice looks wrong, so here is the person who made it.

HOST:
Welcome back. Defend this one. Why delete a working list of tools?

EXPERT:
Because the list is the wrong shape for the work. Most real tasks are a pipeline. Find the file, read the part, change it, run the check, read the failure, change it again. As separate calls that is six round trips and six copies of the conversation. As code, it is one request, one program, one result.

CO-HOST:
But a long tool list is not free either.

EXPERT:
It is not. The definitions ship in every request. With hundreds of tools you pay for a catalog on every step, and the model's choice gets worse as the list grows. So we keep the tools and drop the list. The tools are described in the prompt instead.

CO-HOST:
So the catalog is the list, moved into the prompt.

EXPERT:
Yes, and we bound it. Every namespace is shown, and then full listings are added one namespace per round, shortest first, until the token budget runs out. Whatever does not fit can be found by a search inside the program. The model is told the search is synchronous, which is the opposite of what most models assume, and that its results carry the exact path to call. Guessing a path is the failure we were trying to prevent.

HOST:
Thank you. One detail ties the choice back to the last beat. The tool that runs code is a static definition. It never changes, so it never invalidates a cached prompt. The catalog changes, and because the catalog is an instruction source, it updates as a delta instead of restating itself. The churn goes where churn is cheap.

CO-HOST:
And what stays on the native list?

HOST:
The core workflow tools opt out.

CO-HOST:
Reading, editing, and the shell stay native, because the model should always see those directly. Everything else defaults in, and the name of the tool that runs code is reserved so nothing can claim it.

HOST:
And the code itself runs in a confined interpreter. It can call tools and make web requests. It cannot import modules, cannot touch the filesystem directly, and cannot set timers. The web extension refuses file access outright. And the inner calls go through the same validation and hooks as any other call, which is the thing to remember for the next beat.

CO-HOST:
So the takeaway. When the work is composition, do not hand the model a longer menu.

HOST:
Say it as the rule. Expose the toolkit as a single execute call and let the model compose.

## 7. Body beat 4 — Plugins as tool sources

HOST:
Last claim of the episode. A plugin adds tools through the exact same door a built-in uses, and there is no second execution path.

CO-HOST:
That is not how extension points usually work. Usually a plugin gets its own interface, and everything downstream learns to special-case it.

HOST:
Not here.

CO-HOST:
So it receives a context with one domain per subsystem, and the tool domain is small. It can register tools through the same registration step the built-ins use, ask the registry to reload, and list what is there.

HOST:
Which means that after registration, a plugin tool is indistinguishable. Consider the case that needs it to be. A plugin wants to add a linting tool. At the same time it wants to redact secrets out of the arguments before any tool runs. Without a seat in the registry, and without a way to see calls, that plugin has to be compiled into the core.

CO-HOST:
Registering a tool is one thing. Watching every call is another.

HOST:
Which is why the design separates them. Definition goes through the registration step. Observation goes through hooks, and there are exactly two tool hooks. One runs before the call. One runs after.

CO-HOST:
And the one before can do what?

HOST:
Two things. It can rewrite the arguments, which is what one of the built-ins does to strip empty values that some models send. Or it can reject the call outright, before anything runs. The hook that runs afterwards can see whether the call completed or failed, and it can rewrite the content that goes back to the model.

CO-HOST:
Then why can the second hook not reject the call as well?

HOST:
Because the tool has already run. The write has landed. The command has executed. Turning a completed call into a failed one would rewrite the written record after the side effect, and it would no longer match the world. Only the pre-execution hook has a failure channel, and that asymmetry is the whole point.

CO-HOST:
So the failure channel is a statement about what has already happened.

HOST:
Exactly that. Hooks fire in the order they were registered, and a hook can declare that it applies to one provider only, so a provider-specific fix does not need a branch inside the callback.

CO-HOST:
Now the external tool server. It behaves like a plugin, but its tool list changes while the session is running.

HOST:
And that is the last mechanism, and the one that is easiest to get wrong. A dynamic source like that keeps one stable registration step that reads the newest tool list. When the list changes, it asks for a reload instead of registering itself again at the end.

CO-HOST:
Why does the difference matter? Both end up with the new tools.

HOST:
Because registration order decides which plugin wins when two of them claim the same tool. If a refresh registered at the end, the refresh could jump ahead of a plugin that was added after it. Reloading in place keeps precedence a matter of order, not a matter of timing.

CO-HOST:
And the same hooks see the calls inside a code mode program?

HOST:
They do, and this is the connection back to the middle of the episode. When the model sends one program instead of a call, every inner call still runs the before hook. A plugin that handles only the outer call sees almost nothing, because the interesting calls are inside the program.

CO-HOST:
So extension is two separate things, not one.

HOST:
Say it cleanly. One registration step to add tools, two hooks to observe them, and only the first hook may reject.

## 8. The artifact

HOST:
The artifact this episode is a real built-in tool description. The read tool, because it is short and it does several jobs at once. Here it is, the load-bearing part, word for word.

HOST:
"The prefix is for reference and is not part of the file content. Directory entries are returned one per line. Use offset and limit to read large files or directories in sections. Prefer one larger read over many small slices, and use grep to find specific content in large files."

[production note: the description opens with a sentence that names the exact line-prefix format, and that sentence contains a digit. The full description is in the companion.]

CO-HOST:
That is a manual. A short one, but a manual.

HOST:
Watch what each sentence does. The first is a contract about a prefix the tool injects itself.

CO-HOST:
Which matters because the edit tool can only fail a mismatched prefix. It cannot explain one.

HOST:
So the sentence teaches the rule the executor cannot enforce.

CO-HOST:
That is an odd thing to have to say out loud, but the tool cannot say it for itself.

HOST:
The second sentence answers the question a caller would otherwise ask, which is how a directory comes back. The third is the paging contract. Section reads are allowed, and their arguments are named. Without it, the model guesses at how to read a large file.

HOST:
And the last sentence is the interesting one. It is two redirects and one prohibition in a single line. Prefer one larger read over many small slices, which stops a model walking a file in windows and inflating the step count. And use the content search tool when you know what you are looking for, instead of reading a whole file to find one function.

CO-HOST:
So the description is routing, not only documentation.

HOST:
It is routing. That is the whole episode in one paragraph. The tool tells the model which shape its answer arrives in, which neighbour to use instead, and which limit it must not cross. Read it again and notice how much of it is about the other tools.

CO-HOST:
Which is why the description ships in every request.

HOST:
And why the toolkit is a prompt, not a library.

## 9. Recap

HOST:
Where we landed. One. A tool description is prompt engineering. It states the output shape, names the preferred alternative, and states what the executor cannot check.

CO-HOST:
Two. The dangerous tools are gated by contract. One editing family per model, a bounded command, and a notification instead of a wait.

HOST:
Three. Code mode replaces the native list with one execute tool and a bounded catalog.

CO-HOST:
And plugins add tools through the same registration step, watched by two hooks.

HOST:
Say the rule, and the one it stands on.

Validate at the boundary, bound every output, then expose the toolkit as a single execute call and let the model compose.
