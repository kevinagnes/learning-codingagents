## 4. Body beat 1 — A tool is one object

HOST:
A tool is not a plugin with a shape bolted on. It is one object, and every tool in the system has the same parts.

CO-HOST:
I have written tools. Mine were a name and a function. What else is in there?

HOST:
Six parts. A name, options, a description, a shape for the input, an optional shape for the output, and an executor.

CO-HOST:
Options. That is a strange thing to put in a tool.

HOST:
The namespace it belongs to, the permission action used to filter it, and the flags that decide how it is offered. We will come back to names.

CO-HOST:
Why does the contract need to be identical for every tool? A built-in and a tool from an external server are not the same kind of thing.

HOST:
That is exactly why. The registry treats every tool identically, so it cannot care where the tool came from. One shape in, one shape out.

CO-HOST:
And the executor? That is the function.

HOST:
The executor takes the decoded input and a context. The context is the same for every source. The session, the agent, the message, the call identifier, and a way to report progress.

CO-HOST:
Progress. So a long command can say it is still going.

HOST:
Yes. And the executor returns two things, which is the part people miss. It returns a structured output, and it returns the content the model actually reads. They are not the same thing.

CO-HOST:
Give me a case where they differ. I can see why you would want both, but I cannot picture the same result arriving twice.

HOST:
A search returns ten results. The harness gets a list it can count, filter, and render in an interface. The model gets a short block of prose with the same ten results in it. The model reads prose. The harness reads data.

CO-HOST:
So one call, two results. The list is for the program, and the paragraph is for the reader.

HOST:
That is the whole idea. The output shape is optional, but when a tool declares one, the value is checked against it before anyone else sees it. A tool that returns the wrong shape is a bug, and the model should not inherit it.

CO-HOST:
Why is the output shape optional and the input shape not?

HOST:
Because the input is the model's guess and the output is your code's promise. If the model gets the input wrong, the call fails and it retries. If your code gets the output wrong, the mistake travels into history and every later step reads it.

CO-HOST:
One is a bad guess. The other is a bad fact.

HOST:
And bad facts are much harder to remove.

CO-HOST:
You said the contract is deliberately uniform. What breaks if it is not?

HOST:
Then the registry needs a branch for each source, and every branch is a place where one source behaves differently. One shape means one place to handle all of it.

CO-HOST:
And the description? That is prose. Why is prose part of a contract?

HOST:
Because for the model, the description is the documentation. It travels with the name and the input shape in every request. It is the only thing that tells the model when to reach for this tool instead of another one.

CO-HOST:
So a vague description is a tool that gets used badly, or not at all. And nobody files a bug against a sentence.

HOST:
Nobody does. The description is not decoration. It is interface. And notice what the contract does not contain. It does not contain trust. Registering a tool says nothing about whether it is allowed to run. That decision lives somewhere else, and it is not the tool's to make.

CO-HOST:
So registration is a claim about what exists, not about what is permitted. Which is the next beat, I suspect.

HOST:
The beat after next. First, how the tool gets into the catalog.

## 5. Body beat 2 — Registration is a replay

HOST:
Registration adds the tool to a map.

CO-HOST:
That is what I would write. A map, an add, a remove, done.

HOST:
It is not a map, and it is not an add. Registration is an edit, and the registry keeps the list of edits instead of the result.

CO-HOST:
Say that again.

HOST:
A registration is a small function. It receives an empty editor and it adds, updates, or removes tools, or declares a namespace. The registry stores that function. It does not store the catalog.

CO-HOST:
Then where does the catalog come from?

HOST:
Every read rebuilds it. Take a fresh empty editor, replay every registration in order, and keep the result. That is the catalog for this moment.

CO-HOST:
That sounds expensive. A registry with a hundred tools, rebuilt on every change, because one plugin added a description. I would reach for a map out of self defence.

HOST:
You rebuild on the first read after a change, and then you cache. Rebuilds are cheap because the edits only build small maps. And you get three things a mutable map cannot give you.

CO-HOST:
Go.

HOST:
One. Precedence is deterministic. The last valid registration for a name wins, because it runs last. Two. Undo is real. Removing one registration rebuilds the list without it, and whatever it was covering appears again. Three. A plugin that discovers tools later can invalidate and reload, instead of appending to the end of the list.

CO-HOST:
The undo is the interesting one. In a map, remove deletes the name, and there is nothing underneath it. The earlier entry was overwritten, not stacked. So it cannot come back. I have written that one.

HOST:
It is a common one. And the same mistake has a second face. If a plugin forgets to tie its registration to a scope, its tools outlive the plugin entirely. A registration is installed as a scope finalizer as well, so closing the scope disposes it. Forgetting that is how a disabled plugin keeps answering calls.

CO-HOST:
What about a bad registration? A broken shape, a name with a space in it.

HOST:
It is logged and skipped. Registration errors are collected, not thrown, so one bad plugin cannot take down the whole catalog. The check covers the namespace, the name characters, a reserved name, and whether the declared shapes convert to the wire format at all.

CO-HOST:
So a tool can be rejected before the model ever sees it.

HOST:
That is the point. A shape that only fails when a call arrives means the tool was advertised, the model chose it, and then it died on first use. Reject it at the door instead.

CO-HOST:
And an update? Can a plugin rename a tool by updating it?

HOST:
No. An update re-locks the name and the namespace, so it can change a description but not an identity. An invalid update leaves the previous definition in place.

CO-HOST:
What about two plugins that both want the same name? One of them loses and never finds out.

HOST:
You get the later one, and which one is later is not obvious from the outside. Recording the winning registration's source turns a mystery into a diagnostic.

CO-HOST:
And this all happens before the request, not during it. So the catalog a step sees is a photograph, not a window.

HOST:
Because the catalog is replayed and captured, tools are fixed before the request is sent. There is no in-memory loop that registers a tool halfway through and calls it in the same breath. A change lands in the next snapshot, not in the current call.

CO-HOST:
Which is a constraint on the design, not on you.

HOST:
It is a constraint on the design. The model cannot invent a capability mid-step, and you cannot slip one in.

## 6. Body beat 3 — The snapshot

HOST:
The registry holds the catalog. So whatever is in the registry when a call arrives is what runs.

CO-HOST:
That sounds correct, and it also sounds like the bug I described. A tool changes between the moment the model reads the menu and the moment it orders.

HOST:
That is the gap a snapshot closes. A snapshot is two things that must agree. The definitions the provider will show the model, and an executor that can run those tools. Both are captured for one request.

CO-HOST:
Why two things? The list is the list.

HOST:
Because the list is what the model reads, and the executor is what your code does. If they come from different moments, the model can ask for something it saw and the executor refuses. One snapshot means a step offers exactly the tools it can run.

CO-HOST:
So the executor is not looking at the registry. It closes over the snapshot's own maps, and a reload or a disposal only affects later snapshots.

HOST:
Only later ones. And the list is filtered before it is captured.

CO-HOST:
Filtered by what?

HOST:
By permission rules. One rule, deliberately narrow. If a rule denies a tool for every resource, it is dropped from the catalog. Anything softer leaves it visible, and the tool still checks its own policy when a call arrives.

CO-HOST:
So hiding is not permitting.

HOST:
Hiding is not permitting. The catalog stays honest and the execution stays safe, and that redundancy is on purpose. Treat a hidden tool as safe and a guessed name walks through.

CO-HOST:
Now the names. This is where I get lost. I have a tool in a namespace, and the model calls something else entirely.

HOST:
A tool has a name and an optional namespace. The namespace exists so a family of tools can share one description. But the model needs one flat name. So the dots become underscores, and the two are joined. A tool named baz in a namespace called foo dot bar becomes foo underscore bar underscore baz.

CO-HOST:
And characters that are not letters or digits?

HOST:
Become underscores. Which is how you get a collision nobody planned. One name with a dot and another with an underscore normalize to the same flat name, and the second silently replaces the first.

CO-HOST:
Silently. So two names can become one, and nothing complains.

HOST:
Nothing complains, because both registrations were valid. Which is why the failure messages are specific. If the name was advertised and then removed for this request, the error says it is not available for this request. If the name never existed, the error quotes the name back and points at the available list.

CO-HOST:
So the same symptom gets two diagnoses.

HOST:
One is a context change. The other is a guess.

CO-HOST:
Now the part I actually doubt. You said type safety ends at registration.

HOST:
I did, and the choice looks wrong. So here is the person who made it.

EXPERT:
We erase the producer's type at the boundary, on purpose. A built-in, a plugin, and an external server all declare their input differently, and the registry cannot be generic in a type it cannot name.

CO-HOST:
So I lose the compiler and get a check at runtime. And a runtime check is a string comparison. The compiler was proving something. This is hoping.

EXPERT:
You keep a check at registration, where the declared shape has to convert to the wire format at all. And you get a second check where the call arrives. That second one is not a formality. It is the same decode that builds the message the model reads. The check you would have done at compile time is the check that teaches the model.

CO-HOST:
So the type error becomes a conversation.

EXPERT:
A short one, if the message is good. That is the next part.

HOST:
So the rule. A step can only run the tools it advertised.

## 7. Body beat 4 — What the model reads when it is wrong

HOST:
If the model sends the wrong arguments, the tool should throw, and the model should see the failure.

CO-HOST:
That is honest. My function failed. Report it. I would rather see the real error than a message someone wrote to be gentle with a model.

HOST:
Report it to whom? A failure from inside your code is written for you. It names a line and a type. The model needs a field, the value it sent, and a reason to try again.

CO-HOST:
So the error is part of the interface.

HOST:
The error is part of the interface, and the boundary owns it. Two things happen around every call. The input is decoded before the tool runs, and the declared output is checked after.

CO-HOST:
Before the decode, I have seen a repair step.

HOST:
There is one, and it is deliberately timid. It fixes a value only when the shape proves the mistake. A whole argument object that arrived as a string, a number that arrived as text, a null where an optional field belongs. If a branch is ambiguous, it leaves the value for validation to reject.

CO-HOST:
Why not coerce everything? If it looks like a number, make it a number. Half the tools I have written spend their first ten lines fixing up their own arguments. It feels like the same job.

HOST:
Because coercion without proof changes meaning. A string that could be a number and could be a name is a guess, and a guess that succeeds silently is worse than an error that fails loudly. The repair only fires when the shape is unambiguous.

CO-HOST:
Then the decode.

HOST:
One decode, against whatever shape the producer declared. Three kinds of shape are accepted, because producers declare them differently, and all three are normalized into one pass or fail with a list of issues.

CO-HOST:
And when it fails?

HOST:
The failure is formatted for the model. It names the tool, so a model that emitted three calls knows which one broke. It lists the issues with a path, so it can repair one field instead of the whole object. It shows the arguments it sent, because otherwise it cannot tell which value was wrong. And it ends with an instruction to update the arguments and call the tool again.

CO-HOST:
That last line sounds like hand holding. The tool already said what was wrong. Why does it need to be told to try again?

HOST:
It is the most important line in the message. Without it, models explain the error to the user instead of fixing it. The error becomes a report instead of a retry.

CO-HOST:
How many issues does it list? Because I have seen a validation report that was longer than the file it was complaining about.

HOST:
Five, then a count of the rest. A shape with thirty failures produces a wall of text that costs context and buries the first real problem.

CO-HOST:
And the output side?

HOST:
Checked on the way out. A tool that declares an output shape and returns the wrong one fails with its own message, because a violation that reaches history is inherited by every later step.

CO-HOST:
What about a tool that fails with something that is not a tool error at all? A plugin can throw anything. I have thrown strings.

HOST:
It is wrapped into one at the boundary. A plugin can fail with anything, and a foreign failure would slip past every downstream handler and leave its call permanently unsettled. So the contract is enforced once, at the edge.

CO-HOST:
And after the step limit?

HOST:
Tools are disabled, and a late call is rejected with a message that says so. That message is doing something subtle. It tells the model the loop is ending, not that the model made a mistake.

CO-HOST:
Which brings us to the message itself.

HOST:
It does. Here it is.

## 8. The artifact

HOST:
This is the message a model receives when its arguments fail. I am reading the lines that carry the design, with the two field names spoken as words and the argument block saved for after.

HOST:
"Invalid arguments for tool edit:
new string: Expected string for form field new string
Arguments provided:
Update the arguments and call the tool again."

[production note: the source writes two camel-case field names where the read says "new string". The companion carries the message exactly, including the echoed argument block.]

CO-HOST:
Shorter than I expected. Four lines.

HOST:
The missing part is the block between the last two lines. It repeats exactly what the model sent. A path, an old string, and no new string at all. Which is the bug.

CO-HOST:
So the message names the missing field, and then shows the object that is missing it.

HOST:
Four moves in four lines. It says which tool, which field, what the model sent, and what to do next. Remove one and the model has to guess. Without the tool name, it cannot tell which call failed when it made three. Without the echoed arguments, it cannot see which value was wrong. Without the last line, it explains the problem to the user instead of fixing it.

CO-HOST:
And the last line is the one a developer would never write.

HOST:
A developer does not need to be told to retry. A model does. That is the shift in this episode. The message is not a stack trace. It is an instruction for the next attempt.

CO-HOST:
Does it ever mislead? It calls a field invalid when it is missing.

HOST:
It reports what the shape said. Missing is a kind of invalid, and the path still points at the field. The model does not need the taxonomy. It needs the location and the instruction.

CO-HOST:
What if there are thirty problems?

HOST:
Five, and a count. The cap is deliberate. A giant error dump costs the very budget the retry needs.

CO-HOST:
So the error has a size too.

HOST:
Everything the model reads has a size. That is next week.

## 9. Recap

HOST:
Where we landed. One. A tool is one object, and its result has two readers. The model reads the words, and the harness reads the data.

CO-HOST:
Two. Registration is a list of edits replayed onto an empty page, so the last valid one wins and removing it uncovers the one below.

HOST:
Three. A request captures a snapshot of definitions plus an executor, so a step can only run what it advertised.

CO-HOST:
And the rule. Validate at the boundary, and write the failure for the model that has to fix it.

HOST:
One model call per step. Admission is not execution. Continuation is read from the record.
