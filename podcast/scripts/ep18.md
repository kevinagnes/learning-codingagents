## 4. Body beat 1 — One publish, two audiences

HOST:
An agent has one place where it announces what happened. Everyone who cares about an event is a subscriber to that place, and nobody gets a private copy.

CO-HOST:
But the two subscribers want opposite things. The thing writing the database wants order and certainty. The thing drawing a screen wants speed, and it will disconnect in a tunnel. How does one announcement serve both?

HOST:
By promising them different things. The bus has two kinds of consumer, and the difference is the contract, not the payload.

HOST:
The first kind is a projector. It is registered inside the process, and it folds the event into a read model inside the same transaction that records the event. It needs order, persistence, and exactly-once handling, because it mutates durable state. If it runs twice, the tables are wrong.

HOST:
The second kind is a listener. It observes the event after it is recorded, and it feeds the live stream. It needs to be fast. It is allowed to miss events, because it is rendering, not deciding.

CO-HOST:
So the same event can be a fact for one consumer and a hint for the other.

HOST:
Same event, same payload, two contracts. That is the sentence to hold on to.

CO-HOST:
Let me defend the other design. Why must it be the same event? Why not write to the database, then separately tell the screen, in whatever shape the screen likes?

HOST:
Because then you have two descriptions of one fact, and the two drift. One event type, two contracts, and the payload cannot disagree with itself.

HOST:
Then the server turns the live side into bytes. It subscribes one listener to the bus, encodes each event once, and pushes the encoded frame into a queue for each connected client.

CO-HOST:
One queue per client. So a slow client cannot slow the others.

HOST:
Not for long. Each queue is bounded. When a client cannot keep up, its queue overflows, the server drops that subscriber, and its stream fails with an explicit error. It does not grow the buffer until the process dies.

CO-HOST:
That still sounds harsh. You are killing a viewer because it blinked.

HOST:
You are telling a viewer it is offline. A client that cannot keep up has the same problem as a client that lost the network. It should reconnect from the log, not hold stale frames in the server.

CO-HOST:
So the bus is not a notification service. It is the edge of the record, and the screen hangs off the edge.

HOST:
The edge may lose events. The record may not.

CO-HOST:
And notice what the ordering forces. You publish after the commit, always, so a client never renders what the database does not contain.

HOST:
Notifying inside the transaction would risk showing work that then rolled back.

CO-HOST:
The projector cannot have that problem, because it is inside the transaction.

HOST:
It is. That is the asymmetry. The projector shares the writer's fate. The listener does not, and so it must not be told too early.

HOST:
Two details show the same care. The subscription opens with a connected frame, so the client knows the pipe is live. And a heartbeat keeps a proxy from closing an idle connection during a long model call.

CO-HOST:
And if one event cannot be encoded?

HOST:
Then every subscriber fails at once. The encoding boundary has to be total over the public event list, or one bad event takes down every viewer. That is not a rendering bug. It is a boundary that was never closed.

CO-HOST:
One announcement, two audiences. A projector that must never miss, and a listener that is allowed to.

HOST:
And one more constraint that is easy to forget. A subscription can be scoped to a place. With a place in scope, you receive that place's events plus the global ones. A client that assumes it is watching everything will quietly miss a session that moved.

CO-HOST:
Even the firehose has an address.

HOST:
So the feed is a fan-out of announcements. Which of those announcements is a client allowed to believe?

## 5. Body beat 2 — Facts and hints

HOST:
Here is the claim I want to test. Everything on the wire is a fact, so a client that reads the stream needs nothing else.

CO-HOST:
You spent the last four minutes telling me the stream can drop events. If it is the truth and it can drop, the client is wrong. Which is it?

HOST:
It is two lists, declared per event type. The type decides once, and the code enforces it in one place.

HOST:
A durable event carries an envelope. The envelope has three parts. The aggregate it belongs to, a sequence number within that aggregate, and a version for the event's data shape. Those three things make it replayable. A client that reconnects can read the events back from the log and rebuild the same state.

HOST:
An ephemeral event has no envelope, and it is never replayed. It is a hint. A fragment of text, a fragment of reasoning, a progress tick from a tool. If a client misses one, it is inconvenienced. It is not wrong, because the final value arrives in a durable ending event.

CO-HOST:
So a durable event is not really a message. It is a position in a history, with a version attached.

HOST:
A position you can return to. That is the difference.

CO-HOST:
And the version is a promise to a reader that has not been written yet.

HOST:
It is a promise that an old event still has a shape a new reader can decode. Break it, and replay breaks for everyone who was offline.

CO-HOST:
So the delta is decoration and the ending is the record.

HOST:
The ending is authoritative. The delta is what makes it feel alive while you wait.

HOST:
And the deltas are batched. Stream fragments are coalesced on an interval before they are published. So a client must accumulate them and reconcile at the ending event. It must not assume one delta per token, or one delta per block. That assumption works in a demo and drifts in production.

CO-HOST:
Which means the screen is always an approximation until the ending lands.

HOST:
Always. The screen is allowed to be approximately right for a moment, and it must become exactly right at the end.

CO-HOST:
What does drift look like on screen?

HOST:
Text that is missing a phrase, or text that repeats one, because the client stitched fragments with the wrong assumption about how they arrive. The ending event is the repair.

CO-HOST:
So how do I know which list a new event belongs in?

HOST:
For every fragment you stream, name the durable event that carries the final value. If you cannot name it, the fragment is not a hint. It is a fact, and it belongs in the durable set.

CO-HOST:
Give me the list, then. What does a client actually have to handle to draw an agent at work?

HOST:
More than people expect. It needs the session appearing and changing. Renamed, agent selected, model selected, permissions, moved, busy, idle.

CO-HOST:
Execution state.

HOST:
Started, succeeded, failed, interrupted.

CO-HOST:
Step state.

HOST:
Started, streamed, ended, failed.

CO-HOST:
Output.

HOST:
Text and reasoning, where the deltas are optional and the ending is authoritative.

CO-HOST:
Tools, and the recovery events.

HOST:
Input arriving, the call starting, progress, success, failure. Plus retry and compaction, so those appear as something other than a freeze.

CO-HOST:
Plus the change preview, so a client can show the diff.

HOST:
The step's ending event carries the snapshot and the files it touched, and revert has its own events. That is how a client shows you the change without asking the filesystem.

CO-HOST:
And the blocking questions.

HOST:
Permission requests, form requests, and the endpoints that answer them.

CO-HOST:
Four different clocks, then. Execution, step, output, tools.

HOST:
Four clocks, and a client that merges them shows you a blur.

CO-HOST:
That is a long list for a progress spinner.

HOST:
It is a long list because the agent is not a spinner. It is a machine with phases, and a client that cannot name the phase cannot show you the truth.

CO-HOST:
So the durable ending is the truth. What happens when the client was not there to hear it?

## 6. Body beat 3 — The client that was not there

HOST:
The claim is simple. If a client disconnects, the fix is a bigger buffer.

CO-HOST:
Or you persist every delta, so nothing is ever missed. Storage is cheap.

HOST:
Both answers make the same mistake. They treat the live feed as a record that failed, when the live feed is a broadcast that was never a record.

CO-HOST:
Then why have a live feed at all? If the log is the truth, the feed sounds like a convenience for impatient people.

HOST:
It is a convenience, and the product lives inside it. Nobody wants to poll a database to watch a sentence form.

HOST:
The feed is volatile by contract. A slow consumer overflows its queue and the stream fails. Events published during a disconnect are missed. The recovery path is the durable per-aggregate log, not a bigger buffer.

HOST:
And making the feed durable would mean every stream fragment became a persisted fact. That is exactly what the split exists to prevent. You would bloat the log, and every projector would have to handle noise with no final meaning.

CO-HOST:
Here is what I cannot get past. The database already holds the current state. Why must a client rebuild it from events at all?

HOST:
Because the events carry the transitions in order, and a client shows a run while it is moving.

CO-HOST:
So how does a client catch up?

HOST:
It reads the log after the last sequence it saw. The read replays the durable events in order, emits a synced marker at the point where replay ends, and then, if the client asked to follow, continues with live events.

CO-HOST:
Why the marker?

HOST:
Because the client needs to know where replay stopped and the live stream began. Without it, a client can lose track of its cursor and ask for the same range again, in a loop. The marker is the seam.

CO-HOST:
So the client has two modes. Catch up, then follow.

HOST:
Catch up, then follow, and never mistake one for the other.

HOST:
And the two reads are separate surfaces. Watching and catching up are different requests. A client opts into the one it needs. The live feed is for the screen. The log is for correctness.

CO-HOST:
What happens if the client dies in the middle of the replay?

HOST:
It starts again from the last sequence it recorded. The log is a cursor, not a session.

CO-HOST:
What about the busy indicator? That feels like state, not decoration.

HOST:
It is ephemeral. Idle, retrying, busy. It is the coarsest signal a client needs, and it is re-derivable from the execution events. If you miss the status, the execution events tell the same story.

HOST:
Here is the test that decides all of this, and it is one question. Can you rebuild every read model from the durable events alone, with the live stream turned off? If yes, the stream is an optimization, and the design ports to another stack. If no, something that should be durable was left in the stream.

CO-HOST:
Ports to another stack. That is a strong claim.

HOST:
It is a checklist. The event log, with ordering per aggregate. The projectors that fold events into queryable tables. A way to read the log from a cursor. And then you replace the transport and the interface.

CO-HOST:
So portability is really a test of honesty. You find out what you believed was durable when you turn the stream off.

HOST:
It is a test you can run, which is rare for an architecture claim. Turn the stream off and see what breaks.

CO-HOST:
And if the log itself is lost?

HOST:
Then there is nothing to replay from, and the stream was never going to save you.

CO-HOST:
So the transport is disposable.

HOST:
The transport is disposable, and the line between fact and hint is not. If a feature only works because the socket stayed open, it is not a feature. It is a bug in that line.

CO-HOST:
And the change preview fits the same test.

HOST:
It does. A step's ending event carries the files and the snapshot. So a client that reconnects can rebuild the diff from durable events. The preview is not a picture the server painted for one viewer. It is a fact with a shape a viewer can draw.

CO-HOST:
So a client can watch, and it can catch up. But watching is only half of what a client does.

## 7. Body beat 4 — Writing intent, not commands

HOST:
Once a client can read the stream, it can do everything it needs to do.

CO-HOST:
No. I can watch the agent park on a permission request and wait forever. Reading is not answering.

HOST:
Fair. There are four operations, and every one of them is a durable write plus an advisory wake.

HOST:
The first is admitting a prompt. Recording new input is not the same as running it. Admission writes a durable row in the inbox and returns. Then a separate wake asks for execution. Keeping those apart is what makes admission idempotent by message identifier, and what lets a client submit work while the session is busy.

CO-HOST:
So the write is the promise. The wake is only a nudge.

HOST:
The nudge can be lost and nothing is lost with it. The row is still there, and the next drain finds it. The enqueued event is published before anything acts, so the proof that the work exists is durable first.

CO-HOST:
Idempotent by message identifier. Say what that buys me.

HOST:
A retried submit returns the first item instead of creating a second one. So a client can retry a dropped network call without duplicating the prompt.

CO-HOST:
And if the identifier belongs to a different session?

HOST:
Then admission refuses it. Reuse is only safe when the session and the type match.

CO-HOST:
Explain the two delivery modes, because I always mix them up.

HOST:
A steer changes work in progress, and it is delivered at the next safe step boundary. A queue starts new work, and it is delivered only when the session would otherwise go idle. Prompts steer by default, because a person typing in the middle of an answer usually means adjust this, not start over.

HOST:
A client can change its mind about a pending item. Flipping it from waiting to steering is how you push a correction into an answer that is already being written.

CO-HOST:
And the third?

HOST:
Answering a blocking question. A permission request is a parked fiber, waiting on a one-shot promise. Nothing in the agent moves until some client replies. The reply either allows the tool to continue, or carries the decline past the fault-tolerant boundary, so a no never becomes model-visible tool output.

CO-HOST:
What if nobody replies?

HOST:
Then it waits. There is no timeout by default. The client owns the decision to reply, to dismiss, or to interrupt. An unanswered permission is not a bug in the agent. It is an unanswered question.

HOST:
The fourth operation is interrupt. It stops the active execution. Interrupting an idle session does nothing, and the call tells you which of the two happened, so a client can tell a real stop from a no-op.

HOST:
Interrupt also takes a resume flag. With resume, it wakes the steering input and the control work that was waiting behind the interrupted intent. Queued prompts stay parked, because a steer-scoped drain never promotes them.

CO-HOST:
The resume flag sounds like it should restart everything, though.

HOST:
It restarts the correction, not the backlog. That is the distinction the flag encodes.

CO-HOST:
Let me try to break it. A user queues a prompt, then interrupts with resume. What runs?

HOST:
The correction runs. The queued prompt stays parked until the session would otherwise go idle. Resume does not promote the backlog.

CO-HOST:
And if the interrupt arrives a moment too late, after the run already settled?

HOST:
Then it reports that nothing was interrupted. An idle interruption is a no-op, and the call says so.

CO-HOST:
So stop is not one behavior. It is stop, or stop and pick up the correction.

HOST:
And stop is not instant. The call returns when the interruption is accepted. Cleanup settles afterwards, and publishes a terminal event. A client that treats the reply as finished is racing that event.

CO-HOST:
Which means the client's own actions come back to it as events.

HOST:
Every one of them. The client writes intent, then reconciles from the same stream it was already watching. That is the whole contract of the surface.

CO-HOST:
So the client never gets a final answer from its own call.

HOST:
It gets an acknowledgement. The outcome arrives as an event, like everything else.

CO-HOST:
Then let us read the contract that makes it possible.

## 8. The artifact

HOST:
The project writes a contract on the durable side of the bus. Here it is, word for word.

HOST:
"Durable, ordered per aggregate log read. Follow false completes at the end of the log. Follow true replays, then transitions to live. Both modes emit one synced marker at the captured replay watermark."

[production note: the source names a code field where these words say "follow". The companion carries the source line exactly.]

CO-HOST:
Per aggregate. Why does the ordering stop at the aggregate?

HOST:
Because the log is not one global queue. It is one ordered history per session. That is enough for a client, because a client renders one session. And it is enough for a projector, because a projector folds one session's events into that session's tables. Ordering per aggregate is the smallest promise that makes replay correct.

CO-HOST:
And the envelope.

HOST:
Three fields. The aggregate, the sequence, and the version. The aggregate says which history. The sequence says where in that history. The version says which shape the data had when it was written, so a reader from a later build can still decode an older event.

CO-HOST:
And the marker.

HOST:
The marker is the handover between replay and live. It is also the thing that stops a client from re-asking for the same range forever.

CO-HOST:
Which is the bug you only see under a flaky network.

HOST:
It is the one the marker was written for.

HOST:
The other half of the idea is the manifest. The schema layer keeps an inventory of event definitions, and the public list filters out the internal and replay-only events. So a client does not merely decline to use those events. It cannot decode them.

CO-HOST:
So the envelope is how a fact is stored, and the manifest is which facts a client is allowed to see.

HOST:
And the live channel is the part with no promise at all. That is the whole design in three pieces.

## 9. Recap

HOST:
Where we landed. One. One publish feeds the projectors inside the transaction, and the live feed after it.

CO-HOST:
Two. Durable events carry an envelope and are the replayable boundary. Stream fragments are hints, and the ending event is the value.

HOST:
Three. The feed is allowed to fail a slow client, and the log read is the catch-up path.

CO-HOST:
Say the rule.

HOST:
Persist the facts, stream the hints, and let the transport be disposable.

CO-HOST:
And three older rules are still holding the floor. Record the fact before anyone acts. Continuation is read from the record. And one execution per session.

HOST:
Which is the same rule every time, said at a different scale. Write down what you are about to rely on.
