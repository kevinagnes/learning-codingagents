## 4. Body beat 1 — Admission is not delivery

HOST:
Here is the claim. Sending a message and showing it to the model are the same act.

CO-HOST:
That is how every chat app feels. You press send, it appears, and the assistant starts thinking.

HOST:
Feels, yes. And it is wrong in a way that costs you twice. Once when the process dies, and once when a client retries.

CO-HOST:
Take the crash first.

HOST:
The user sends a correction while a tool runs. Your code accepts it, puts it in an array, and waits. The process is killed. The array is gone. The user watched that message land, and the model never saw it.

CO-HOST:
And nothing anywhere says the work existed.

HOST:
Nothing. And nobody can reconstruct the disagreement, because the only copy lived in a process that is gone.

CO-HOST:
Now the retry.

HOST:
The client sends again after a network blip. Your code admits the same message twice. The model answers twice, and the second answer is to a question it already handled.

CO-HOST:
So one failure loses work, and the other duplicates it. Those need different fixes.

HOST:
They have one cause. Acceptance and delivery were the same step. So the design splits them. Admission records that work exists. Delivery turns that work into something the model can see.

CO-HOST:
Different writes.

HOST:
Different transactions, and different times.

CO-HOST:
Walk me through the row. What does admission actually write?

HOST:
One event, saying an inbox item was enqueued. Its projection inserts one row into the session inbox table, keyed by session and by the sequence number of the admission. A kind, a payload, a delivery mode, and a number that says where it sits in line.

CO-HOST:
A number, not a timestamp.

HOST:
A sequence number, from the same counter as everything else. Two items in the same millisecond still have an order, and that order decides what may be promoted later.

CO-HOST:
Why a counter? You already have clocks.

HOST:
Because two writes can share a millisecond, and clocks can move backwards. A counter gives a total order with no clock in it.

CO-HOST:
Then what turns the row into a message?

HOST:
A separate act. Admission ends by waking execution, and a failed wake costs a delay, not a message. Later, delivery deletes the row and inserts the message in the same event's transaction. One write to each table, atomically.

CO-HOST:
Why not skip the row and write the message?

HOST:
Because between acceptance and delivery, three things can still happen. You can change the mode. You can cancel. Or the process can die, and the next boot finds the row and knows the work was accepted.

CO-HOST:
And without the row, the transcript would show a message the model has not seen.

HOST:
A reader would draw the wrong conclusion about what the agent knows. The screen would be ahead of the truth.

CO-HOST:
So pending-only.

HOST:
A row exists only while the work is unconsumed. No delivered status to clean up, no join to keep in sync, no reader filtering by status. What is waiting is a plain read of a small table.

CO-HOST:
And nothing needs cleaning up, because there is nothing left to clean.

CO-HOST:
And a status column would work, and then grow forever.

HOST:
It works. It leaves a table that only grows.

CO-HOST:
Here is what I do not buy. A correction typed mid-answer is still a message. You have invented a second noun for one thing the user thinks of as one act.

HOST:
The user thinks of one act. The machine has two, and the second one can fail on its own.

CO-HOST:
So the noun is the failure boundary.

CO-HOST:
What if the client retries the send?

HOST:
Admission reconciles on the message identifier before it prepares anything. If that identifier is already admitted, the retry gets the existing item back.

CO-HOST:
So the rule for this beat.

HOST:
Admitting work is not executing it. One records that something is owed. The other pays it.

## 5. Body beat 2 — Two modes, one field

HOST:
Second claim. The delivery mode is a property of the message.

CO-HOST:
Meaning if I marked something as a steer, it stays a steer.

HOST:
It does not. The mode is a property of the pending row, and the row can be changed while it waits.

CO-HOST:
Give me the case.

HOST:
You watch the agent work and type a note. You meant a correction, so it arrives as a steer. Then you read what it is doing and decide the note is a new task. Between admission and delivery, you flip the mode to queued. Nothing is lost and nothing is resent.

CO-HOST:
And the other direction?

HOST:
You line up three tasks while the session is idle, then decide the first should shape the current answer. You flip it to steer, and it is heard at the next boundary.

CO-HOST:
So these are not tones of voice.

HOST:
They are a routing decision, made later than the message. Bake steer into the message and you have decided at the wrong moment.

CO-HOST:
Why would anyone bake it in?

HOST:
Because the message is what you already have. A field on the pending row looks like duplication, until the first user changes their mind. Then it is the only place the answer can live.

HOST:
Now the definitions. Steer is input that should influence work already in progress. It is delivered at the next safe step boundary. Queue is input that should start new work. It is delivered only when the session would otherwise go idle.

CO-HOST:
Who chooses the default?

HOST:
A prompt steers by default. Queued is the opt-in. That matches most typing. If you watch an agent and type, you are usually trying to change the thing in front of you.

CO-HOST:
I want to push on that. If steer is the default, then a user who wants to line up three tasks has to know a word most interfaces never show them.

HOST:
They do, and that is a real cost. The mode is visible on the pending item and changeable until delivery. A wrong guess is recoverable while the work waits.

CO-HOST:
Unless it is delivered before they look.

HOST:
Then the correction is a second message. That is a product problem, not a durability problem. The split at least makes it fixable.

CO-HOST:
What happens if I try to change the mode of something already delivered?

HOST:
Nothing. The row is gone. A change targets a pending item, and only a pending item has a mode left to flip.

CO-HOST:
So the field has the lifetime of the row.

HOST:
Exactly the lifetime of the row. That is why it belongs on the row and not on the message.

CO-HOST:
And the four kinds are not a taxonomy for the user. They are a taxonomy for the runner.

HOST:
One more thing about what an item can be. Not only text. The inbox holds four kinds. A user message. A synthetic message, which is the system speaking as if it were the user. A compaction. And a move.

CO-HOST:
Compaction and move are not things a user typed.

HOST:
No. They are things the runner must do, and they travel in the same line. We come back to them.

CO-HOST:
Before that. Two modes, four kinds. Do the kinds interact with the modes?

HOST:
They do, and that is the next beat. A control is a kind, and its mode decides whether it waits or interrupts.

CO-HOST:
Here is my worry. Four kinds in one queue means a control can be mistaken for a message. Why not a separate channel for controls?

HOST:
Because the order between them is the whole problem. A control arriving on a second channel would need its own ordering rules, and those rules would disagree with this one.

CO-HOST:
So one line, two lanes, and controls that are not messages but still wait in it.

HOST:
So, the takeaway. Steer changes work in progress. Queued work starts new work.

## 6. Body beat 3 — The boundary decides

HOST:
Third claim. When the runner is free, it takes the next thing in line.

CO-HOST:
First in, first out. That sounds fair.

HOST:
It is fair and it is wrong. The line has two lanes, and which lane may move depends on where the runner is standing.

CO-HOST:
Give me the failure.

HOST:
You queue two tasks while the agent is mid-answer. Say promotion ignored scope and took the oldest item regardless. Now the second task lands in the middle of a live answer. The model has two jobs in one step, and the user gets an answer that is about neither.

CO-HOST:
And the first task is not even done.

HOST:
It is half done, and the model has been told to start something else. The transcript reads like two conversations interleaved.

HOST:
So promotion takes a scope. At a step boundary in the middle of work, the scope is steer. It may take steered rows. It will not take a queued row, even if that row is older.

CO-HOST:
And at the end?

HOST:
At the idle boundary, the scope is input. Exactly one queued item may be promoted. One. Then any steers that arrived while that was happening are promoted after it, in their own order.

CO-HOST:
Why exactly one?

HOST:
Because the session is about to become busy again. One new task is a fresh start. Three at once is a pile, and the model will treat the pile as one instruction.

CO-HOST:
What if someone queues a task and then steers a correction while it is being promoted?

HOST:
The steers that arrived during promotion are taken after it, in order. They were meant to shape the work that started.

CO-HOST:
And the queued item is not stuck forever. It is stuck until this turn ends.

CO-HOST:
That is a narrow window. Arrive a moment later and you are in the next turn.

HOST:
You are. And that is honest. A correction that arrives after the new work started is a correction to that work.

HOST:
There is a cheaper version of this rule. A drain first asks whether anything is promotable. If nothing is, it returns without calling the model. An idle session costs one small read.

CO-HOST:
And if the only thing waiting is a queued task, and the drain's scope is steer?

HOST:
Then it returns complete and leaves the row where it is. That check is the thing that stops a queued task from leaking into a busy turn. One condition, in one place.

CO-HOST:
I keep expecting a scheduler with priorities. This sounds more like a guard clause.

HOST:
It is a guard clause. A scheduler would have to know the agent's state. This only has to know what kind of boundary it is.

CO-HOST:
But a guard clause that reads the boundary is still a scheduler with a different name.

HOST:
It asks one question at one point. It does not rank work. It asks whether this boundary may deliver this kind of item.

CO-HOST:
So the rule is narrower than fairness. It is a permission, checked at a boundary.

CO-HOST:
Here is my push. You keep saying the boundary decides. But the user does not see a boundary. They see a send button.

HOST:
So the interface has to explain it, or the user feels a delay they cannot account for. The design gives you something truthful to show. That item is waiting for a stopping point.

CO-HOST:
And if they cannot wait?

HOST:
Then they steer. That is what the other mode is for. The user is not choosing a queue position. They are choosing whether the current work should change.

CO-HOST:
Which means the interface has to teach two words.

HOST:
It has to teach two words, or pick one and let the user change it later.

HOST:
The takeaway. Arrival order does not decide delivery. The boundary does.

## 7. Body beat 4 — Controls, and a table that forgets

HOST:
Fourth claim. The inbox keeps what you sent, in the order you sent it, until it is delivered.

CO-HOST:
That is the promise of a queue.

HOST:
Two parts are false. The order is not always yours, and the keeping stops at delivery.

CO-HOST:
Start with the order.

HOST:
You steer a compaction, then two corrections. Compaction replaces older history with a summary plus a recent window. In pure arrival order, your corrections would be delivered first and then summarized into the checkpoint. The text you typed would survive as a paraphrase.

CO-HOST:
Instead?

HOST:
The steered compaction is pulled ahead of the earlier steers. It is applied first, and then the corrections are delivered, so they sit verbatim after the checkpoint instead of inside its summary.

CO-HOST:
So one control can jump the line.

HOST:
One control, in one direction, for one reason. A comment in the code says exactly this, because someone reasoned about it once.

CO-HOST:
So the order is not a promise to the user. It is a consequence of what is safe to apply next.

CO-HOST:
What would break if the comment were ignored?

HOST:
Your correction would arrive as a sentence inside a summary of a sentence. The model would read a paraphrase, and paraphrased instructions drift. You typed it to be exact.

CO-HOST:
And the other control?

HOST:
A move changes the working directory. Nothing may be pulled across it. A summary built for one directory is wrong for the next. Promotion stops, the runner handles it, and the line resumes.

CO-HOST:
What does handling it mean?

HOST:
It changes where the session's services live, which belongs to a later episode. What matters here is that the inbox refuses to deliver across the boundary.

CO-HOST:
So a move outranks everything. A move is a context switch. Everything queued was written for the old directory.

HOST:
So old intent is never applied to new ground.

HOST:
Now the second false part. The keeping stops at delivery.

CO-HOST:
Because the row is deleted.

HOST:
Because the row is deleted, in the same transaction that inserts the message. The table is a holding area, not a log. History is the log.

CO-HOST:
So what happens if I cancel a row, and then something tries to deliver it?

HOST:
Delivery fails with a lifecycle conflict. Not an empty message, not a silent skip. A row that is gone means somebody changed their mind.

CO-HOST:
And if the head of the line is a control?

HOST:
Promotion returns nothing, and says so. The runner handles the control before any prompt is delivered. That is why promotion returns a count or an absence.

CO-HOST:
I pushed on the default earlier, so let me push on this. Deleting the row means you cannot audit what someone queued and then cancelled.

HOST:
You can. Cancelling is an event. The admission is an event. You cannot ask the inbox table what happened last week, because that is not its job. Events are the audit trail.

CO-HOST:
A short-lived table is a strange thing to defend. It is the part I would have got wrong.

CO-HOST:
Which is the same shape as the last episode.

HOST:
It is. Minimal facts in the log, and a read model shaped for the question you actually ask. The inbox is a read model of unfinished business.

CO-HOST:
Then let me say the shape back to you. Pending work is a row. History is a row. The inbox is the short-lived one.

HOST:
And the short life is the feature. A table that only holds what is owed cannot disagree with history.

CO-HOST:
One more. If the table is pending-only, why does it need an index at all? It must be tiny.

HOST:
It is tiny per session, and there are many sessions. The index is on session, mode, and position, so the question is still one lookup.

HOST:
Takeaway. Controls travel in the same line, and a delivered row is gone.

## 8. The artifact

HOST:
The artifact today is not a prompt. It is the pair of definitions the whole episode hangs on. Here they are, word for word.

HOST:
"Steer. Input that should influence work already in progress. It is delivered at the next safe step boundary. Prompts steer by default. Queue. Input that should start new work. It is delivered only when the session would otherwise go idle."

[production note: the source writes these as two labelled definitions in a bulleted list. The read speaks the labels as sentences and changes nothing else. The companion carries the original formatting and the stored field.]

CO-HOST:
Two sentences of routing, and one sentence of default.

HOST:
And the default is the asymmetric part. Read them again and notice that neither definition mentions what the input contains. Steer and queue are not kinds of message. They are answers to the question, when may this be heard.

CO-HOST:
The first one says the next safe step boundary. The second says the session would otherwise go idle.

HOST:
That is the entire mechanism, stated in the definition. A step boundary is a place where the model is between calls. Idle is a place where there is no next call yet. One names a moment inside work. The other names the moment work would stop.

CO-HOST:
Why safe in the first one?

HOST:
Because a boundary is also where a compaction or a move may be waiting. Safe means the runner has finished settling the step it ran, and has not started the next one. Delivering into the middle of a step would change the request after it was built.

CO-HOST:
And the default sentence is the only place the word prompt appears.

HOST:
Which is the asymmetry. A prompt is a person typing. Synthetic input, a compaction, a move, none of them inherit the default by accident. The default is written for the one case where a human guessed.

CO-HOST:
So the vocabulary is doing design work.

HOST:
The vocabulary is the design. Two words, one stored field, one scope check, and a table that holds only what is still owed.

## 9. Recap

HOST:
Where we landed. One. Admitting work records that it exists. Delivery deletes the pending row and inserts the visible message, in one transaction.

CO-HOST:
Two. Steer influences work in progress at the next safe step boundary. Queued work starts new work only when the session would otherwise go idle.

HOST:
Three. Controls share the line and interrupt it. A compaction may jump ahead of earlier steers. Nothing crosses a move. And the table never holds a delivered row.

CO-HOST:
Which leaves the inbox empty most of the time, and holding exactly the work that is still owed.

HOST:
Say the rule.

CO-HOST:
Admission is not execution.
