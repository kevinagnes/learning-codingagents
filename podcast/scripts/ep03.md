## 4. Body beat 1 — A session is a log, not a row

HOST:
Here is the claim. A session is a row you keep up to date with the latest state.

CO-HOST:
That is how I would build it. One row. Current model, current agent, current transcript. Update it as things happen.

HOST:
Then answer a simple question after a crash. Did the model finish the last step, or did it never start?

CO-HOST:
You would look at the row.

HOST:
And the row says the session is busy. It cannot tell you whether the model answered, whether the tool ran, or whether the process died in between. You overwrote the evidence with the latest summary of it.

CO-HOST:
So keep a history instead.

HOST:
Keep a log. One durable entry per thing that happened, appended in order. Never a document you rewrite.

CO-HOST:
What makes the order trustworthy? Timestamps are right there.

HOST:
Clocks move backwards. Two writes can share a millisecond. A replay must produce the same order every time, and a wall clock cannot promise that. So each session keeps a counter, and every entry gets the next number.

CO-HOST:
And you read by that number, never by time.

HOST:
Time is for display and range queries. The counter is the order. That is the same idea as the sequence number on an event, one level up.

CO-HOST:
Is the number contiguous? One, two, three, with no holes?

HOST:
Not necessarily. Events that produce no message still consume a number. The only promise is that it increases, and that the pair of session and number is unique.

CO-HOST:
So a gap is not a missing entry.

HOST:
A gap is an event that produced no message. Reading by number still gives you a total order.

CO-HOST:
What about the entries themselves? Is a message one block of text?

HOST:
Every entry is tagged. A user entry. An assistant entry. A synthetic entry, which is the system speaking as if it were the user. A system entry, which is an instruction update. A skill entry. A shell entry for a command that ran.

CO-HOST:
That is a lot of types.

HOST:
There are more. A compaction entry, which replaces older history with a summary. Switch markers for the agent, the model, and the working directory. And an idle entry, which marks that a stretch of work ended and why.

CO-HOST:
Why is idle an entry? That feels like a status field.

HOST:
Because a status field tells you the session is idle now. An entry tells you when it became idle, and what happened before. A stretch of work is everything since the last idle entry. That definition survives a restart. A boolean does not.

CO-HOST:
And the assistant entry is the exception, isn't it?

HOST:
It is the one entry updated in place. Its text arrives in fragments, its tool calls move from streaming to running to done, and its completion time is empty until the step settles. Everything else is append-only.

CO-HOST:
Why allow one mutable entry?

HOST:
The alternative is a new entry for every fragment. That is many more rows, and a harder job for everything that reads them. One entry that settles is the cheaper shape, as long as the read path knows it may be in flight.

CO-HOST:
And what does settles mean?

HOST:
It means the step has a completion time. Until then, the entry is a promise, not a fact.

CO-HOST:
Which comes back later.

HOST:
It does. One more distinction. A durable entry is not a provider message. One assistant entry can carry text, reasoning, and several tool calls. Lowering it can produce several provider messages. The log is yours. The wire shape is built later.

CO-HOST:
So the log is the truth, and the provider message is a translation.

HOST:
The log is the truth. History is a log, and its order is a number, not a clock.

## 5. Body beat 2 — One transaction, or the store disagrees with itself

HOST:
Here is the claim. Recording an event and updating the view that reads it are two writes, so do them in that order and move on.

CO-HOST:
That is what a service layer does. Write the event, then update the table.

HOST:
Then the process dies between the two writes. The event exists and the view does not. Or the view exists and the event does not.

CO-HOST:
Give me the concrete version.

HOST:
A user sends a message. One part of the system needs to schedule work. Another needs to insert the row the transcript reads. A third needs to tell connected clients the message exists. Three writes. A crash between them leaves work admitted with no message, or a message no client ever saw.

CO-HOST:
So the fix is one transaction.

HOST:
One transaction, one ordered event, and a set of handlers that run inside it. The bus takes a lock for the session, reads the latest sequence number, computes the next one, runs every handler registered for that event type, advances the stored sequence, and only then notifies the subscribers who are connected.

CO-HOST:
So by the time anyone can observe the event, the view is already consistent with it.

HOST:
That is the property. When the transaction commits, the read model is not catching up. It is done.

CO-HOST:
So there is no separate flush step, and no window where a reader sees half a write.

CO-HOST:
What are those handlers called?

HOST:
Projectors. A projector subscribes to one event type and folds it into a read model. The message list is a read model. Usage counters are a read model. Instruction state is a read model. They are shaped for queries, not for recording history.

CO-HOST:
And the subscribers who are connected now?

HOST:
They are a volatile channel. They are notified after the commit, and a client that reconnects replays from the durable log. Write first, notify second. If you notify first, a client can ask for a fact that does not exist yet.

CO-HOST:
Why keep a raw event row at all, if the projections are what you query?

HOST:
For replay and export. The projections answer today's questions. The raw log lets you build a new projection tomorrow, and it lets a follower catch up.

CO-HOST:
And the raw row is written before anyone is notified.

HOST:
Inside the same transaction, before the commit. Subscribers are a channel, not a log.

HOST:
There is one more thing inside that transaction. A local commit hook, which runs before the sequence advances. The execution claim is written there, so a session cannot be marked busy without the event that says it started.

CO-HOST:
So the same transaction carries the bookkeeping that recovery depends on.

HOST:
One transaction, one moment, no window.

CO-HOST:
Which is also why the projectors cannot call the network.

CO-HOST:
What about the same event arriving twice?

HOST:
Then recording it has to be a no-op the second time. The bus compares the incoming event with what is stored at that sequence. Same bytes, same event, ignore it. Different bytes at the same sequence, fail loudly.

CO-HOST:
Why fail? A silent overwrite would be easier.

HOST:
Because then history changes between restarts, and every number anyone computed from it becomes a guess. A replay that diverges is a defect, and the system should say so.

CO-HOST:
I want to push on the cost. One transaction means the handlers hold the write lock. That is a bottleneck.

HOST:
It is, and it is deliberate. The handlers are kept to bounded database work. No remote calls inside a projector. The moment a projector waits on the network, it holds every write for that session while it waits.

CO-HOST:
So the rule is not one transaction at any price. It is one transaction, and keep the work inside it small.

HOST:
Exactly. The fact and the view commit together, or the store can disagree with itself.

## 6. Body beat 3 — Minimal events, richer views

HOST:
Here is the claim. A durable event should carry everything a reader will need, so nobody has to look anything up.

CO-HOST:
That is denormalization. You do it so reads are cheap.

HOST:
It is a trade, and this version of it is wrong in a specific way. The question is which side pays. If the event carries the derived state, the log pays forever. If the projection computes it, the log stays small and the view pays once.

CO-HOST:
So the event is not a cache of the view.

HOST:
Consider a model switch. The event says the session now uses a new model. A reader later wants to show what it switched from.

CO-HOST:
So put the previous model in the event.

HOST:
Now two switches happen in quick succession. The second event's idea of previous was computed when it was emitted. If a concurrent change landed in between, the event carries a value that was never true at the moment it was recorded.

CO-HOST:
And two consumers can disagree about the same history.

HOST:
They can. So the event names the new model, and the projector fills in the previous value inside the transaction.

CO-HOST:
And the previous value is written into the message, so a later reader does not have to fold anything.

HOST:
It is written at projection time. That is the self-contained part.

CO-HOST:
So the view can be complete even when the event is not.

HOST:
That is the counterintuitive part, so here is the person who made it.

EXPERT:
We keep events minimal on purpose. An event records the fact that cannot be derived. Everything a reader needs around that fact is computed when the event is folded.

CO-HOST:
Why not make the event self-contained? Then replay would be simpler.

EXPERT:
Replay would be simpler and the log would be wrong. A self-contained event freezes the context at emit time. When the derived shape changes, you either re-emit old events or you are stuck with a shape you no longer want.

CO-HOST:
So the event is the fact, and the view is the interpretation.

EXPERT:
The view is self-contained. The event is minimal. Those are different goals, and putting both in the event satisfies neither.

HOST:
Thank you. And that is why the enrichment reads another table inside the same transaction. The projection has the database handle. It can see the current model, the current agent, the current directory.

CO-HOST:
Does that not make the projection harder to test?

HOST:
It makes it honest. The projection is where the interpretation lives, so that is where you test it.

CO-HOST:
What is the alternative you rejected?

HOST:
Keeping only the current row, which loses history and replay. Or putting everything a view needs into the event, which bloats the log and couples the event to a presentation that will change. Then every change to a view forces you to re-emit the past.

CO-HOST:
So the version is part of that. Type, aggregate, version.

HOST:
An event is declared with all three, so replay knows which projector to run, and old events keep pointing at the old shape. The log does not need rewriting.

CO-HOST:
What about the size argument? A smaller event is also a smaller log.

HOST:
That is the other payoff. A log full of derived state grows with every field you add to a view. A log of facts grows with the facts.

CO-HOST:
So a reader never has to reconstruct the world.

HOST:
The projection does that work once, and the view carries the result. Record the fact, compute the context, and let the view be the thing that is complete.

## 7. Body beat 4 — Reading it back

HOST:
Here is the claim. The transcript on your screen is the session history, and the model sees the same thing you do.

CO-HOST:
That is the point of a transcript. What else would it be?

HOST:
A view with rules. The first rule is the compaction boundary. When older history is replaced by a summary, the model no longer sees the old messages. So a reader should not show them either.

CO-HOST:
So the screen starts at the summary.

HOST:
The screen starts at the latest completed compaction. Earlier rows still exist in the log. They are not what the model is acting on.

CO-HOST:
What about a compaction that holds the provider's own opaque window instead of text?

HOST:
That is a native checkpoint. It is only replayable by a compatible model. So the read path takes a boundary parameter. A model-neutral reader and a specific-model reader can disagree, and both can be right.

CO-HOST:
That is a strange sentence.

HOST:
It is the honest one. The boundary is part of the read, not a global setting.

CO-HOST:
So two clients can show different transcripts of the same session, and neither is lying.

HOST:
Neither is lying, because each asked for a different boundary.

HOST:
The second rule is the settled prefix. An assistant entry that is still in flight may contain a tool call with no result yet. A preview must not render that as final.

CO-HOST:
So the screen stops before it.

HOST:
The screen stops at the first assistant entry with no completion time. The model's own read does not stop. The model needs the whole log to continue, including the unresolved call it is about to finish.

CO-HOST:
So preview and model input are different reads of the same log.

HOST:
Different reads, same log, different rules. That is the pattern for the whole episode.

CO-HOST:
Which one does the runner use?

HOST:
The runner reads the full log, without the preview cut. The preview is for people.

HOST:
The third rule is accounting. Usage is not recomputed by asking the provider again. It is recorded on the event that produced it, and folded into counters on the session.

CO-HOST:
And after a compaction, the transcript no longer contains those old steps. Do the numbers vanish?

HOST:
They do not, because the counters were folded when the events happened, and the usage events are durable in their own right. The dashboard and the transcript can disagree about what is visible. They must not disagree about what was spent.

CO-HOST:
So the dashboard is not derived from the transcript.

HOST:
It is derived from the events and the message rows, which is why a compaction cannot erase the spend.

CO-HOST:
I want to push on replay. If a projection is enriched with state from the moment it ran, is replay actually deterministic?

HOST:
Not from the event alone. That is why the enrichment is recorded in the view. The previous value is written down. Replay reads the log, and the read model carries the context it was built with.

CO-HOST:
So the log is the source of truth, but the view is allowed to remember.

HOST:
The view must remember what it computed, or replay would produce a different answer.

CO-HOST:
And a client that reconnects?

HOST:
It replays the durable log and then follows the events as they arrive. The handoff is marked once, with a sequence number, so the client knows exactly where replay ended and the stream began. No gap, no duplicate.

CO-HOST:
And that marker is the only thing that tells it where the two meet.

HOST:
One marker, carrying a sequence number. It is the boundary between what was written and what is happening.

CO-HOST:
That is the takeaway, then. The log is one, the views are several, and each view has a rule.

HOST:
And the rule is written at the top of the system, not buried in a reader.

## 8. The artifact

HOST:
The artifact today is a rule, not a prompt. Here it is, word for word.

HOST:
"Keep durable events minimal: record irreducible new facts and do not repeat state derivable by folding the ordered aggregate history. Enrich projections and read models with previous or derived state when consumers need self-contained views."

[production note: the source is the repository's own contributor rule for session core. The companion carries the line and its location.]

CO-HOST:
That is dense.

HOST:
It is one rule doing three jobs. First, what goes in the event. Irreducible new facts. Second, what stays out. Anything you can get by folding the history. Third, where the missing context goes. Into the projection and the read model.

CO-HOST:
What does irreducible mean here?

HOST:
It means you cannot get it back by folding. A count of messages is derivable. The fact that a message was admitted is not.

CO-HOST:
So the event is the smallest thing that would be lost otherwise.

HOST:
The smallest thing that would be lost, and the only thing that must never be guessed.

CO-HOST:
Ordered aggregate history. Say that in English.

HOST:
The aggregate is the session. Ordered means by sequence number. So the phrase means the session's log, read in order. If you can compute it from that log, it does not belong in the event.

CO-HOST:
And self-contained views is the concession.

HOST:
It is. The event is minimal, but the reader should not have to reconstruct the world. The projection does that work once, and the view carries the result.

CO-HOST:
So the rule is not store less. It is store each thing once, in the right place.

HOST:
That is the whole design in one sentence. The event records the fact. The projection records the interpretation. The view is what a consumer reads.

CO-HOST:
Which is why the event and the view commit together.

HOST:
Which is why they cannot drift apart.
