## 4. Body beat 1 — Identity is a hash

HOST:
An instruction is not text. It is a value with a name, and the text is only one of the ways that value can be rendered.

CO-HOST:
That sounds like a distinction without a difference. A rules file is a file.

HOST:
Then someone edits twenty lines of it. On the next step the model does not receive the whole file again. It receives a short note, or a diff. And the thing the session wrote down is a fingerprint, not the text. So where did the text go?

CO-HOST:
Right. That is the part I cannot reconstruct.

HOST:
Start with the shape of a source. A source has a stable key, a way to read its current value, and three renderers. One for the first time the model sees it. One for a later change. One for removal.

CO-HOST:
Three renderers for one value. Why not render it when you need it?

HOST:
Because the value is not stored as text. It is canonicalized first. Object keys are sorted and whitespace is made unambiguous, so two values that mean the same thing produce the same bytes. Then those bytes are hashed. The hash is the identity of the value.

CO-HOST:
So the event carries a hash. That is a pointer, and pointers go stale.

HOST:
The value goes into a blob store, keyed by that hash. And here is the part that looks wrong, so here is the person who made it.

EXPERT:
We keep identity in the event and the payload once, by identity. The hash is what lets us compare a source to what we last saw. The blob is what lets a resumed session rebuild the text without the original file still being there.

CO-HOST:
Why not put the text in the event and skip the indirection?

EXPERT:
Then two sessions with the same rules file store it twice. The blob insert ignores duplicates, so the same value costs one row, and the event stays small while the value is still recoverable.

CO-HOST:
So the delta is two hashes per key. Cheap, but it does not say what changed.

HOST:
The delta is a change list, not a description. The text comes from the renderer, which reads the new blob. For each source, read the value, hash it, and compare that hash to the one stored for that key. Unchanged sources are skipped. A changed source produces a delta entry that maps the key to the new hash. A removed source produces a tombstone. The new values ride along in a map keyed by hash.

CO-HOST:
So on a quiet step, the delta is empty.

HOST:
Empty, and nothing is published. The stored state keeps two maps. One is the baseline for the current epoch. The other is the latest value seen for every key. Hashing happens in one function, so no other part of the system decides identity.

CO-HOST:
So the store grows with distinct values, not with edits.

HOST:
With distinct values. The same bytes from two sessions share one row, and a hundred edits that end in the same text cost one copy.

CO-HOST:
And an old delta still resolves, because its hash still names a row.

HOST:
That is what makes replay possible. The event carries only the identity, and the value is fetched from the store when it is needed.

CO-HOST:
And if the read fails?

HOST:
That is not a change. A temporary failure keeps the stored value. It only blocks the first observation, when there is no stored value to keep.

CO-HOST:
So "I could not read it" and "it is gone" are different facts. One preserves the value, and the other writes a tombstone.

HOST:
It does. And the tombstone tells the model the content no longer applies.

CO-HOST:
Store the value once, name it by its hash, and let the written record carry the name.

## 5. Body beat 2 — Baseline and delta

HOST:
The baseline is sent again at the start of every request. The change is sent once, as a message.

CO-HOST:
Those two sentences sound like they contradict each other.

HOST:
They are the two halves of one design. Every request renders the baseline from the epoch's initial values. That is the instruction part of the system prompt. It is the state of the world as of the start of the epoch.

CO-HOST:
And the delta?

HOST:
When a change is observed, it is rendered and frozen into a durable system message, then appended to history. So the model reads "this changed" at the point in the conversation where it changed. It does not read the whole file again.

CO-HOST:
Why freeze the text? You have the value in a blob. Render it when you need it.

HOST:
Because the sources that produced it are scoped to a directory, and a resumed process may not have them. Re-rendering later could show text the model never actually saw. So the rendered update is written down at the moment it is observed.

CO-HOST:
That is the honest account.

HOST:
It is the only written trace that survives a restart. The baseline can be rebuilt from blobs. The update cannot, because a source is a fact about a location at a moment.

CO-HOST:
So the baseline is reconstructed, and the update is remembered.

HOST:
Exactly. And that is why an epoch exists. A checkpoint supersedes the chronological updates that came before it. When it completes, the current values become the new baseline, and history selection drops the update messages the baseline now covers.

CO-HOST:
So a checkpoint is also a clean slate for instructions.

HOST:
A clean slate that carries the present forward. The old updates are no longer needed, because the baseline already contains their result.

CO-HOST:
Let me push on the cost. You render the whole baseline on every request. That is the expensive part, and you do it every time.

HOST:
It is also the part that does not change between requests. That is exactly what the cache wants.

CO-HOST:
But if you sent only deltas, a resumed session would start with no instructions at all.

HOST:
Right. And if you restated the file inside history on every edit, the cache prefix would move and the transcript would fill with copies.

CO-HOST:
So the stable thing is repeated, and the changing thing is said once.

HOST:
The baseline is the state of the world. The delta is the story of how it got there. They belong in different places.

CO-HOST:
What about the empty case? A project deletes its rules file.

HOST:
The source reads an empty set. That maps to a removal, not to silence. A session that previously had instructions learns that they are gone, which is different from never having had any.

CO-HOST:
And if the first read fails before there is any state?

HOST:
Initialization is blocked. Seeding an empty baseline would let the model work from an empty instruction set forever, because unchanged keys are skipped and the missing value never comes back.

CO-HOST:
So a hole at the start is worse than a wait.

HOST:
A hole at the start is permanent. A wait is one step.

CO-HOST:
Let me try the other direction. Why not skip the baseline and put one big instruction message at the start of each execution? Then it is history, and the cache never sees it.

HOST:
Then every resumed process has to reconstruct that message, and it sits in the middle of history, where an edit can change text the model already saw. The baseline is a request-time fact. History is a committed fact. Mixing them makes replay lie.

CO-HOST:
So the split is about when it is rendered, not about size.

HOST:
It is about whether it is safe to render again.

CO-HOST:
Repeat the baseline, say the change once, and freeze the change where it happened.

## 6. Body beat 3 — Discovery

HOST:
There is one rules file, and you already know where it is.

CO-HOST:
False. I have four, and one of them is in a directory I forgot existed.

HOST:
That is the normal case. So discovery is not one lookup. It is four routes that converge on a single source.

CO-HOST:
Give me the routes.

HOST:
One. A global file in the global config directory, loaded once. Two. A walk from the current directory up to the project root, or the home directory, collecting every rules file on the way.

CO-HOST:
Order matters there.

HOST:
It is the render order. Global first, then project files from nearest to farthest. Three. The configured list. Globs, absolute paths, home-relative paths, and web addresses. A relative pattern searches upward from the location to the project root. A web address is fetched once when the config loads, and keeps its last good copy if a fetch fails.

CO-HOST:
And four?

HOST:
The read tool. After it successfully reads a file or lists a directory, it walks upward from that path for rules files below the project root, and injects the ones the session has not seen.

CO-HOST:
So opening a helper module three directories deep can add instructions nobody configured.

HOST:
Once. That is the hard part. It has to enter exactly once, not every time you touch that directory.

CO-HOST:
How do you remember?

HOST:
The injected message carries a ledger in its metadata, listing the paths it brought in. Before injecting, the loader reads that metadata from the model-visible history and skips paths already there. An in-flight claim covers two reads racing in the same step.

CO-HOST:
Why read the ledger from history instead of keeping a set in memory?

HOST:
Because compaction and revert can drop the message. If the ledger lived only in memory, the path would be gone for the rest of the session with no way back. Reading history means a path that falls out is discovered again.

CO-HOST:
That is a nice property. What happens when a file changes?

HOST:
The source re-reads on watcher events, debounced so a burst of saves becomes one rescan. Then the update renderer compares per file. A removed file says its instructions no longer apply. An added file says new instructions apply from that path. A changed file gets a unified diff, unless the diff would be longer than the new text, in which case it restates the file.

CO-HOST:
Why prefer a diff at all? Text is simpler.

HOST:
Because a one-line change should cost one line. But a large structural change reads better as the new file, so the renderer picks whichever is shorter.

CO-HOST:
So the renderer decides how much to say, not how much to store.

HOST:
The store keeps the full value. The renderer decides what the model needs to read right now.

CO-HOST:
And all of it is one source?

HOST:
One source for instruction files. The discovery object holds file contents in memory by path, and the insertion order of that map is the render order. There is also a separate, smaller source for references. External directories the model may consult, each with a name and a description. A reference with no description is filtered out, because a name alone tells the model nothing about when to look.

CO-HOST:
So the reference list has the same shape, minus the file.

HOST:
Same shape, smaller. A list of directories, sorted by name, each with a description that says when to look there.

CO-HOST:
Why not collapse all of it into one flat instructions blob?

HOST:
Because you lose per-file identity. A delta needs to say which file changed. And a change needs to be attributable to a path when you read the transcript next week.

CO-HOST:
So the path is the key in both directions. Discover by path, remember by path, and let the history be the ledger.

## 7. Body beat 4 — Skills and external servers

HOST:
A catalog of capabilities costs the same whether it holds one skill or a hundred.

CO-HOST:
That cannot be true. A hundred skills, each several pages long, is a hundred pages of prompt.

HOST:
Only if you paste the bodies. The prompt holds the catalog. For each skill, an id, a name, and one sentence of description. The body waits for a tool call.

CO-HOST:
So the model shops from a list.

HOST:
It does. And the list is filtered before the model ever sees it. A skill is advertised only if it has a description, is not opted out of automatic use, and is not denied by permission for its id. The list is sorted by id, so its bytes are stable.

CO-HOST:
What happens when the model picks one?

HOST:
It calls the skill tool with the id. The tool checks permission, then prepares the skill. That means reading the body, recording the base directory that relative paths resolve against, and sampling the skill's files, up to ten, excluding the entry file. The result is a skill content block, returned as an ordinary tool result.

CO-HOST:
Why a tool result and not part of the prompt?

HOST:
Because the model asked for it. The body enters the conversation at the moment it is needed, and nowhere else. The tool also stays on the provider's native tool list, rather than going through the code execution tool. Loading a skill is one known call, and code mode buys it nothing.

CO-HOST:
And when a skill is added or removed?

HOST:
The catalog is an instruction source, so it deltas like one. An addition or a removal renders as a small note. A changed description restates the whole list, because a partially changed catalog is not safely described by a delta. An empty catalog is a removal too, with a line telling the model to stop using anything it saw before.

CO-HOST:
Now the other kind of source. An external server.

HOST:
That is the Model Context Protocol, M C P. A server gives us two things. A block of instructions about how to use it, and a set of tools. The instructions become a source, and the tools become a tool source.

CO-HOST:
And the interesting part is not the block. It is when the block is allowed to exist.

HOST:
Right. A server's instructions are rendered only if the session can actually reach at least one of that server's tools.

CO-HOST:
So a code-mode server needs permission to execute, and a native server needs one allowed tool.

HOST:
Either way, the question is reachability, not configuration.

CO-HOST:
Why be that strict? The notes are harmless.

HOST:
They are not. If the prompt says use this server's search tool, and every one of its tools is denied, the model is being coached into a call that will fail authorization. The prompt created the error. One step wasted, and a failure the user cannot explain.

CO-HOST:
So the instructions and the tools have to agree.

HOST:
They are gated by the same permission evaluation. The block is sorted by server name. In code mode, each server block names the path under which its tools appear in the code catalog, so the model knows to reach them through the execution tool. An empty visible set becomes a removal, so old guidance does not linger.

CO-HOST:
Two sources, one pipeline.

HOST:
Catalog and server instructions are both content-addressed, both delta-rendered, both ordered. The differences are what they advertise, and who is allowed to see them.

CO-HOST:
What happens when a server disconnects mid-session?

HOST:
Its tools leave the snapshot and its block leaves the source. The removal renders like any other change. The model is told the guidance no longer applies, instead of being left with an entry it cannot call.

CO-HOST:
Advertise what the model can reach, and fetch the body only when it asks.

## 8. The artifact

HOST:
The catalog is a short piece of prompt text. Here it is, word for word.

HOST:
"Skills provide specialized instructions and workflows for specific tasks. Use the skill tool to load a skill when a task matches its description. The user may also invoke a skill directly. When that happens, its instructions appear in the conversation as a skill content block, the same shape the skill tool returns. A skill that is already present this way does not need to be invoked again."

[production note: the source writes the block name as markup. The spoken read says "skill content block". The companion carries the exact text.]

CO-HOST:
Three sentences, and the third one is doing something I did not expect. It is the anti-duplicate rule. A user can invoke a skill directly, and the same block is already in the conversation.

HOST:
Without that sentence, the model reads the catalog, decides the task matches, and calls the tool, and the body appears twice.

CO-HOST:
What sits below the sentences?

HOST:
One entry per skill. An id, a name, and a description. That is the whole footprint. No body, no file list, no base directory.

CO-HOST:
So the description is the retrieval key.

HOST:
It is. A vague description is a skill nobody loads. The id is stable, the name is for the model to recognize, and the description is the only thing it has to match a task against.

CO-HOST:
That makes the wording of a description a design decision.

HOST:
The same way a tool description is. The catalog is not documentation. It is an index, and an index with bad entries is worse than no index.

CO-HOST:
And the order?

HOST:
Sorted by id. The catalog sits in the stable part of the prompt, so its bytes have to be the same from request to request. An unsorted list would churn the baseline every time the skill map was rebuilt.

CO-HOST:
A catalog that changes its own cache key. Which is why it is sorted before it is hashed.

HOST:
The same discipline as every other source in this episode.

## 9. Recap

HOST:
Where we landed. One. One model call per step still holds, and each instruction source is canonicalized, hashed, and stored once in content-addressed blobs.

CO-HOST:
Two. The baseline renders on every request, and a change freezes its rendered text into a message at the point it was observed, so a restart cannot rewrite what the model saw.

HOST:
Three. The prompt is still assembled from stable parts in a cache-stable order, and discovery, skills, and external servers are all sources in that pipeline. Each advertises only what the session can reach.

CO-HOST:
And the rule. Track each source by hash, and when it changes send the delta, not the whole baseline again.
