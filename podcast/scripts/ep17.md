## 4. Body beat 1 — The step brackets itself

HOST:
Every step takes a fingerprint of the working tree before it talks to the model, and another one after it finishes.

CO-HOST:
Before and after. That sounds like a backup, and backups are expensive.

HOST:
It is a capture of the working tree at one instant, and what it returns is an identifier, not a copy.

CO-HOST:
So the contents go somewhere else, and the step keeps the address.

HOST:
The contents go into an object store, addressed by their own hash. In opencode that identifier is a Git tree id, branded so it can travel through events and rows as an opaque token.

CO-HOST:
And what breaks if you had stored a patch instead?

HOST:
Two things. First, comparison gets expensive and lossy. Two captures are compared by walking the object graph. Identical content is literally the same object, so an unchanged file costs nothing to prove unchanged.

CO-HOST:
With a patch you would be trusting whitespace and context lines to tell you nothing happened.

HOST:
And second, history stops being self-contained. A hash plus objects can be referenced from an event and interpreted later, with no model and no provider in the room.

CO-HOST:
So the evidence outlives the process that produced it.

HOST:
It outlives the process, the provider, and the model.

CO-HOST:
What did they reject to get there?

HOST:
Three. Diffing against the previous request state, which does not exist until you define it. A filesystem watcher, which is racy, not deterministic, and does not survive a restart. And a full copy of every file per step, which is correct and wasteful. Content addressing deduplicates for free.

CO-HOST:
The watcher rejection is the interesting one, because a watcher is what most people reach for.

HOST:
It fails the same test as the rest. The account of a change has to be reconstructible after a restart. A watcher only knows what it saw.

CO-HOST:
Now the timing. You said the capture happens before the request, and hashing a large tree takes time.

HOST:
So the start capture is forked as a fiber, and the provider request begins immediately. The capture hides behind the time the provider spends thinking.

CO-HOST:
Then there is a window where a tool could write before the capture lands.

HOST:
There is, and the design closes it with one rule. The start snapshot only has to exist before the first local tool runs. A local tool is the only thing that can mutate the tree.

CO-HOST:
So the await is not at the top of the step.

HOST:
It sits at the step's first durable publish. That event carries the snapshot id, and no provider event can be written before it exists. So the capture forks, the request goes out, the snapshot lands, and the step opens.

CO-HOST:
And if the capture fails?

HOST:
It returns nothing, and the step runs anyway. Snapshots are best effort. If they are switched off, or the location is not a Git repository, or the capture throws, the caller proceeds without one. Change tracking is an audit trail, never a precondition.

CO-HOST:
So a failure here is invisible unless the client asks.

HOST:
Which is why absence has to be a value, not an error. The step says it has no snapshot, and nothing else changes.

CO-HOST:
Which brings us back to the boundary. The record can be incomplete.

HOST:
It can. Capture covers the project only. Paths outside the project directory, paths the source repository ignores, and untracked files above a size limit are not in the tree.

CO-HOST:
A size limit on an untracked file. That is a very specific line to draw.

HOST:
It is, and it is there for a reason. A stray multi-gigabyte file in the working tree should not be able to stall a step.

CO-HOST:
So the snapshot is not the filesystem. It is the part of it you agreed to be responsible for.

HOST:
Fingerprint the tree before the first tool can touch it, and compare by identity, not by replay.

## 5. Body beat 2 — Names on the record, patches on demand

HOST:
The step stores two snapshot ids and the list of paths that differ between them. It does not store the patch.

CO-HOST:
That is the part I would get wrong. A diff is what people want. Why not save it?

HOST:
Because it can disagree with the tree, and because it can be enormous. Keep the cheap summary and derive the expensive thing when somebody asks.

CO-HOST:
Walk me through the two operations.

HOST:
One lists changed paths. It walks the two trees and returns project-relative paths, without loading contents or generating patches. That goes on the step, and tells a client how many files to draw.

CO-HOST:
And two.

HOST:
Two generates structured diffs for those paths. For each file, the path, the status, the number of additions and deletions, and the unified patch text.

CO-HOST:
Status being?

HOST:
Added, deleted, or modified. Nothing else. And a context width, which is how many unchanged lines surround each hunk.

CO-HOST:
Which means the patch is a view, not the truth.

HOST:
The trees are the truth. The patch is a rendering of them at a width you choose.

CO-HOST:
So the summary and the patch cannot drift, because the patch is recomputed from the same two trees.

HOST:
They cannot. The trees are immutable, so the same two ids always produce the same patch. A client can cache a diff by its pair of ids and never be wrong.

CO-HOST:
The unchanged case is the one that worries me. Most steps change nothing.

HOST:
And it is free. If the start id and the end id are equal, the file list is empty and the comparison is never run. One equality check on two hashes.

CO-HOST:
Now the record itself. What does a reader actually see?

HOST:
The step's end event carries the end snapshot and the changed paths, both optional. The projector folds the start id, the end id, and the path list onto the assistant message.

CO-HOST:
And "no snapshot" versus "no changes"?

HOST:
That is a real distinction and a classic bug. No snapshot is absent. No changes is an empty list. A client that conflates them shows an empty diff for a session where tracking was switched off.

CO-HOST:
Now the range question. One step is a small unit. What if I want the diff for a whole request?

HOST:
Then you need the range, and the range has a definition. A turn is a range of steps. It opens at the first prompt after the previous idle marker, and closes at the next. So a prompt steered in while the session was busy belongs to the same turn.

CO-HOST:
And the diff compares?

HOST:
The first recorded start snapshot in the range with the last recorded end snapshot in the range.

CO-HOST:
What if the last step is still running?

HOST:
Then the end is the working copy. A client polling for a live diff sees partial progress, and once the step settles the durable end id takes over.

CO-HOST:
That is a nice detail. It means the diff moves while you watch it.

HOST:
And one more boundary. A range that spans a location switch is rejected, not diffed. Trees captured in one location's repository cannot be compared against another's. Guessing would be worse than refusing.

CO-HOST:
Let me push on renames, because that seems like something you would want.

HOST:
You would, and rename detection is off on purpose. A rename then appears as one deleted path and one added path. Undo needs both. If the diff reported only the destination, revert would restore the new path and leave the old one deleted.

CO-HOST:
So the diff is shaped by the undo that comes later.

HOST:
Everything in this part is. And the patch output is bounded by a byte budget, so a generated file with a hundred thousand lines degrades into a truncated marker instead of stalling the screen.

CO-HOST:
So the takeaway. Names on the record, patches on demand.

HOST:
Names on the record, patches recomputed from trees that cannot change.

## 6. Body beat 3 — Undo is three moves

HOST:
Now the undo. And the first thing to say is that it is three operations, not one.

CO-HOST:
A button is a button. Why three?

HOST:
Because users want to preview before they commit, and because one of the three is destructive. Splitting them is what keeps a mistaken boundary recoverable.

CO-HOST:
Go through them.

HOST:
Stage records a boundary and restores the files, but leaves the history alone.

CO-HOST:
So the files move and the conversation does not.

HOST:
Exactly. Stage first captures the current working tree as the original. That is the state to return to if the user changes their mind. Then it works out a restore plan and applies it.

CO-HOST:
So I could stage, look at the tree, and walk away.

HOST:
You could, and the stage survives a restart, because the boundary and the original are stored on the session row.

CO-HOST:
How is the plan built? That is the part I cannot picture.

HOST:
It walks forward from the boundary through the assistant steps. For each file a step touched, it keeps the earliest start snapshot it has seen. That is the state of that file before it was first changed.

CO-HOST:
Not the last one before the boundary.

HOST:
The earliest. If three steps each touched the same file, the file rewinds to before the first touch. Using the latest one would leave the first edit in place.

CO-HOST:
And a file that did not exist in that tree?

HOST:
It gets deleted. That is how a creation is undone. Restoring a file either overwrites it with the recorded content, or removes it because the tree says it was not there.

CO-HOST:
Now the original. Why keep it after you already restored the files?

HOST:
Because stage is reversible, and because the boundary can move. If the user stages again at a different message, the first stage's original is kept. The escape hatch does not move with the boundary.

CO-HOST:
Otherwise clear would restore the wrong tree.

HOST:
Otherwise clear stops meaning "put it back to before I started". That is the whole contract of the undo preview.

CO-HOST:
So clear puts the files back and forgets the boundary.

HOST:
It restores the original snapshot over the files the revert touched, and drops the stored boundary. A stage followed by a clear leaves the working tree as it was.

CO-HOST:
And if I stage twice, does the second one rewind further?

HOST:
It moves the boundary, and keeps the original. So the second stage restores from the new boundary, and the escape hatch still points at the state before you started.

CO-HOST:
And commit is the destructive one.

HOST:
Commit is one publish. The projector does the deleting. Every message at or after the boundary goes. Every inbox row enqueued at or after the boundary goes. The revert state is cleared, and instruction state is reset.

CO-HOST:
Why is commit a publish instead of a write?

HOST:
Because the deletion has to be a fact like any other, folded by the projector in one transaction. If it were a write in the handler, a crash could leave half a history.

CO-HOST:
Inbox rows too. That surprised me.

HOST:
And it is easy to miss. If you rewind the conversation but leave pending input from after the boundary, the next drain delivers a message that belongs to a history you have deleted.

CO-HOST:
So commit is a transaction over several tables.

HOST:
One transaction, and one guard in front of all three operations. Stage, clear, and commit all reject an active session.

CO-HOST:
Why?

HOST:
Because a running execution could be mid write. Applying a restore underneath it either loses the write or restores a half written tree. The guard is what makes "cannot undo mid run" true rather than hopeful.

CO-HOST:
So the takeaway. Stage and clear are reversible. Commit is not.

HOST:
Stage restores and holds the door open. Clear walks back out. Commit closes it.

## 7. Body beat 4 — What undo cannot reach

HOST:
And now the honest half. Revert returns content, not consequences.

CO-HOST:
Meaning it will look broken to somebody.

HOST:
It will, and that is the design being correct.

CO-HOST:
Correct and useless are not the same thing.

HOST:
No, and that is the tension.

CO-HOST:
Take the cold open case. One file was created by a shell command the snapshots never saw. Another is being written by a background process.

HOST:
Revert runs, and both are still there.

CO-HOST:
So the user says it did not work.

HOST:
The first boundary is the capture scope. Paths outside the project, paths the repository ignores, and untracked files over the size cap were never in any tree. Restore cannot touch what was never captured. A file an unmanaged process created is invisible.

CO-HOST:
What about a file the repository ignores, like a build output?

HOST:
Same answer. It was never in a tree, so there is nothing to restore it from.

CO-HOST:
That is the same boundary from the first beat.

HOST:
It is the same boundary, and it is why the first beat spent time on it. Every limit on capture becomes a limit on undo.

CO-HOST:
So the undo is exactly as wide as the record.

HOST:
Exactly as wide, and no wider.

CO-HOST:
What is the second one?

HOST:
Effects that are not file content. A network call, a remote system, a process that is now running. None of that is in a tree. Revert returns bytes.

CO-HOST:
So a deploy that happened is still deployed.

HOST:
And a migration that ran is still run. The agent can put your files back. It cannot put the world back.

CO-HOST:
Then the honest phrasing is "the files are back", not "the change is undone".

HOST:
That is exactly the phrasing. The change is a story about a system, and revert only knows about one part of the system.

CO-HOST:
The third?

HOST:
Runs that were not idle. We covered the guard, but it deserves its place on this list. Revert refuses an active session rather than racing it.

CO-HOST:
Which is why stop and undo have to be two separate actions in the interface.

HOST:
They do, and the order matters. Stop the run, then undo the files.

CO-HOST:
Fourth.

HOST:
History before commit. Stage restores the files but leaves the messages in place. A client that shows the reverted history before commit is showing the history that has not been reverted yet.

CO-HOST:
Which is a lie the interface tells, not the engine.

HOST:
It is an interface bug, and it is avoidable. Say "staged" and mean it.

CO-HOST:
That is an argument for a different button label, not for a different engine.

HOST:
It is both. The engine tells you what it did. The interface decides whether the person understands it.

CO-HOST:
And the fifth?

HOST:
Content versus metadata. Content-addressed trees restore the bytes. Ownership and timestamps are not part of the recorded value.

CO-HOST:
So a script that compares modification times will still think the file is new.

HOST:
It will. Content addressing records content. If your build depends on a time stamp, revert does not repair that, and pretending otherwise would be a worse bug.

CO-HOST:
I want to push on the framing here, because "cannot undo" sounds like a defect list. Is it?

HOST:
It is a scope statement, and every system that claims undo has one. The defect is not the boundary. The defect is a button that implies a complete undo and then quietly does a partial one.

CO-HOST:
So the design note is to name the unsupported set out loud.

HOST:
Name it in the interface. Anything you did not capture is outside revert, and the person clicking should be told before they click, not after.

CO-HOST:
So the takeaway. Revert is bounded by what was captured, and honesty is part of the feature.

HOST:
Snapshot, subtract, and be clear about what you kept.

## 8. The artifact

HOST:
The material states the whole contract of revert in a few sentences. Here it is, word for word.

HOST:
"Revert restores files to the state recorded in step-start snapshots and, on commit, removes the conversation at and after a chosen boundary, but only over the region the snapshots actually captured, and only while the session is idle. Stage records a boundary and applies the file restoration, but keeps history intact. Clear undoes a stage. It restores the files back to the original snapshot and drops the stored boundary. Commit finalizes. The projector deletes every message at or after the boundary, deletes inbox rows enqueued at or after the boundary, clears the revert state, and resets instruction state."

[production note: the source sets off the three operation names with colons and the first sentence with a dash. They are read here as commas and separate sentences so the speech engine does not swallow the list. The companion carries the passage exactly.]

CO-HOST:
Every clause in that is a limit.

HOST:
Every one. Start with the first. "Only over the region the snapshots actually captured." That is not a caveat at the end. It is in the definition.

CO-HOST:
And "only while the session is idle" is in the definition too.

HOST:
Which is unusual, and correct. Most undo features describe what they do and leave the preconditions to the documentation. This one puts the precondition in the same sentence as the promise.

CO-HOST:
Then the three verbs.

HOST:
Stage, clear, commit. Two of them are reversible, and the sentence says which. Stage keeps history intact. Clear restores the original. Commit deletes.

CO-HOST:
And the last sentence names the tables.

HOST:
It names four effects in one sentence. Messages, inbox rows, revert state, instruction state. That is the checklist for anyone reimplementing it, and it is the reason commit cannot be a soft delete.

CO-HOST:
A soft delete would leave the inbox rows.

HOST:
And the next drain would deliver work from a history that no longer exists. The sentence is precise because the bug is easy.

CO-HOST:
So the artifact is really a specification.

HOST:
It is the shortest true description of the feature. Which is what a good comment is.

## 9. Recap

HOST:
Where we landed. One. Each step fingerprints the working tree before and after, and the fingerprint is a content hash, so comparison is cheap and exact.

CO-HOST:
Two. The step keeps two ids and the changed paths. The patch is recomputed on demand, so the summary and the patch cannot drift apart.

HOST:
Three. Revert is stage, clear, and commit. Only commit deletes history, and undo reaches exactly as far as capture did.

CO-HOST:
Say the rule.

HOST:
Snapshot, subtract, and decide. Which sits beside the ones we already have. Record the fact before anyone acts. One execution per session. And compact to a summary plus the newest exchange.
