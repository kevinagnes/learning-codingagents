## 4. Body beat 1 — A retry policy is a budget

HOST:
Here is the claim. A retry policy is not patience. It is a budget with a schedule attached, and every part of that budget is bounded.

CO-HOST:
Bounded how. I have written retry code. It is a loop with a counter in it.

HOST:
A counter is one of five decisions. The other four are where people get it wrong.

CO-HOST:
Go on then. Name the five.

HOST:
Growth, which is how long between attempts. Count, which is how many. Jitter, which is whether clients fail in step. Server intent, which is whether the provider gets a say. And cost, which is whether every retry costs the same as the first.

CO-HOST:
That last one is not a scheduling question.

HOST:
It changes the schedule, so it is. Take growth. The gap doubles, starting at two seconds. Two, four, eight, sixteen. But each gap is clamped at ten seconds, so the curve flattens instead of running away.

CO-HOST:
Why clamp the gap. Surely waiting longer is gentler on the provider.

HOST:
It is gentler on the provider and harsher on the person watching. The clamp says the session has a horizon.

CO-HOST:
Fine. Then the count.

HOST:
Ten retries. Enough to ride out a short outage, and small enough that a provider which is truly dead fails in about a minute.

CO-HOST:
So the whole schedule is roughly a minute of waiting.

HOST:
About eighty-four seconds if every attempt fails, before jitter. Which is the third decision. Each gap is randomized by about a third, so a fleet of sessions that break at once does not return in one wave and knock the provider over again.

CO-HOST:
Now the part I want to argue about. The provider sends a retry-after header. Why not trust it. That is the server's own number.

HOST:
Because the server's number can be wrong, hostile, or measured in hours. So the header is a floor, not an instruction. Wait at least that long, and never more than fifteen minutes.

CO-HOST:
So you overrule the provider.

HOST:
I bound it. If it asks for two seconds, we wait at least two seconds. If it asks for an hour, we wait fifteen minutes and try again, and it is free to rate limit us again.

CO-HOST:
And the fifth decision. Cost.

HOST:
A request that failed before it produced anything is cheap to repeat. A request that timed out already burned its whole timeout. So timeouts get a smaller budget of their own. Three, not ten.

CO-HOST:
Because ten timeouts is ten times the wall clock.

HOST:
Yes. Ten retries of a fast failure is a minute. Ten retries of a slow timeout is most of an hour.

CO-HOST:
So the schedule is not one number. It is a shape, and the shape has corners.

HOST:
It has four corners, and one of them is a ceiling the server cannot move.

CO-HOST:
Hold on. You have described a schedule with randomness in it. How do you test that. You cannot assert a random delay.

HOST:
You assert the shape, not the value. Drive it with a fake clock and a sequence of failures, and check the delay sequence and the stop condition.

CO-HOST:
So the jitter is a range, not a number.

HOST:
A range of about a third either way. And if the outage outlasts the budget, the step fails with a typed error. A budget you never spend down is not a budget.

CO-HOST:
One more detail, because it matters to the interface. The scheduled wait is written down as an absolute time, not as a countdown. A client that reconnects mid wait shows the same clock as one that never left.

HOST:
That is a small detail with a real consequence. The retry survives a page reload, because it is a fact in the record, not a timer in a tab. Which is the takeaway. A retry policy is a budget with a schedule, and its job is to keep a broken provider from holding the session hostage.

CO-HOST:
Then what happens when the wait is over, the retry fails again, and the model had already said something?

HOST:
That is a different decision, and it does not start with a clock.

## 5. Body beat 2 — Retry, continue, or start again

HOST:
The claim is this. Whether to retry is decided by one fact, and the fact is not the error. It is whether the attempt had shown the user anything yet.

CO-HOST:
That sounds like a detail. Surely the error tells you what to do.

HOST:
The error tells you whether the failure is worth trying again. It does not tell you what a second attempt would cost. Two paragraphs are on screen, and the model is mid sentence.

CO-HOST:
So the obvious move is to resend the request.

HOST:
Resend it and the model starts from nothing. It has no memory of the half answer, because it never entered its history. So it writes a different answer, and the user reads both.

CO-HOST:
And if you give up instead, you throw away a response that was almost finished.

HOST:
Also true. So there are three recoveries, not two, and the deciding fact is durable. Did output start. Not does the code think it started. What do the written events say.

CO-HOST:
Why does that distinction matter.

HOST:
Because a different process may make the decision. The step may have been running somewhere that is now gone. If the answer lived in a variable, the next process would guess. Folded from the events, it reads it.

CO-HOST:
So walk me through the three.

HOST:
First, retry. The failure happened before any visible output. The assistant message either has not started or is empty. So the same call runs again, transparently, against the same assistant message. The user sees one message that eventually fills in. Nothing is duplicated, because nothing was shown.

CO-HOST:
That is the boring case, and boring is correct.

HOST:
It is. Second, continue. Output had started, so the partial answer is worth keeping. The agent does not re-ask the question. It appends a short instruction and starts a new assistant message, and the model picks up from its own partial answer.

CO-HOST:
So the difference between retry and continue is one line of bookkeeping. Same message, or a new one.

HOST:
It is one identifier. Retry keeps the assistant message. Continue rotates it and writes a synthetic instruction in between. That is the whole difference between a message that fills in later and one that resumes.

CO-HOST:
Let me push on that. Why not always continue. Continuing never loses work.

HOST:
Because continuing before any output is worse than retrying. The model gets an instruction to resume, with nothing to resume from, so it guesses. You have turned a clean failure into a fabricated opening.

CO-HOST:
So the instruction is only as good as the prefix it points at.

HOST:
It is a pointer. With no prefix, it points at nothing.

CO-HOST:
And the third.

HOST:
Recover the whole request. Some transport failures cannot be resumed at the stream layer. The socket is gone in a way that cannot continue a partial read, and the transport itself says so. Then the only correct action is to discard the attempt and issue the entire request again.

CO-HOST:
Why is that not the default. It sounds the most thorough.

HOST:
Because it is expensive and it can loop. It is allowed once per step. A second full recovery would discard and re-issue forever, so it is a latch, not a branch. And it is gated on no output.

CO-HOST:
So one of the three is a transport property, and two are about what you already showed.

HOST:
That is the shape of it. Both retry and continue publish a scheduled retry event, so the client can show a countdown.

CO-HOST:
What breaks if you get the choice wrong.

HOST:
Three ways. Retry after partial output gives you two answers. Continue with no prefix makes the model invent a starting point. And a full recovery in a loop drops the stream at the same place every time.

CO-HOST:
Which is the quiet one.

HOST:
The first. Two answers look like progress. The user reads both and trusts the second one.

CO-HOST:
So two of the three recoveries exist to protect what is already on screen.

HOST:
And the third exists to protect the request itself.

CO-HOST:
So the takeaway is not about errors at all.

HOST:
The takeaway is this. Retry, continue, or re-issue, chosen by one durable fact. Did output start.

## 6. Body beat 3 — Classify once, from evidence

HOST:
Next claim. The error message is not the classification, and the classification is not the message.

CO-HOST:
That sounds like word games. An error is an error.

HOST:
Dozens of providers report the same idea, that your request is too long, in dozens of different strings. One puts it in a message field. One in a detail field. One returns an array of errors. One returns only a status code.

CO-HOST:
So a naive agent matches the one phrasing it has seen.

HOST:
And treats the rest as unknown. So it retries a request that can never fit, because the classifier has never met that spelling before.

CO-HOST:
That is a real bug and it is invisible. The user sees retries, not a diagnosis.

HOST:
Three layers sit between the wire and the user. Classify, decide, normalize.

CO-HOST:
Take them in order.

HOST:
Classify turns the raw failure, the status, the headers, the body, the error object, into one typed reason. Rate limit. Authentication. Quota. Content policy. Transport. Provider internal. Invalid output. Invalid request. No route. Unknown. Timeout.

CO-HOST:
That is a lot of kinds.

HOST:
The number is the point. Each one has a different answer. And the classification is ordered evidence, not prose. A payment required status is quota. A rate limit status that mentions a balance is also quota, not a throttle.

CO-HOST:
Because topping up fixes one and waiting fixes the other.

HOST:
Exactly. Status first, then codes, then text, and text only when the status does not contradict it.

CO-HOST:
Now the part I think is brave. What happens to a failure nobody recognizes.

HOST:
It becomes unknown provider, and unknown is retry eligible.

CO-HOST:
That is backwards. Unknown should be the scary one.

HOST:
It is the design bet, and it is deliberate. A deterministic rejection almost always carries a status or a known code, because the provider wants you to stop. A transient failure arrives in shapes nobody anticipated. So the fall through retries, and the classifier only records affirmative evidence.

CO-HOST:
Then defend it properly. If unknown retries, and most errors are unknown, you have built a machine that retries everything.

HOST:
The classifier is not guessing. It records affirmative evidence for every deterministic class it can prove. Unknown means nobody has produced that evidence yet. The retry budget is what stops the machine, not the classification.

CO-HOST:
So the budget is the safety net under the taxonomy.

HOST:
The budget is the safety net under everything in this episode.

CO-HOST:
And the retry decision reads the class.

HOST:
It reads only the class. Rate limit and provider internal retry. Authentication, quota, content policy, invalid request, unsupported operation, no route, and timeout do not. Transport is the interesting one, because it depends on delivery.

CO-HOST:
Delivery of what.

HOST:
Of the request. If the transport rejected the write, it does not retry. If the provider accepted the write and the failure happened while reading the answer, a read can be recovered. The class carries that detail, so the policy does not have to guess from a sentence.

CO-HOST:
And there is an escape hatch.

HOST:
One header. A provider can say retry, or do not retry, and that overrides the class. It is the only place where a header outranks the taxonomy.

CO-HOST:
Then normalize.

HOST:
Normalize maps every reason, and a few non provider causes, into one persisted shape. A type string, a human message, an optional status, and an optional raw body. That is what the user sees, what the assistant message stores, and what the retry event carries.

CO-HOST:
Why one shape. The reasons are all different.

HOST:
Because everything downstream would otherwise branch on the source. The interface wants a message and a status. The retry event wants something durable. The transcript wants something replayable. One shape serves all three, and the raw body rides along inside it.

CO-HOST:
And if somebody adds a reason and forgets the mapping.

HOST:
The switch is exhaustive, so it does not compile. That is the cheapest possible enforcement. The compiler becomes the checklist.

CO-HOST:
So the taxonomy is enforced by the type checker, and the retry budget is what enforces the taxonomy.

HOST:
Yes. And the last layer is the one the user actually reads.

CO-HOST:
So the takeaway. Classify at the door, and let the decision read the class.

HOST:
Classify once, from evidence, and let the retry decision read the class rather than the sentence.

## 7. Body beat 4 — A clean ending is not a good ending

HOST:
Last claim, and it is the one that hides best. A stream can end cleanly and still be a failure.

CO-HOST:
Cleanly how. If it ended, it ended.

HOST:
Two cases, and neither is a network error. The first is a content filter. The provider finishes the response normally, with a normal finish reason, and the content is blocked.

CO-HOST:
So there is no error at all. There is an empty answer and a reason code.

HOST:
And if you store that as a normal completion, the user sees an assistant that said nothing. No error, no message, no clue. The session looks stalled. So the finish reason becomes a typed content filter error, carrying the provider's own category and explanation when it sends them.

CO-HOST:
Hold on. Is a content filter really a failure. The provider did what it was asked, and it declined.

HOST:
It declined without telling the model, and it left an empty message. From the agent's side that is indistinguishable from a bug. So it becomes an error the user can read, with the provider's category attached.

CO-HOST:
Because an empty answer with no explanation is the one outcome nobody can act on.

HOST:
It is. It looks like a stall, and the user has no next move.

CO-HOST:
Right. And the second case.

HOST:
The stream ends successfully, and the finish reason is unknown. The provider did not say stop, did not say length, did not say tool call. It said it does not know.

CO-HOST:
Which could mean anything.

HOST:
Which is why it is not treated as a completion. The agent synthesizes an incomplete stream failure, so the step goes through the same recovery logic as any other broken attempt. It cannot masquerade as success.

CO-HOST:
And a stream that stops before the end marker.

HOST:
That is the same failure with a different origin. The reply is classified as invalid provider output, with a marker that says incomplete stream. It is retryable, and if output had already started, retryable is not the point. It routes to continue.

CO-HOST:
So the marker and the routing are separate decisions.

HOST:
They have to be. Retryability answers whether another attempt could work. Routing answers what the next attempt should say. A stream that died mid sentence is retryable and it is also a continuation, and the second fact is the one the user sees.

CO-HOST:
And there is a fourth outcome I keep forgetting. The model did not fail. It ran out of room.

HOST:
The output limit. The response ended because it hit the token ceiling, not because anything broke. That is its own outcome, and its own instruction. Ask the model to break the rest of the work into smaller pieces.

CO-HOST:
And that one is allowed to happen more than once.

HOST:
Up to a point. Two continuations, and then a third truncated response is a typed failure. The message says the response was still truncated after two continuations, so the user learns why the agent stopped trying.

CO-HOST:
Two continuations feels arbitrary. Why two.

HOST:
Because each continuation is a full model call, and a model that has been truncated three times in a row is not going to succeed on the fourth. The number marks the point where the failure stops being the network and becomes the request.

CO-HOST:
So the limit is a diagnosis, not a punishment.

HOST:
It tells the user which thing to change.

CO-HOST:
Which is the pattern in all of this. Every failure has a name, a decision, and a limit. No failure is allowed to be a surprise, and no limit is allowed to be a secret.

HOST:
Every one. And the limit is what separates a policy from a loop. A policy can refuse. A loop can only go around again.

CO-HOST:
Then show me the words the model actually receives.

HOST:
They are short, and they are the whole recovery, spoken to the model.

## 8. The artifact

HOST:
When a stream stops early, the next step is not the same question. It is a new message, and it carries an instruction. Here is the first one, word for word.

HOST:
"The previous response was interrupted. Continue from where you left off without repeating completed content."

CO-HOST:
That second sentence is doing the work.

HOST:
It is. Without it, models restart the answer, and you pay for the same paragraphs twice. There is a second string for the other failure, the one where the model ran out of room rather than the network running out of time.

HOST:
"Your last response hit the output token limit (stop reason: length). Do not apologize, recap, or repeat yourself. Break the remaining work into smaller pieces."

CO-HOST:
Telling a model not to apologize is a strange thing to put in a prompt.

HOST:
It is a strange thing to have to put in a prompt. The model has been cut off mid answer, and its instinct is to say sorry and summarise what it was saying. That spends the new tokens on the old failure. So the instruction names the three wastes and forbids them, then gives the model one thing it can act on.

CO-HOST:
Break the rest into smaller pieces.

HOST:
Which turns a truncation into a plan. And the two strings differ because the failures differ. One says the stream was cut. The other says the model reached its own ceiling. The recovery has the same shape, but the model needs to know which thing happened, or it will keep writing at the size that failed a moment ago.

CO-HOST:
And if it keeps happening anyway.

HOST:
Then the continuation stops being a continuation and becomes an error with a name. The agent stops, and the user is told why.

CO-HOST:
Which is more honest than a third paragraph that starts mid sentence.

## 9. Recap

HOST:
Where we landed. One. A retry is a bounded schedule. Growth, count, jitter, server intent, and a smaller budget for timeouts.

CO-HOST:
Two. The recovery is chosen by whether output started. Retry fills the same message. Continue starts a new one with an instruction. A full re-request happens once, and only from the transport.

HOST:
Three. Failures are classified once from evidence and normalized into one shape, and unknown is a category that retries. And four, a clean ending is not a good ending.

CO-HOST:
Say the rule.

HOST:
Decide retry, continue, or recover from the taxonomy. And keep the older ones. Continuation is read from the record, and a decline never reaches model context.
