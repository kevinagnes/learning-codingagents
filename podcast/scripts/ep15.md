HOST:
Watch what happens when a session gets long. The transcript grows, the tool results pile up, and the provider starts rejecting requests as too long. Nothing has failed. Nobody made a mistake. The conversation outgrew the window it lives in.

HOST:

That is worse than running out of room. A summary that loses the exact paths and the current state makes the next step confidently wrong.

HOST:
So how does an agent decide what to forget, and when?

## 4. Body beat 1 — You cannot weigh the parcel before you post it

HOST:
Here is the claim. You cannot ask the provider how big your prompt is. You can only ask what the last one was.

CO-HOST:
Why not count it locally. A tokenizer is a library. You pass it the text and it gives you a number.

HOST:
And on dense text that number is wrong. Code, tables, long identifiers. Count characters and divide by four and you will be low.

CO-HOST:
So estimate high instead.

HOST:
Then you compact a conversation that still had room, and you throw away detail for nothing. Both failures come from the same question. How big is the context, really.

CO-HOST:
And the answer is that you do not know.

HOST:
You know two things. The provider told you a true number for the last request it saw, and you can estimate the text since. So the size is measured plus estimated.

CO-HOST:
Measured from where, and measured how.

HOST:
From the most recent assistant message that reported usage. Input tokens, cache reads, cache writes, output, reasoning. That is the anchor. Everything before it is already accounted for.

CO-HOST:
And everything after it is somebody's guess.

HOST:
Is estimated locally at about four characters per token. A real number for most of the conversation, a rough one for the tail.

CO-HOST:
Why the tail. Why not measure the whole thing from the last message.

HOST:
Because the anchor's usage covers its own output, but not its local tool results. The provider never saw those. They arrived after the reply.

CO-HOST:
So the tool results are counted, and the message that produced them is not.

HOST:
That detail keeps the budget from drifting by the size of the largest tool output. Get it wrong and every estimate is off by the biggest thing you read.

CO-HOST:
That is a strange asymmetry. The result counts, the message does not.

HOST:
The message's usage already includes its own output. The tool result was never sent to the provider, so nothing has counted it yet.

CO-HOST:
And there is a margin on the estimate.

HOST:
Fifteen percent, when the agent is sizing the reply, because dense text runs higher than four characters per token. The margin makes the estimate err toward fitting.

CO-HOST:
So the estimate is deliberately pessimistic.

HOST:
In one direction. It would rather compact a little early than be rejected.

CO-HOST:
Now the part I find suspicious. You said the anchor has to come from the same provider.

HOST:
It does. Another provider's count may describe a window this model cannot replay. A native checkpoint replaces history with something opaque, and that count describes a window that no longer exists as text.

CO-HOST:
So when you switch providers mid session, the anchor goes stale.

HOST:
The anchor is ignored, not deleted. The message is still there. It is not evidence for this model.

CO-HOST:
And if the model's window is unknown. Zero.

HOST:
Then the count is zero and the ceiling is infinite, so automatic compaction never fires. A zero window means cannot detect, not must compact now.

CO-HOST:
Which is the opposite of what most code would do. Zero means empty, empty means act.

HOST:
And acting there would summarise the session on every step and destroy the context it was trying to save.

CO-HOST:
So the whole measurement is a hybrid on purpose.

HOST:
It is. Trust the provider for what it saw, estimate only what arrived since. A pure local estimate drifts. A pure provider number does not exist before you send.

CO-HOST:
So the number is not a fact. It is a receipt plus a guess.

HOST:
And every decision in the rest of this episode reads that number. Which is the takeaway. You cannot weigh the parcel before you post it, so you use the last receipt and weigh what you added.

CO-HOST:
And the receipt has a limit. How much room do you actually leave yourself.

HOST:
That is the next question, and it has an answer with a floor in it.

## 5. Body beat 2 — The ceiling is not the window

HOST:
Next claim. The ceiling is not the window. The gap between them is the reply you are asking for.

CO-HOST:
That sounds like the same number with a different name.

HOST:
The window is the largest request plus response the model accepts. Fill it and there is no room left to answer. The provider grants a few tokens, and the model says three words and stops.

CO-HOST:
So you compact to free space, and then you have no space for the summary either.

HOST:
Which is how compaction becomes a loop that eats itself. You fill the window, you compact to fit, the summary has nowhere to go, and you compact again.

CO-HOST:
And the summary request has the same problem. It is a request too.

HOST:
It is, and it is capped at the same ceiling, so its output limit is whatever the reserve leaves. The summary has to fit inside the space it is trying to free.

CO-HOST:
So the reserve is also the summary's budget.

HOST:
Everything here is one budget seen from different angles. The window, the ceiling, the reserve, and the summary's own reply.

CO-HOST:
So the design keeps a reserve.

HOST:
Ten percent of the window, or sixteen thousand tokens, whichever is larger. A window too small to spare sixteen thousand keeps ten percent.

CO-HOST:
And the ceiling is window minus reserve.

HOST:
Exactly. The request is allowed to reach the ceiling, and the reserve below it belongs to the answer.

CO-HOST:
Why not a fixed reserve. Sixteen thousand for every model.

HOST:
A small window cannot afford a fixed reserve that big, and a huge window would reserve almost nothing. Percentages scale, and the floor protects the small case.

CO-HOST:
Then why is the floor there at all. Sixteen thousand tokens is a strange number.

HOST:
It is the least room worth keeping for a last reply and a summary. Below that, the percentage is the only thing that still scales.

CO-HOST:
Wait. You said window. But some models cap the prompt separately from the reply.

HOST:
Three sizes. The context window, request plus response. An input limit, which some models cap separately. And an output limit, the largest reply. The budget uses the input limit when there is one, and falls back to the window.

CO-HOST:
So the ceiling is computed from whichever limit binds.

HOST:
Which means the number is yours to get wrong, and the reserve is the margin for getting it wrong.

CO-HOST:
What if the reserve is wrong. The request still fits, and there is no room left to answer.

HOST:
Then the model produces a sentence and stops, and compaction runs again.

CO-HOST:
Now the case that surprised me. When is compaction due.

HOST:
When the estimate has reached the ceiling, and two conditions hold. The last message is not a completed compaction, and there is a measurement from the current provider that is newer than the latest checkpoint.

CO-HOST:
The first one is obvious. Do not compact twice.

HOST:
The runner needs to rebuild the request from the checkpoint first. Compacting again before it has done that would summarise the summary and lose a layer of detail.

CO-HOST:
And the second condition.

HOST:
If the newest thing in history is a native checkpoint, the text after it estimates as nothing, because the window is opaque. So the agent waits for a real response before it trusts any number.

CO-HOST:
So the second condition is about trust, not size.

HOST:
It is about evidence. A number you cannot reproduce is not a measurement.

CO-HOST:
And there is an escape hatch for someone who knows their model.

HOST:
A setting can supply an explicit reserve instead. The default is the percentage with the floor.

CO-HOST:
But a person can still ask.

HOST:
A person can always ask. Manual compaction runs even when automatic compaction is switched off. The switch is about the agent deciding for you, not about the feature existing.

CO-HOST:
So the takeaway is about the reserve.

HOST:
A budget without a reserve is not a budget. It is a wall.

## 6. Body beat 3 — Make it smaller, not again

HOST:
Third claim. A rejected request is not retried. It is made smaller.

CO-HOST:
Hold on. Last episode was entirely about retrying. Now a rejection arrives and you do not retry it.

HOST:
You do not retry the same request, because the same request will be rejected the same way. There are three ways compaction starts, and one of them is that exact rejection.

CO-HOST:
Name the three.

HOST:
Auto, which is the estimate reaching the ceiling before the request is sent. Manual, which is a person asking, delivered as a control item in the inbox. And overflow, which is the provider rejecting the request mid step because it is too long.

CO-HOST:
And overflow is the interesting one, because the step has already begun.

HOST:
It is detected during the step, before the assistant produces output. The agent compacts with the overflow reason and, if that succeeds, restarts the step from the new checkpoint.

CO-HOST:
So the failed attempt is discarded, not continued.

HOST:
There is nothing to continue. The provider refused the input.

CO-HOST:
Now the shrinking itself. How do you shrink a request when you do not know how far off you were.

HOST:
You do not guess once. You step down. The first shrink aims at seventy percent of the first rejected request's size. Then fifty. Then thirty-five. Then it gives up.

CO-HOST:
Why those numbers.

HOST:
Because the estimate ran low by an unknown amount, and one correction could undershoot or overshoot. Three steps compound toward something smaller. The target is always recomputed from the first rejected size, so the steps do not drift.

CO-HOST:
What if the problem is not size at all. What if it is bytes.

HOST:
Then it is a different branch. Payload too large is about bytes, not token count, and inline images almost always account for it. The first time it happens on an unchanged request, the agent resends the same content as text, which carries no media. That is free and does not consume a shrink step.

CO-HOST:
And if the text version is still too large.

HOST:
Then it is treated as too long, and the shrink steps begin.

CO-HOST:
So the byte problem gets one free fix before it counts as a size problem.

HOST:
One, because stripping media usually solves it outright.

CO-HOST:
What does sending as text actually do to the conversation.

HOST:
It flattens everything since the last compaction into one text message, dropping reasoning, media, and instruction updates. A previous summary stays in front, and a native window stays as the provider made it.

CO-HOST:
And if it still does not fit.

HOST:
Then whole exchanges are dropped, oldest first, one note at a time. An exchange is a user message and everything after it up to the next user message. It is kept or dropped as a unit, so an assistant's tool calls and their results stay together.

CO-HOST:
Why the unit. Why not drop single messages.

HOST:
Because a tool call without its result is a request the provider will reject. The exchange is the smallest thing that stays coherent.

CO-HOST:
And if even the newest exchange does not fit.

HOST:
Then it fails, with a message that says it cannot be reduced further without losing the latest exchange or the checkpoint. Dropping the newest exchange would mean answering a question the user did not ask.

CO-HOST:
So the loop has a floor, and the floor is the current task.

HOST:
The floor is the current task. And there is one more detail. Room is set aside for the omission note before anything is kept, so the note saying how many exchanges were dropped cannot push the request back over the target.

CO-HOST:
The note about what you cut is part of the budget.

HOST:
Everything that goes on the wire is part of the budget. Which is the takeaway. Shrink by whole exchanges, from the first rejected size, and stop before you drop the newest one.

## 7. Body beat 4 — A handoff note, not a summary

HOST:
Last claim, and it is the one that decides whether the next step works. Compaction does not summarise your conversation. It writes a handoff note and keeps the newest exchange word for word.

CO-HOST:
That sounds like the same thing with better branding. A summary is prose. A handoff note is a form.

HOST:
It is. A summary is whatever the model thinks mattered. A handoff note has a contract, and the contract has sections.

CO-HOST:
Who decided those were the sections.

HOST:
The failure mode decided. Ask for a summary and you get a paragraph that mentions some files. The next agent cannot tell what is finished, what is blocking, or what you asked for.

CO-HOST:
Give me one.

HOST:
Relevant files, capped at fifteen, most important first, and told not to list every file it read. Without the cap the list grows until it dominates the note.

CO-HOST:
And the rules block.

HOST:
Terse bullets, short references, and exact paths, symbols, commands, and identifiers.

CO-HOST:
Because the next agent can re-read code, but cannot recover a renamed symbol.

HOST:
Exactly. Compression must not paraphrase the things the next step needs verbatim. There is a second rule that is stranger. Do not mention the summary process, or that context was compacted.

CO-HOST:
Why hide it.

HOST:
Because a model that knows it was compacted starts apologising for what it forgot. The user needs the work to continue.

CO-HOST:
Now the split. What actually survives verbatim.

HOST:
The newest messages within about fifteen thousand tokens, kept as text beside the summary. The split starts at a user message, so tool calls and results stay together. The newest exchange is always kept, so there is still an older part to summarise.

CO-HOST:
So the boundary is chosen where an exchange begins.

HOST:
The boundary keeps every exchange whole. Same reason as the shrink loop. A tool call and its result are one thing.

CO-HOST:
And the reply itself is checked.

HOST:
It has to contain at least one template heading. If it does not, the agent sends one reminder. A second miss is a failure, saying the summary did not match the template or produced no summary.

CO-HOST:
One reminder, not a loop. The format is enforced, not suggested.

HOST:
One reminder, because a model that ignored the format twice will not be fixed by a third try. And a checkpoint that does not match the form is worse than none, because the next reader trusts it.

CO-HOST:
What about the second compaction, and the third.

HOST:
The prompt changes. The first says, summarise this conversation for another agent. Later ones say, update the existing checkpoint into one consolidated summary. Newer history always wins. Move completed work out of Active, and remove resolved blockers and answered questions.

CO-HOST:
So the note does not grow forever.

HOST:
It converges. Preserve first, then reconcile. An older, more verbose form left a catch-all section that would be carried forward forever, so a checkpoint with that heading is rewritten once.

CO-HOST:
And when the provider can do all of this itself.

HOST:
Then the checkpoint is not text at all. That is where the obvious choice is wrong, so here is the person who made it.

EXPERT:
We treat a native checkpoint as an opaque window. The provider returns it, we store it with its provenance, and we replay it only against the endpoint that produced it.

CO-HOST:
Then why not always use it. The provider knows its own context better than you do.

EXPERT:
It does, and when it works it preserves more for less. But the checkpoint is addressed to one deployment. Provenance is a hash of the endpoint, checked before compaction, after any request hook, and again when history is rendered. A checkpoint that does not match is skipped, and the transcript it replaced comes back.

CO-HOST:
So the session is pinned to a machine.

EXPERT:
The session is pinned to an identity. Move it, and you fall back to text rather than send an encrypted window to something that cannot read it.

HOST:
Which is the takeaway. Compact to a summary plus the newest exchange, and replay an opaque window only where it was made.

## 8. The artifact

HOST:
The summary is a form, and the form is written down. Here are its section headings, word for word.

HOST:
"Objective. Requirements. Decisions. Work State. Completed. Active. Blocked. Next Move. Relevant Files. Important Context."

CO-HOST:
Read as a list, that is a project status, not a conversation.

HOST:
That is the point. Here are the rules that go with it, word for word.

HOST:
"Keep each section concise. Use terse, single-line bullets, not prose paragraphs or nested lists. Prefer short references over detailed restatement. It is fine to leave out information the next agent can recover from the code or the files listed above. Preserve exact file paths, symbols, commands, error strings, U R Ls, and identifiers. Carry forward only user questions or requests that remain unanswered or require further action. Do not repeat ones that newer history has answered or resolved. Preserve exact wording when carrying one forward. Preserve consequential workflow state, including whether changes are uncommitted, committed, pushed, under review, or merged. Do not mention the summary process or that context was compacted."

[production note: the source writes the acronym for web addresses as one word. It is spelled out here so the speech engine says the letters. The companion carries the rule exactly.]

CO-HOST:
Two of those rules are doing most of the work, and both are about what the next agent cannot reconstruct.

HOST:
The file rule and the question rule. Preserve the exact paths, and carry forward only what is still open. One protects what cannot be recovered. The other stops the note from accumulating a list of questions you already answered.

CO-HOST:
So the note is written for the next agent, not for the user. And the last rule is about silence.

HOST:
Do not mention that context was compacted. The note is a report to the next agent, not a confession to the user. Every rule here is pointed at the same thing. The next step should be able to start without asking you anything.

## 9. Recap

HOST:
Where we landed. One. The size is measured plus estimated, and only from the same provider.

CO-HOST:
Two. The ceiling is the window minus a reserve, so the reply always has room. An unknown window never triggers automatic compaction.

HOST:
Three. Three triggers, auto, manual, and overflow, and a shrink loop that cuts to fractions of the first rejected size, keeps exchanges whole, and refuses to drop the newest one.

CO-HOST:
And four. The checkpoint is a fixed form plus the newest exchange verbatim, updated by reconciliation, and native windows only replay where they were made.

HOST:
Say the rule.

CO-HOST:
Compact to a summary plus the newest exchange. And keep the older ones. Decide from the taxonomy, and read continuation from the record.
