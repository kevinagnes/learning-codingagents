# Episode 13 beat sheet — Permissions

Production sheet. Not read aloud. Four beats, each with the same four moves. Word
allocations are the delivered counts.

## Beat 1 — Order is the whole rule

- **Claim.** "A permission decision is a pure function of three things. An action, a
  resource, and an ordered list of rules. The last matching rule wins."
- **Source.** Topic 6.1 (Part 6, permissions and human in the loop).
- **Example / edge the co-host raises.** Two rules match one request and nobody said which
  one wins. The co-host also pushes on first-match versus last-match, and on the wildcard
  translator being a tiny language rather than a real expression engine.
- **Mechanism.**
  - A rule is an action pattern, a resource pattern, and one effect: allow, ask, or deny.
    There is no nesting, no negation, and no priority field.
  - Merging is concatenation that preserves order. Nothing is deduplicated, so two identical
    rules are both kept and the later one answers.
  - Wildcards become a small translation: star is any run, question mark is one character,
    everything else is escaped, and patterns are anchored at both ends. A pattern ending in
    a space and a star also matches the bare prefix.
  - Nothing matching yields ask. Deny is checked in a separate pass over the configured
    rules, before saved grants are appended, so an always-allow cannot resurrect a hard
    deny. Saved rules are durable rows keyed by project, action, and resource, appended
    last as allows.
- **Takeaway.** "Order is the entire precedence mechanism, so the most specific rule goes
  last."
- **Words.** 679.

## Beat 2 — The no that cannot be read

- **Claim.** "A refusal is not a result. In this implementation it is carried as a defect,
  and that is the whole point."
- **Source.** Topic 6.2 (Part 6); Appendix A group Policy for the model-facing text.
- **Example / edge the co-host raises.** The cold open: reject a destructive command, read a
  tool result saying it failed, watch the model try a different route. The co-host calls the
  defect channel a category error, and asks who catches the decline and why a special error
  type would not do.
- **Mechanism.**
  - Allow is silent. Deny is a typed error the model reads. Ask registers a pending request
    with a one-shot signal, publishes it, and suspends the tool with no timer and no loop.
  - A plain reject dies as a decline rather than failing. Error mappers rewrite failures
    only, so the decline passes through every tool's wrapper untouched.
  - Exactly one boundary recovers it typed: the place that produces tool results. The step
    then marks the tool aborted and interrupts the step. The decline ends the step instead
    of becoming a message.
  - A reject with a message stays typed. The wrapper turns it into a tool failure, the model
    reads the feedback, and the step continues. The split is by information content.
  - **EXPERT** appears here, once, with room. This is the emotional centre of the season.
    Entry line: "This is the part where the choice looks wrong, so here is the person who
    made it." Four turns. Point: the defect channel is the one path no existing wrapper
    swallows, so the safety does not depend on the next tool author remembering a
    convention, and telling the model it was denied invites negotiation.
- **Takeaway.** "A decline never reaches model context."
- **Words.** 734.

## Beat 3 — One reject, one batch

- **Claim.** "One reject settles the whole batch. One always settles only what its new rule
  covers."
- **Source.** Topic 6.3 (Part 6).
- **Example / edge the co-host raises.** Four edits in one step, four prompts, one approval
  and one rejection, and two prompts left hanging. The co-host also asks why prompts cannot
  settle independently, and what happens if two clients answer at once.
- **Mechanism.**
  - Pending asks are plural. A reject fails the targeted request, then fans out to every
    other pending request in the same session with the same error and the same message.
  - An always writes the saved rule first, then re-evaluates each sibling against the
    updated rules. Siblings that now resolve to allow are released. Siblings that still ask
    stay pending.
  - Coverage is decided by the evaluation function, not by a string comparison. The fan-out
    is filtered by session, so another conversation's prompts are untouched.
  - The whole reply handler is uninterruptible, so a batch cannot be half-settled. Once
    releases only its target. A second reply finds nothing to settle and fails as not found.
- **Takeaway.** "The batch boundary is the session. A no is total, and a yes is
  conditional."
- **Words.** 635.

## Beat 4 — The question tool

- **Claim.** "Asking a person is itself a permissioned action. And dismissing a question
  means the same thing as declining one."
- **Source.** Topic 6.4 (Part 6); Appendix A group Tools for the description.
- **Example / edge the co-host raises.** Scaffolding a project needs three decisions, and
  guessing means doing the work twice. The co-host asks why asking needs a permission, and
  what closing a prompt means.
- **Mechanism.**
  - The primitive is a form: an identifier, a session, a title, fields with a key, a type,
    and constraints. Conditional visibility may reference earlier fields only, so rendering
    is a single forward pass with no cycle.
  - State is pending, answered, or cancelled with an optional message. A reply is validated
    against the fields, so a client cannot submit an option the form never offered. Pending
    forms never expire, and terminal forms are kept briefly for reconnecting clients.
  - The question tool clears its own question permission first, then opens a form, one field
    per question, with options as the value space and free-form input always enabled.
  - An answer becomes model text. A dismissal with no message dies as a cancellation through
    the same tunnel and ends the step. A dismissal with a message is an ordinary tool
    failure the model continues on. Interrupting the wait cancels the form, and the settles
    are uninterruptible.
- **Takeaway.** "A form is the general way to ask a person, and the question tool is one
  consumer of it."
- **Words.** 639.

## Terms to define on first use

- **ruleset** — an ordered list of rules.
- **rule** — an action pattern, a resource pattern, and one effect.
- **effect** — allow, ask, or deny.
- **saved rule** — a durable, project-scoped always-allow grant.
- **pending request** — a registered ask waiting on a one-shot signal.
- **defect** — a non-recoverable error that bypasses typed error handling.
- **decline** — a refusal with no message. **Corrected feedback** — a refusal with one.
- **form** — the primitive for asking a person for structured input.

## Do not say in this episode

- "turn" for a step. A decline ends the step.
- "queue" for waiting input. The tool suspends on a signal.
- "checkpoint" or "compaction". Neither appears here.
- "sandbox", "policy engine", or "capability token", which the material does not use.
- Any rule, flag, table, or field name from the code.
