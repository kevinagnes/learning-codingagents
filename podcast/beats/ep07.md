# Episode 7 beat sheet — Output is a budget

Production scaffolding, not prose. Four beats, four moves each: claim, example, mechanism,
takeaway. The script was written from this sheet; where they disagree, the script is what
was recorded and the sources are what is true.

**Topics:** 1.3, 5.4, 7.5 · **Parts 1, 5, 7** · **Runtime:** ~22.2 minutes · **Words:** 3,325

---

## Beat 1 — The reply is the room the prompt leaves

**Claim.** The output limit is a number you choose for the model.

**Source.** 1.3 Output-token budgeting (Part 1).

**Example the co-host raises.** "I set it to the model's maximum and move on." Then: what the
provider does instead, and why the same code asks for a different amount every step.

**Mechanism.**

- Two catalog numbers: the window (`context`) and the model's output cap (`output`). Two
  prompt numbers: measured (the provider's own usage at the last response) and estimated
  (everything since, about four characters per token plus a margin).
- `room = context − measured − ceil(estimated × 1.15)`.
  `outputLimit = min(catalog output, max(floor, room))`, with a fallback when the catalog has
  no output cap and a hard ceiling because catalogs overstate.
- The floor matters: automatic compaction normally keeps the window from filling that far;
  without a floor a nearly full window asks for zero tokens and fails before the provider
  sees the request.
- An explicit thinking budget is capped at half the output limit, because thinking spends the
  same budget and a budget near the limit starves the answer or the tool call.
- When a step ends at the length limit, a synthetic message says the response hit the output
  limit, forbids apologising, recapping, or repeating, and asks for the remaining work in
  smaller pieces.

**Takeaway.** The output limit is the room your prompt leaves, not a number you like.

## Beat 2 — Measured and estimated are a trust boundary

**Claim.** You can count the prompt yourself, exactly, with a tokenizer.

**Source.** 1.3 Output-token budgeting (Part 1); the compaction interaction from 7.5
(Part 7).

**Example the co-host raises.** "A tokenizer is deterministic. Why estimate at all?" Then the
model switch: "You switch models and the budget goes wrong."

**Mechanism.**

- Your count and the provider's count are not the same count: provider template, image
  accounting, and cache bookkeeping all sit outside your text.
- The anchor is the most recent assistant response from the **current** provider. Another
  provider's count describes a window this model cannot replay, so it is ignored.
- The two numbers stay separate: the estimate is characters per token, and the margin is
  applied when room is computed. That separation lets compaction count its budget as
  measured, deliberately dropping the margin, or every summary would clamp to the floor.
- Compaction aims at about ninety percent of the window, so a fifteen percent margin applied
  there would leave a three-line summary on a full session.
- The first request of a session has no anchor: measured is zero and everything is estimated,
  which is what keeps the first request from asking for the full cap on a short window.

**Takeaway.** Trust the provider's count, mark everything since as a guess, and never mix the
two.

**Words.** 619.

## Beat 3 — Every result has a size

**Claim.** A tool result is whatever the tool returns.

**Source.** 5.4 Output normalization: content, images, and bounding to disk (Part 5).

**Example the co-host raises.** "I cannot know how big a command's output will be before I
run it." Then the objection: "The result was correct. Why not deliver it and let the model
deal with the size?"

**Mechanism.**

- Every result folds into content, and content has two kinds: text and file. A string is one
  text part; a part list passes through; a structured-only result becomes text.
- Image parts are decoded, checked against the configured limits, and resized. A decode or
  size failure drops the image and inserts a counted note with the reason, because the reason
  tells the model whether a smaller retry would help.
- Text over the line or byte limit is written whole to a managed directory. The model gets a
  bounded head plus a marker naming the range, the total, and the file. The marker appears
  once, after the retained text.
- Metadata records `truncated` and the output path. The presence of the key, true or false,
  is the "already measured" guard.
- Bounding runs after execution and before publishing, inside the uninterruptible settlement,
  so the model-visible bytes and the recorded bytes match.
- Producers may bound first: shell keeps a tail because build logs end with the interesting
  part; read keeps a head because the model asked for a region.
- Expert insert (2 turns, 102 words): a bounded result plus a marker beats a complete one,
  because a fixed budget makes extra text a cost, and the marker keeps the option to fetch
  the rest.

**Takeaway.** Bound every result, and make the loss visible, because a silent cut teaches the
model to invent the rest.

**Words.** 640.

## Beat 4 — Fit the reply to the request you send

**Claim.** You compute the output limit once, when you prepare the request.

**Source.** 7.5 Output-limit fitting; effect on prompt caching (Part 7).

**Example the co-host raises.** "I build it, I send it, nothing changes in between." Then:
"the summary comes back as three lines" — the starved summary.

**Mechanism.**

- `prepare` sizes the output for a request of `budget` tokens. `deliver` can send a larger
  request when the conversation cannot be shrunk further, so `fitOutput` lowers the limit
  again to the room the request actually being sent leaves.
- Two fits from the same arithmetic; the second one wins, because the first was computed from
  an input that no longer exists.
- Compaction counts its input as measured, with no estimate margin, and caps summaries at a
  separate maximum. The cap is a safety valve against an overstated catalog.
- Compaction rewrites the early context, so the provider's cached prefix misses from the point
  of the change onward. That is unavoidable.
- The loss is bounded: the checkpoint is one message at the front, the system prompt order is
  stable, and a per-session cache key keeps lookups on the same prefix. One miss, then caching
  resumes until the next threshold.

**Takeaway.** Fit the reply to the request you actually send, and expect the rewrite to cost
one cache miss.

**Words.** 618.

## Terms to define on first use

- **measured** — the provider's usage at the last response.
- **estimated** — the text since, at about four characters per token, plus a margin.
- **room** — what is left of the window after the prompt.
- **output limit** — the smaller of the model's cap and the room, floored.
- **truncation marker** — the line naming the kept range, the total, and the saved file.
- **omission note** — the counted replacement for an image that was dropped, with a reason.
- **settlement** — the point at which a result is recorded and published, uninterruptibly.
- **cache read** — provider-side reuse of an unchanged prefix, cheaper than fresh input.

## Do not say in this episode

- Do not say "token limit" when you mean the output allowance; say "output limit".
- Do not call a checkpoint a compaction, or a compaction a checkpoint.
- Do not say the cache is "invalidated" as if it were an error; it is a miss you expect.
- Do not read a file path, a byte count, or a marker template with placeholders.
- Do not say "just truncate it"; the point is the marker and the saved file.
- Do not present the estimate as exact, or the measurement as an estimate.
