# Episode 19 beat sheet — Crash and resume

Production sheet, not prose. Four beats, then the artifact. Word allocations are the written
counts the script landed on.

---

## Beat 1 — Write it down before you do it

**Claim.** The honest way to know a run was interrupted is to ask the run, at the end, whether
it finished.

**Source.** `02-durable-state.md` § 2.4.

**Co-host raises.** The run only knows it finished if it got an end. The process was killed
while a model call was streaming, so there is no end. Later: why not write completed at the
end and treat its absence as a crash?

**Mechanism.**
- A claim is written when a turn starts, in the same transaction as the started event, so
  there is no window where one exists without the other.
- A terminal event releases the claim in the same transaction: succeeded, failed, interrupted.
- Write-ahead beats write-behind: a completion flag cannot tell a crash from a session that
  never started. Presence is positive evidence.
- The marker is one field on the session, set or clear. The session separately carries the
  resume attempt count. Re-claiming a claimed session is a no-op.
- Claim bookkeeping never counts as user activity, so the update time is pinned and a resume
  does not reorder a client's session list.

**Takeaway (spoken).** Write the in-flight fact before anyone depends on it, so a crash is
already written down.

**Words.** 581.

## Beat 2 — A clean stop and a hard stop

**Claim.** When the server shuts down cleanly, it should clean up after itself and release the
claim.

**Source.** `02-durable-state.md` § 2.4.

**Co-host raises.** A clean shutdown is not a crash, so tidiness looks right. Then: does every
restart now resume work the user walked away from?

**Mechanism.**
- Shutdown deliberately keeps the claim: the turn was interrupted by the server going down, not
  by the user, and the resumed execution continues the same turn.
- The terminal hook releases on success, on failure, and on interruption whose reason is not
  shutdown. User stops and inactivity stops are deliberate and release.
- The convergence is the point: a clean shutdown and a hard crash leave the same claim, so one
  recovery path handles both.
- The alternative is worse: if shutdown released the claim, the turn would look complete and
  the in-flight request would be dropped in silence.
- A resumed turn writes no new idle marker, because it is the same turn continuing.

**Takeaway (spoken).** A deliberate stop releases the claim. A shutdown keeps it, so one path
recovers both a clean restart and a hard crash.

**Words.** 565.

## Beat 3 — The claim is not a lock

**Claim.** Recovery needs the dying process to cooperate. A shutdown hook, a finalizer, a last
wish.

**Source.** `02-durable-state.md` § 2.4.

**Co-host raises.** The process is dead and cannot say anything. A shutdown hook does not run on
a hard kill. Then, near the expert: the claim sits on the session, so why is it not a lock?

**Mechanism.**
- A surviving claim with no terminal is the crash record, and the next boot reads the database
  rather than asking the dead process.
- The sweep resumes claims that are still set and not already active locally; it never clears
  the claim, so only a terminal ends it.
- Attempt accounting is durable and written before the resume, so a crash inside the resume is
  still counted; past the budget, a durable terminal fails the turn and releases the claim. The
  budget is per turn, not per session.
- Only top-level sessions are swept; child claims go through durable job records.
- The sweep assumes the owner is dead, which a managed server guarantees; it is inert until
  called.
- The expert: it is a recovery marker, not clustered ownership, fencing, or exactly-once.
  Recovery is at-least-once, and two sweeps over one database would run a turn twice.

**Takeaway (spoken).** A surviving claim with no terminal is the signature of a dead process.
Recovery reads the database instead of trusting the dead.

**Words.** 642.

## Beat 4 — Settling the half-written step

**Claim.** The claim is the only thing a crash leaves behind.

**Source.** `08-reliability.md` § 8.4.

**Co-host raises.** The model call was mid-stream and a compaction was summarizing. There is
more half-finished than one marker. Then: why not delete the half-written rows and start clean?

**Mechanism.**
- A step is settled only when its terminal events are written; a crash between start and
  terminal leaves half-written rows.
- Settlement has three parts: stale compactions fail with an interrupted error; stale tool
  calls fail with an aborted error, carrying a subagent's child session id; and the resume path
  admits a continue notice under the same budget.
- Settlement is the first thing a fresh drain does, before it considers new input, so recovery
  is a property of the database rather than a special mode.
- It fails the call rather than deleting it, so the record stays truthful; it walks projected
  messages, so it sees what a reader sees.
- The rejected alternatives: a shutdown hook, a sweep owned by the dying process, trusting the
  model to notice, and unbounded resume.

**Takeaway (spoken).** Settle first, resume second. The next drain closes what the last process
left open.

**Words.** 641.

## Artifact — the recovery comment about orphaned claims

**Source.** `packages/core/src/session/execution.ts` line 76, read in the companion.

**Read.** The comment says the claim is write-ahead, written in the same transaction as the
started event, released by terminals except a shutdown interruption, that a surviving claim is
the signature of a process that died without teardown, and that recovery is a property of the
database rather than a shutdown hook that may not run.

**Interpretation.** The "same transaction" clause removes the window between the event and the
marker. The "except shutdown interruption" clause is the convergence. "Resumes the turn" is why
the continuation notice says not to repeat completed work. And "never of a shutdown hook that
may not run" is the whole argument for reading the database.

**Words.** 329.
