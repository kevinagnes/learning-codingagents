# Episode 6 beat sheet — Tool contracts

Production scaffolding, not prose. Four beats, four moves each: claim, example, mechanism,
takeaway. The script was written from this sheet; where they disagree, the script is what
was recorded and the sources are what is true.

**Topics:** 5.1, 5.2, 5.3 · **Part 5** · **Runtime:** ~22.4 minutes · **Words:** 3,365

---

## Beat 1 — A tool is one object

**Claim.** A tool is not a plugin with a shape bolted on. It is one object, and every tool in
the system has the same parts.

**Source.** 5.1 The tool contract and registration (Part 5).

**Example the co-host raises.** "I have written tools. Mine were a name and a function. What
else is in there?" Then: why must a built-in and an external server share one contract?

**Mechanism.**

- Six parts: name, options, description, input shape, optional output shape, executor.
  Options carry the namespace, the permission action used for definition filtering, and the
  code-mode flags.
- Registration erases the producer's type on purpose. One shape in, one shape out, so the
  registry cannot branch on where a tool came from.
- An executor returns two things: a machine-checked structured output and the content the
  model reads. The model reads prose; the harness reads data.
- The context is uniform for every source: session, agent, message, call identifier, and a
  progress reporter. The description is interface, not decoration.
- The contract contains no trust. Registering a tool says nothing about whether it may run.

**Takeaway.** A tool is a contract with two readers. The model reads the words, and the
harness reads the data.

**Words.** 637.

## Beat 2 — Registration is a replay

**Claim.** Registration adds the tool to a map.

**Source.** 5.1 The tool contract and registration (Part 5).

**Example the co-host raises.** "That is what I would write. A map, an add, a remove, done."
Then the cost: a hundred tools rebuilt on every change, and the bug where unloading a plugin
deletes the tool it had overridden.

**Mechanism.**

- A registration is a transform: a small function that receives a fresh editor and adds,
  updates, removes, or declares a namespace. The registry stores transforms, not a catalog.
- Every read after a change replays every transform in registration order against an empty
  editor. The result is cached until the next change.
- Three properties fall out: deterministic precedence (last valid registration for an
  effective name wins), real undo (dispose removes one transform and the definition it
  covered reappears), and cheap reload for producers that discover tools later.
- A mutable map loses the undo because a removed entry was overwritten, not stacked; and a
  process-global registry would leak a tool set across working directories.
- Registration errors are collected, not thrown: namespace, name characters, the reserved
  `execute` name, and whether the declared shapes convert to the wire format.
- `update` re-locks name and namespace, so it cannot rename a tool; an invalid update leaves
  the previous definition in place.

**Takeaway.** Registration is a list of edits replayed onto an empty page. The last valid one
wins, and removing it uncovers the one below.

**Words.** 614.

## Beat 3 — The snapshot

**Claim.** The registry holds the catalog, so whatever is in the registry when a call arrives
is what runs.

**Source.** 5.2 The snapshot: definitions and the captured executor (Part 5).

**Example the co-host raises.** "A tool changes between the moment the model reads the menu
and the moment it orders." Then the names: "I have a tool in a namespace, and the model calls
something else entirely."

**Mechanism.**

- A snapshot is two things that must agree: the definitions the provider will show, and an
  executor that can run exactly those tools. They are captured together for one request.
- The executor is a closure over the snapshot's own maps. A reload or disposal affects only
  later snapshots.
- Visibility filtering: a rule that denies a tool outright for every resource drops it from
  the catalog. That is catalog visibility, not execution authorization; the leaf still checks
  its own policy.
- Effective names: namespace dots become underscores and other non-alphanumerics in the tool
  name become underscores. Two names can normalize to one flat name, and the later one
  silently wins.
- Two distinct unavailable-name errors: removed for this request, versus never existed.
- Expert insert (2 turns, 116 words): type safety ends at registration. The registry cannot
  be generic in a type it cannot name, so it stores one shape, validates the shape at
  registration, and decodes again at the boundary where the model-readable error is built.

**Takeaway.** A step can only run the tools it advertised.

**Words.** 639.

## Beat 4 — What the model reads when it is wrong

**Claim.** If the model sends the wrong arguments, the tool should throw, and the model should
see the failure.

**Source.** 5.3 Runtime validation and model-facing error formatting (Part 5).

**Example the co-host raises.** "That is honest. My function failed. Report it." Then: "Why
not coerce everything? Half the tools I have written spend their first ten lines fixing up
their own arguments."

**Mechanism.**

- Repair runs before decode, and only when the shape proves the mistake: a stringified root
  object, a numeric string for a numeric field, a null or empty object for an optional field.
  Ambiguous branches are left for validation to reject.
- One decode against the declared shape, normalizing three schema kinds into one pass or fail
  with a list of issues.
- The message names the tool, lists up to five issues with dotted or indexed paths, echoes
  the arguments, and ends with an instruction to update and call again. Each part prevents a
  specific resend.
- The declared output is checked on the way out, so a violation never becomes durable
  history. A foreign failure is wrapped into a tool error so it cannot escape the handlers.
- After the maximum steps, tools are disabled and a late call is rejected with a message that
  says the loop is ending, not that the model made a mistake.

**Takeaway.** Validate at the boundary, and write the failure for the model that has to fix
it.

**Words.** 634.

## Terms to define on first use

- **tool** — name, options, description, input shape, optional output shape, executor.
- **namespace** — a family label for a group of tools; it flattens into the model-facing name.
- **effective name** — the flattened name the model actually sees and calls.
- **registration transform** — the stored edit that a registry replay applies.
- **snapshot** — the definitions plus executor captured for one request.
- **decode** — validating the model's arguments against the declared input shape.
- **repair** — the conservative pre-pass that fixes only provable type mistakes.

## Do not say in this episode

- Do not call a step a turn.
- Do not say "schema" on air; say "shape" or "data shape".
- Do not say "plugin" when you mean a tool; a plugin is a source of registrations.
- Do not say the registry "contains" the catalog; it contains the edits, and the catalog is
  rebuilt from them.
- Do not say a hidden tool is a permitted tool.
- Do not read a file path, a tool identifier, or a field name in camel case.
