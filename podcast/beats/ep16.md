## Beat 1 — Work is tied to a place

- **Claim:** A session is not a customer of the process. It is a customer of one directory.
- **Source:** 9.1, Location scoping, instances, and session affinity.
- **Co-host raises:** "That sounds like a filing convention. What breaks if I ignore it, and
  why can I not fix it later with a check?"
- **Mechanism:**
  - Services split in two. Global and one-per-process: the event bus, the database, the
    session store, the job registry, and the map of locations to instances. Location-scoped
    and one-per-directory: config, agents, permissions, the tool registry, the filesystem,
    the model transport, snapshots, and the runner.
  - The runner is Location-scoped because a step reads and writes files.
  - An instance is one compiled copy of the per-directory graph on one location, built lazily
    and retained in a map keyed by a canonical form of the location. Only an explicit
    invalidation or a failed boot evicts one. Invalidation detaches routing before it closes
    the graph, so an in-flight step finishes on the graph it borrowed.
  - Routing is one call: provide the session's location's instance. Affinity is separate and
    is about cost, not isolation: the parent id, else the fork source, else the session id.
- **Takeaway, as spoken:** "Scope by location. The graph follows the directory, and the
  session names only its directory."
- **Words allocated:** ~620 (actual 631).

## Beat 2 — One execution, and the doorbell

- **Claim:** One session runs one execution at a time, and that is enforced with a doorbell,
  not a lock.
- **Source:** 9.2, The run coordinator.
- **Co-host raises:** "I would have written a lock. Take a mutex, drain, release it." The lock
  is held correctly and the follow-up still waits, because the drain's last eligibility check
  and the idle transition cannot be one atomic step.
- **Mechanism:**
  - An execution is one busy period for one key: one fiber that drains from the first wake
    until the key would stay idle. It coalesces many steps and many drains.
  - The doorbell is a single field on the execution. Work recorded mid-execution sets it
    instead of starting a second fiber. After each drain the loop takes the scope, clears the
    field, and drains again. A wake that survives the loop starts a successor at settlement.
  - Coalesced wakes keep the widest scope, because the wider scope subsumes the narrower and
    narrowing would hide work that was ready.
  - Different keys never block each other. Joiners wait on a signal the execution carries,
    resolved after the settlement hook runs.
- **Expert:** once, on why one execution per session is a doorbell rather than a lock. Four
  turns. A lock decides who may run; a doorbell records a request that the current run reads
  before it decides to stop.
- **Takeaway, as spoken:** "One execution per session, and a wake is a field on it, not a
  second run."
- **Words allocated:** ~620 (actual 647).

## Beat 3 — Steering, queued work, and the order of promotion

- **Claim:** The delivery mode decides when input is heard, and the promotion rules decide
  what is heard.
- **Source:** 9.3, Steering: steer versus queue and promotion order.
- **Co-host raises:** "Why not process input in the order it arrived? That is what users
  expect from a message list."
- **Mechanism:**
  - A steer influences work in progress and is promoted at the next safe step boundary. A
    queued prompt starts new work and is heard only when the session would otherwise go idle.
  - Among pending steers, a compaction is moved to the front so it summarizes history before
    the later steers, which then stay verbatim after the checkpoint. That reorder is local and
    never crosses a move.
  - A control item at the front of the pending steers blocks promotion entirely and the runner
    handles it first. A move is a boundary: nothing is promoted across it, and the drain hands
    off to the new location's instance.
  - At an idle boundary with no steers, exactly one queued item is promoted, followed by any
    steers that arrived in the meantime, up to the next control.
- **Takeaway, as spoken:** "Steer changes the work in progress. Queued work starts the next
  thing. And compaction goes ahead of the steers it would eat."
- **Words allocated:** ~620 (actual 638).

## Beat 4 — A second session, and a narrow stop

- **Claim:** Stopping one session is narrow, acknowledged immediately, and settles later.
- **Source:** 9.5, Multi-session concurrency and interruption.
- **Co-host raises:** "This is where a naive design kills three unrelated tasks, or freezes
  the screen waiting for one of them to die."
- **Mechanism:**
  - The coordinator is keyed by session id, so two sessions are two keys and run concurrently.
    Interrupt targets only the active execution for that key, and an idle or locally unowned
    session is a no-op.
  - Interrupt resolves when the interruption is accepted, not when cleanup finishes. It claims
    the recorded wakes so settlement does not start a successor for abandoned work; wakes that
    arrive during cleanup are new admissions and restart normally.
  - The terminal is one of three: success, interrupt with a reason, or failure. A user or
    inactivity stop releases the claim and cancels the job keyed by the session; a shutdown
    interrupt keeps the claim for the next boot.
  - If resumption is requested and the next promotable item is a steer, a compaction, or a
    move, the session is woken with steer scope and only that work resumes. Queued next-turn
    prompts stay parked. Child sessions are separate keys, and the subagent tool interrupts the
    child itself.
- **Takeaway, as spoken:** "And that is why the doorbell beats the lock. A lock has no memory
  of who knocked."
- **Words allocated:** ~620 (actual 653).

## Terms to define on first use

- **execution** — one busy period for a session, one fiber, from the first wake until the
  session would stay idle.
- **location** — a directory plus an optional workspace identity, resolved to a project.
- **instance** — one compiled copy of the per-directory service graph standing on one
  location.
- **doorbell** — the single field on a running execution that records a wake.
- **successor** — a fresh execution started for a wake that survived the previous one.
- **steer** — input that influences work already in progress.
- **queued prompt** — input that starts new work only at the idle boundary.
- **control item** — a compaction or a move; it owns the boundary it sits on.
- **claim** — the marker a run writes before it acts, released on a terminal.

## Do not say in this episode

- "turn" for a step. A step is one model call; an execution is the busy period.
- "queue" as a bare noun. Say "queued work", "queued input", or "waiting".
- "just", "simply", "obviously", "basically".
- "lock" as a synonym for the coordinator. The whole episode says it is not a lock.
- "Part nine", "Appendix", or any diagram id.
- Any file path, identifier, or code fragment in a spoken line.
