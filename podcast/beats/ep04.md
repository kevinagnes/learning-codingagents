## Beat 1 — Admission is not delivery

**Claim (spoken).** "Sending a message and showing it to the model are the same act."

**Source.** Part 2, § 2.3, "The concept" and "The real thing".

**Example the co-host raises.** A user corrects the agent mid-tool; the process dies after
acceptance and the model never sees it. Then the client retries after a network blip and the
same message is admitted twice. The first failure loses work, the second duplicates it.

**Mechanism.**

- Admission publishes an enqueued event; its projection inserts one row keyed by session and
  admission sequence. A sequence, not a clock, orders the row.
- Admission then wakes execution as a separate act; a failed wake costs a delay, not a
  message. `resume: false` admits without scheduling.
- Delivery deletes the pending row and inserts the visible message in the same transaction,
  which is what makes the table pending-only.
- Admission reconciles on the caller's message identifier first, so a retried submit returns
  the existing item instead of a second one.

**Takeaway (spoken).** "Admitting work is not executing it. One records that something is
owed. The other pays it."

**Words allocated.** about 635 (HOST about 460, CO-HOST about 175).

## Beat 2 — Two modes, one field

**Claim (spoken).** "The delivery mode is a property of the message."

**Source.** Part 2, § 2.3, "The concept" and "What to notice".

**Example the co-host raises.** A note typed as a correction turns out to be a new task; the
user wants to line up three tasks but has never been shown the word for waiting. The mode has
to be visible and changeable while the work is still pending.

**Mechanism.**

- The mode lives on the pending row, so it can be flipped between steer and queue before
  delivery, and has no meaning once the row is gone.
- Steer is input that should influence work in progress, delivered at the next safe step
  boundary. Queue is input that should start new work, delivered only when the session would
  otherwise go idle.
- A prompt steers by default; queued is the opt-in.
- The inbox holds four kinds, not only text: a user message, a synthetic message, a
  compaction, and a move.

**Takeaway (spoken).** "Steer changes work in progress. Queued work starts new work."

**Words allocated.** about 635 (HOST about 460, CO-HOST about 175).

## Beat 3 — The boundary decides

**Claim (spoken).** "When the runner is free, it takes the next thing in line."

**Source.** Part 2, § 2.3, "The concept" and `promote`'s header comment.

**Example the co-host raises.** Two queued tasks and a live answer. If promotion ignores
scope, the second task lands mid-answer and the model works two jobs in one step.

**Mechanism.**

- Promotion takes a scope. At a step boundary mid-work the scope is steer, and queued rows
  are never promoted at that boundary.
- At the idle boundary the scope is input, and exactly one queued item may be promoted, then
  any steers that arrived during promotion, in order.
- A cheap gate runs before anything else: if nothing is promotable, the drain returns without
  calling the model.
- If the head of the line is a control, promotion returns undefined and the runner handles
  the control before any prompt is delivered.

**Takeaway (spoken).** "Arrival order does not decide delivery. The boundary does."

**Words allocated.** about 635 (HOST about 460, CO-HOST about 175).

## Beat 4 — Controls, and a table that forgets

**Claim (spoken).** "The inbox keeps what you sent, in the order you sent it, until it is
delivered."

**Source.** Part 2, § 2.3, "The concept", `pendingSteers`, and "Decisions and trade-offs".

**Example the co-host raises.** A steered compaction arrives ahead of two corrections. In
pure arrival order the corrections would be summarized into the checkpoint instead of
surviving verbatim. And if the compaction crossed a move, the summary would be built for the
wrong working directory.

**Mechanism.**

- A steered compaction is pulled ahead of earlier steers, so their text stays verbatim after
  the checkpoint rather than inside its summary.
- A move is a hard boundary: nothing may be pulled across it. Promotion stops, the runner
  handles the move, and the line resumes on the other side.
- Delivery deletes the row in the same transaction that inserts the message, so the table is
  a holding area and history is the log.
- A cancelled row makes later delivery fail with a lifecycle conflict rather than inserting
  an empty message. Cancelling and admission are themselves events, so the audit trail is in
  the log.

**Takeaway (spoken).** "Controls travel in the same line, and a delivered row is gone."

**Words allocated.** about 640 (HOST about 460, CO-HOST about 180).

## Terms to define on first use

- **Admission** — recording that work exists.
- **Delivery** — turning pending work into a visible message.
- **Steer** — input that influences work in progress, at the next safe step boundary.
- **Queue** (say "queued work" or "queued input", never the bare noun) — input that starts new
  work, only when the session would otherwise go idle.
- **Promote** — consume pending rows into visible messages.
- **Control item** — a compaction or a move, carried in the same ordered queue.
- **Pending-only** — a row exists only while the work is unconsumed.
- **Compaction** — replacing older history with a summary plus a recent window.
- **Checkpoint** — the durable record a compaction leaves behind.

---

## Do not say in this episode

- "turn" for a single model call. A turn is the stretch from promotion until the session
  would go idle.
- "execution" for one model call. It is one busy period for a session.
- "queue" for a message that influences work in progress; that is a steer.
- "steer" for new work; that is queued.
- "checkpoint" for the act of compacting; that is compaction.
- "status column", "delivered flag", or "join" as a description of the design; the table is
  pending-only and deletes on delivery.
- Bare "queue" as a noun, bare "record" as a noun, and any identifier read aloud.
