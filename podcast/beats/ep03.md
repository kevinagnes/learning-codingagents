## Beat 1 — A session is a log, not a row

**Claim.** A session is a row you keep up to date with the latest state.

**Source.** Part 2, § 2.1.

**Example the co-host raises.** After a crash, the row says the session is busy. It cannot say
whether the model finished, whether the tool ran, or whether the process died in between,
because the latest summary overwrote the evidence.

**Mechanism.**

- A session is a durable log of typed entries, appended in order. One entry per fact, never a
  document you rewrite.
- Order comes from a per-session counter, not a clock. Clocks move backwards; two writes can
  share a millisecond; replay must produce the same order. The session-and-sequence pair is
  unique. Gaps are allowed because events that project no message still consume a number.
- Every entry has a type: user, assistant, synthetic, system, skill, shell, compaction,
  agent-switched, model-switched, location-switched, idle. The type drives lowering and
  display.
- Idle is an entry, not a status field: a stretch of work is everything since the last idle
  entry, and that definition survives a restart. The assistant entry is the one entry updated
  in place until its step settles; everything else is append-only.
- A durable entry is not a provider message. One assistant entry can lower to several provider
  messages.

**Takeaway, as spoken.** History is a log, and its order is a number, not a clock.

**Words.** 617.

## Beat 2 — One transaction, or the store disagrees with itself

**Claim.** Recording an event and updating the view that reads it are two writes, so do them
in that order and move on.

**Source.** Part 2, § 2.2.

**Example the co-host raises.** A user message needs work scheduled, a transcript row inserted,
and clients notified. Three writes, and a crash between them leaves work admitted with no
message, or a message no client saw.

**Mechanism.**

- The bus takes a per-session lock, opens one transaction, reads the latest sequence, computes
  the next one, runs every projector registered for the event type, runs the local commit
  hook, advances the stored sequence, and optionally writes the raw event row. Only after the
  commit does it notify subscribers.
- The projector runs inside the same transaction as the recording, so when the event commits,
  its read model is already consistent. There is no flush step and no half-written window.
- Projectors are bounded database work. No remote calls: a projector that waits on the network
  holds every write for that session.
- Replay is idempotent by byte comparison. Same bytes at the same sequence is a no-op;
  different bytes is a defect, not a silent overwrite. The raw log is optional, for replay and
  export; projections are the source of truth for queries.

**Takeaway, as spoken.** The fact and the view commit together, or the store can disagree with
itself.

**Words.** 633.

## Beat 3 — Minimal events, richer views

**Claim.** A durable event should carry everything a reader will need, so nobody has to look
anything up.

**Source.** Part 2, § 2.2.

**Example the co-host raises.** A model-switch event could carry the previous model. But a
concurrent switch makes the emit-time value wrong, and two consumers can then disagree about
the same history.

**Mechanism.**

- The event names the new model. The projection reads the current model inside the transaction
  and records it as the previous value. The event stays minimal; the read model is
  self-contained.
- Events are declared with a type, an aggregate, and a version. Type and version choose the
  projector, so an event's shape can change without rewriting the log.
- Enrichment belongs in the projection, not the event. Putting derived state in the event
  bloats the log, couples the event shape to presentation, and forces a re-emit whenever the
  view changes.
- The rejected alternative is keeping only the current row: no history, no replay, and no way
  to tell finished work from work that never started.

**Takeaway, as spoken.** Record the fact, compute the context, and let the view be the thing
that is complete.

**Words.** 584.

**Expert.** Once, in beat three. Three turns, first person plural: why minimal events plus
enriched projections beat self-contained events, and why replay would be simpler but wrong.

## Beat 4 — Reading it back

**Claim.** The transcript on your screen is the session history, and the model sees the same
thing you do.

**Source.** Part 2, § 2.5.

**Example the co-host raises.** After a compaction the model no longer sees the old messages,
so a screen that shows them is showing history the model is not acting on. An in-flight
assistant entry may hold an unresolved tool call, and a preview that renders it as final shows
a spinner forever.

**Mechanism.**

- The transcript is the message projection read in sequence order from the latest completed
  compaction. A native checkpoint holds the provider's opaque window and is replayable only by
  a compatible model, so the read path takes a boundary parameter.
- Preview cuts at the first assistant entry with no completion time. The runner's own read does
  not cut; the model needs the whole log to continue.
- Usage is recorded on the event that produced it and folded additively into session counters.
  Step usage rides on step end and step failure; title and compaction usage arrive as separate
  durable usage events. Stats aggregate the message rows and those events. Nothing asks the
  provider again.
- Enrichment is recorded in the view, so replay does not have to guess it. A follower replays
  the durable log, then follows arriving events, with one synced marker carrying the sequence
  number where replay ended and the stream began.

**Takeaway, as spoken.** The log is one, the views are several, and each view has a rule.

**Words.** 628.

## Terms to define on first use

- **Durable** — written down before it is treated as true.
- **Entry** — one typed record in a session's ordered history.
- **Sequence number** — the per-session counter that gives total order without a clock.
- **Event** — a durable fact published to the bus.
- **Projector** — the handler that folds one event type into read models.
- **Read model** — a table shaped for queries, rebuilt from the log.
- **Projection** — folding an event into a read model inside the event's transaction.
- **Aggregate** — the unit a sequence applies to; here, the session.
- **Compaction boundary** — the latest completed compaction that a transcript read starts at.
- **Native checkpoint** — a compaction holding the provider's opaque window, not text.
- **Settled prefix** — the part of the log up to the first assistant entry with no completion
  time.
- **Replay** — reading the durable log back into the same shaped tables.

## Do not say in this episode

- "queue" or "steer"; work arriving is episode four.
- "turn" for a step or for a single entry.
- "record" as a noun; say "the log" or "what was written down".
- "live" as an adjective; say "connected now" or "as they arrive".
- "checkpoint" for compaction; compaction is the act, a checkpoint is what it leaves behind.
- "event sourcing" as a slogan; describe the transaction instead.
