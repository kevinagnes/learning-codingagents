# Episode 14 beat sheet — Staying alive

Production sheet for `scripts/ep14.md`. Not spoken. Topics 8.1, 8.2, 8.3 of
`08-reliability.md`, plus the two continuation strings from Appendix A, group Loop.

**Cold open hook:** a provider sends a one-hour retry-after and the agent sleeps on it.
**Promise:** name the three recoveries and the one durable fact that chooses between them.
**Rule for the recap:** decide retry, continue, or recover from the taxonomy.
**Host share:** HOST 74.5 percent, CO-HOST 25.5 percent of spoken words.

## Beat 1 — A retry policy is a budget

**Claim.** A retry policy is not patience. It is a budget with a schedule attached, and every
part of that budget is bounded.

**Source.** 8.1, Part 8.

**Example the co-host raises.** "I have written retry code. It is a loop with a counter in
it." The counter is one decision out of five, and the other four are where implementations
drift.

**Mechanism.**

- Growth: exponential from two seconds, with each gap clamped at ten seconds, so the curve
  flattens rather than running away.
- Count: ten retries, which rides out a short outage and fails a dead provider in about a
  minute.
- Jitter: each gap randomized by about a third, so a fleet that fails together does not
  retry in one wave.
- Server intent: the provider's retry-after value is a floor, clamped at fifteen minutes,
  because the server's number can be wrong or measured in hours.
- Cost: a timeout already spent its wall clock, so timeouts get a budget of three rather than
  ten; the scheduled wait is written as an absolute time, so it survives reconnection.

**Takeaway, as spoken.** A retry policy is a budget with a schedule, and its job is to keep a
broken provider from holding the session hostage.

**Words allocated.** 680.

## Beat 2 — Retry, continue, or start again

**Claim.** Whether to retry is decided by one fact, and the fact is not the error. It is
whether the attempt had shown the user anything yet.

**Source.** 8.2, Part 8.

**Example the co-host raises.** The model writes two paragraphs, the connection drops, and the
agent resends. The model has no memory of the half answer, so it writes a different one and
the user reads both. "Why not always continue" is the follow-up pushback.

**Mechanism.**

- Retry: no visible output yet, so the same call runs against the same assistant message and
  the user sees one message fill in.
- Continue: output had started, so the partial answer stays, a synthetic instruction is
  appended, and a new assistant message ID is issued.
- Recover-full: a transport-level retry-full failure with no output discards the attempt and
  re-issues the whole request, latched once per step.
- The pivot is `outputStarted`, folded from durable events rather than held in a variable, so
  a different process can make the same call.
- Both retry and continue publish a durable scheduled-retry event with an absolute time.

**Takeaway, as spoken.** Retry, continue, or re-issue, chosen by one durable fact. Did output
start.

**Words allocated.** 709.

## Beat 3 — Classify once, from evidence

**Claim.** The error message is not the classification, and the classification is not the
message.

**Source.** 8.3, Part 8.

**Example the co-host raises.** Dozens of providers spell "your request is too long"
differently. A naive agent matches one phrasing and retries the rest forever, because unknown
looks retryable and the classifier never met that spelling.

**Mechanism.**

- Classify: status, headers, body, and the error object become one typed reason, by ordered
  evidence. Quota before rate limit, status before text, text only when the status does not
  contradict it.
- Decide: retryability is a property of the reason. Transport depends on delivery, invalid
  provider output retries only when incomplete, and unknown retries by design.
- Normalize: every reason maps to one persisted shape of type, message, optional status, and
  optional response body, with an exhaustive switch the compiler enforces.
- One override header can outrank the class; nothing else can.

**Takeaway, as spoken.** Classify once, from evidence, and let the retry decision read the
class rather than the sentence.

**Words allocated.** 726.

## Beat 4 — A clean ending is not a good ending

**Claim.** A stream can end cleanly and still be a failure.

**Source.** 8.3 (finish-boundary failures), 8.2 (output limit), Part 8; Appendix A, group Loop.

**Example the co-host raises.** A content filter finishes normally and blocks the response.
Stored as a normal completion, the user sees an assistant that said nothing, with no error and
no next move.

**Mechanism.**

- Content filter: the finish reason becomes a typed content filter error carrying the
  provider's category and explanation when present.
- Unknown finish: a stream that ends with finish reason unknown is refused as a completion and
  synthesized into an incomplete-stream failure, so it takes the normal recovery path.
- Incomplete stream: invalid provider output flagged incomplete stream is retryable, and routes
  to continue when output had started; retryability and routing are separate decisions.
- Output limit: a response truncated at the token ceiling is its own outcome, answered by an
  instruction to break the remaining work into smaller pieces, and after two continuations a
  third truncation is a typed failure.

**Takeaway, as spoken.** Silence at the finish line is not success. If the record cannot say
how the stream ended, the step has not ended.

**Words allocated.** 619.

## Terms to define on first use

- **retry-after** — the provider's own suggested wait, treated as a floor under a ceiling.
- **jitter** — randomization of each gap so clients do not retry in step.
- **output started** — the durable fact that the attempt emitted something the user could see.
- **recover-full** — discarding an attempt and re-issuing the whole request, allowed once per
  step and only from the transport.
- **taxonomy** — the typed reasons a provider failure is classified into.
- **normalize** — mapping every reason onto one persisted error shape.
- **content filter** — a normal finish whose content the provider blocked.
- **incomplete stream** — a stream that stopped before the provider's end marker.
- **output limit** — the token ceiling on the reply, not a failure of the request.

## Do not say in this episode

- "turn" for a step, and "retry loop" for the bounded schedule.
- "the model retries" — the runner decides, the model only receives the continuation string.
- "timeout" as a synonym for any transport failure.
- "unknown means broken" — unknown is a deliberate, retry-eligible category.
- "the summary" or "the checkpoint" — compaction belongs to the next episode.
- Any digit, any identifier, any path, any diagram label.
