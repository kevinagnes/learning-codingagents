# Episode 18 beat sheet — Watching it work

Production sheet, not prose. Four beats, then the artifact. Word allocations are the written
counts the script landed on.

---

## Beat 1 — One publish, two audiences

**Claim.** An agent has one place where it announces what happened, and everyone who cares is
a subscriber, and one announcement serves both a database writer and a screen.

**Source.** `11-observability-api.md` § 11.1.

**Co-host raises.** The two consumers want opposite things. The writer wants order and
certainty; the screen wants speed and will disconnect in a tunnel. How does one announcement
serve both? Then: is it cruel to drop a slow viewer?

**Mechanism.**
- The bus has two consumer kinds, and the difference is the contract, not the payload.
- Projectors are in-process, fold inside the recording transaction, and need order,
  persistence, and exactly-once handling because they mutate durable state.
- Listeners run after commit, feed the live stream, are fast, and may miss events because they
  render rather than decide.
- The server encodes once and fans out to a bounded dropping queue per subscriber; overflow
  fails that subscriber. A connected frame opens the stream and a heartbeat keeps proxies from
  closing it.
- Publish after commit, always, so a client never renders what the database does not contain.
- A subscription can be scoped to a place, so a client that assumes a global firehose misses
  moves.

**Takeaway (spoken).** One announcement, two audiences. A projector that must never miss, and
a listener that is allowed to.

**Words.** 664.

## Beat 2 — Facts and hints

**Claim.** Everything on the wire is a fact, so a client that reads the stream needs nothing
else.

**Source.** `11-observability-api.md` § 11.1.

**Co-host raises.** The stream can drop events. If it is the truth and it can drop, the client
is wrong. Which is it? Then: what does a client actually have to handle?

**Mechanism.**
- The durability kind is declared per event type, and enforced in one place.
- A durable event carries an envelope: aggregate, sequence, version. It is replayable, so a
  reconnecting client can rebuild state from the log.
- An ephemeral event has no envelope and is never replayed; it is a hint, and the durable
  ending event carries the final value.
- Deltas are batched, so a client accumulates and reconciles at the end event. It must not
  assume one delta per token or per block.
- For every fragment, name the durable event that carries the final value, or the fragment is
  a fact and belongs in the durable set.
- The client feeds on session state, execution lifecycle, step lifecycle, output, tool
  activity, recovery and context, the change preview, and blocking questions.

**Takeaway (spoken).** Durable ending events are the value. Deltas are how the wait feels.

**Words.** 670.

## Beat 3 — The client that was not there

**Claim.** If a client disconnects, the fix is a bigger buffer.

**Source.** `11-observability-api.md` § 11.3.

**Co-host raises.** Or persist every delta so nothing is ever missed. Then: if the database
already holds the current state, why rebuild it from events?

**Mechanism.**
- The live feed is volatile by contract: a slow consumer overflows and the stream fails, and
  events during a disconnect are missed.
- The recovery path is the durable per-aggregate log, not a bigger buffer. Making the feed
  durable would persist every fragment, which is what the split prevents.
- The log read replays after a cursor, emits a synced marker at the watermark, then follows
  live. Watching and catching up are distinct surfaces.
- Session status is ephemeral and re-derivable from execution events.
- The portability test: rebuild every read model with the live stream off. Keep the log,
  ordering per aggregate, projectors, and a cursor read; replace the transport and interface.
- The change preview is durable too: the step's ending event carries the snapshot and files.

**Takeaway (spoken).** Turn the stream off and rebuild everything from the log. If you cannot,
something durable was left in the stream.

**Words.** 719.

## Beat 4 — Writing intent, not commands

**Claim.** Once a client can read the stream, it can do everything it needs to do.

**Source.** `11-observability-api.md` § 11.2.

**Co-host raises.** No: it can watch the agent park on a permission request and wait forever.
Reading is not answering. Then two break-it attempts: a queued prompt plus an interrupt with
resume, and an interrupt that arrives after settlement.

**Mechanism.**
- Every operation is a durable write plus an advisory wake.
- Admit a prompt: a durable inbox row is written and returned, then a separate wake requests
  execution. Idempotent by message id; a reused id from another session or type is refused.
- Choose delivery: steer changes work in progress at the next safe step boundary; queue starts
  new work only when the session would go idle. Prompts steer by default.
- Reply to a blocking question: a permission or form request is a parked fiber; the reply
  resolves it, and a decline never reaches model context.
- Interrupt: stops the active execution, reports whether anything was interrupted, and with
  resume wakes steering and control work while queued prompts stay parked. It acknowledges
  before cleanup settles.

**Takeaway (spoken).** A client writes durable intent and wakes execution, then reconciles
from the same stream it watches.

**Words.** 693.

## Artifact — the durable log contract

**Source.** `packages/core/src/bus.ts` line 149, read in the companion.

**Read.** The comment states that the log is durable and ordered per aggregate, that following
false completes at the end of the log, that following true replays then transitions to live,
and that both modes emit one synced marker at the captured replay watermark.

**Interpretation.** Per-aggregate ordering is the smallest promise that makes replay correct.
The envelope is three fields: aggregate, sequence, version. The marker is the seam between
replay and live and the reason a client cannot re-request the same range forever. The manifest
is the other half: internal and replay-only events are filtered out of what a client may
decode.

**Words.** 299.
