# Episode 10 beats — Instructions, skills, MCP

Production beat sheet. The script in `../scripts/ep10.md` was written from this. Times are
spoken words at about one hundred and fifty words per minute.

**Total:** 3,301 words. **Beats:** four, about six hundred and twenty-five words each.
**Artifact:** the skills catalog, read in segment eight.

---

## Beat 1 — Identity is a hash

**Claim.** An instruction source is a value with a stable key and three renderers, and its
identity is the hash of its canonical form, not the text on disk.

**Source.** Topic 4.3, Part 4. Content addressing in `packages/core/src/instructions/index.ts`.

**Co-host raises.** "So the event carries a hash. That is a pointer, and pointers go stale.
Where did the text go?" The naive model is that the file is the source of truth and the
event should carry it.

**Mechanism.**
- A source has a key, a read effect, and renderers for first sight, change, and removal.
- Values are canonicalized with sorted object keys, then hashed with SHA-256. Canonical form
  means key order cannot create a false change.
- The diff compares the new hash to the stored hash per key. Unchanged keys are skipped, a
  changed key produces a delta entry, a removed key produces a tombstone.
- Values go into a blob map keyed by hash, written with insert-or-ignore, so many sessions
  share one row. Durable state keeps the epoch baseline and the latest values.
- A temporary read failure keeps the stored value. It blocks initialization only when there
  is no previous state. An observed absence is a removal, which is a different fact.

**Expert.** One appearance, two turns plus a question. The counterintuitive point: the event
stores identity and the payload lives once in a blob store. A reasonable engineer would put
the text in the event and skip the indirection.

**Takeaway, as spoken.** "Store the value once, name it by its hash, and let the record carry
the name."

**Words.** 625.

## Beat 2 — Baseline and delta

**Claim.** The baseline is rendered on every request, and a change is rendered once and frozen
into history at the point it was observed.

**Source.** Topic 4.3, Part 4. `initial_values` and `current_values`, the frozen update text
in `packages/core/src/session/instruction-state.ts`, and the epoch rule.

**Co-host raises.** "Those two sentences contradict each other." Then the cost objection: the
baseline is the expensive part, and it is sent every time.

**Mechanism.**
- `renderInitial` runs over the epoch's initial values at the start of every model request and
  becomes the system prompt's instruction part.
- `renderUpdate` runs over the delta; its rendered text is frozen into a durable system
  message at commit time and appended to history.
- Freezing is required because the sources are Location-scoped and a resumed process may not
  have them. Re-rendering later could show text the model never saw.
- A checkpoint advances the epoch: current values become the initial values, and history
  selection drops the update messages the new baseline covers.
- An unavailable source at first observation blocks initialization instead of seeding a
  permanent empty baseline.

**Takeaway, as spoken.** "Repeat the baseline, say the change once, and freeze the change
where it happened."

**Words.** 631.

## Beat 3 — Discovery

**Claim.** Instruction files reach a session by four routes that converge on one source, and
the read tool adds a fifth, session-scoped route.

**Source.** Topic 4.4, Part 4. `packages/core/src/instruction-discovery.ts` and
`packages/core/src/session/instructions.ts`.

**Co-host raises.** "I have four rules files, and one is in a directory I forgot existed."
Then: "How do you remember what was already injected?"

**Mechanism.**
- Routes: the global file, the ancestor walk from the working directory, the configured globs
  and paths and addresses, and read-triggered injection of nearby files.
- Insertion order is render order: global first, then project files nearest to farthest.
- The read tool publishes a durable synthetic message whose metadata carries the injected
  path ledger. The loader reads that ledger from model-visible history, so a path dropped by
  compaction or revert is discovered again.
- Watcher events trigger a debounced re-read. A changed file renders a unified diff unless
  the full text is shorter.
- An empty file set maps to a removal, so a session learns its instructions are gone.

**Takeaway, as spoken.** "Discover by path, remember by path, and let the history be the
ledger."

**Words.** 627.

## Beat 4 — Skills and external servers

**Claim.** A capability catalog costs the same whether it holds one skill or a hundred, because
the prompt carries only identity and a description, and the body arrives as a tool result.

**Source.** Topics 4.5 and 4.6, Part 4. `packages/core/src/skill/instructions.ts`,
`packages/core/src/skill.ts`, and `packages/core/src/mcp/instructions.ts`.

**Co-host raises.** "A hundred skills, each several pages long, is a hundred pages of prompt."
Then, for MCP: "The notes are harmless" — the case that breaks it is a server whose tools are
all denied while its notes remain.

**Mechanism.**
- Availability filters by description present, automatic invocation not disabled, and the
  skill permission. The catalog is sorted by id so its bytes are stable.
- The skill tool checks permission, reads the body, records the base directory, and samples
  up to ten files. The result is a skill content block returned as ordinary tool output.
- Additions and removals delta; a changed description restates the list. The skill tool stays
  on the native tool list rather than going through code mode.
- An MCP server contributes an instruction block and a tool source. The block is visible only
  if the session can reach a tool: a code-mode server needs the execute action allowed, a
  native server needs at least one allowed tool.
- Blocks are sorted by server name. An empty visible set is a removal.

**Takeaway, as spoken.** "Advertise what the model can reach, and fetch the body only when it
asks."

**Words.** 629.

## Terms to define on first use

- **Instruction source** — one composable input to the prompt, with a key, a read, and three
  renderers.
- **Canonical form** — the same value written the same way every time, with object keys sorted,
  so equal values hash equally.
- **Hash** — the identity of a value. The event carries it instead of the value.
- **Blob** — the stored value, keyed by its hash and written once.
- **Epoch** — the span a baseline covers. A checkpoint starts a new one.
- **Baseline** — the full instruction render shown at the start of every request.
- **Delta** — the small render for what changed since the stored state.
- **Tombstone** — the recorded fact that a source was removed, as opposed to a read failure.
- **Catalog** — the id, name, and description list in the prompt. The body is not in it.
- **Model Context Protocol, M C P** — a server that supplies instructions and tools.
- **Code mode** — the execution tool through which a server's tools are called.
- **Reachability** — whether the session can actually call at least one of a server's tools.

## Do not say in this episode

- "Part four" or "Appendix A". Refer to other episodes by number and title.
- A rules file by name. It is "the rules file", never a filename.
- "Schema" for the shape of a value. Say "the data shape" or "the form".
- "CodeMode", "providerState", "tools[...]", or any other identifier. Translate to "code
  mode", "call-side state", and "the path under which the tools appear".
- "Just", "simply", "basically", "leverage", "utilize".
- "Record" as a noun where it will be heard as a verb. Say "the written record".
- "Turn" for a step. A step is one model call.
