## Beat 1 — The request is intent, not the wire

**Claim.** A good model boundary sends the provider's own request shape, because anything
else is a copy you have to maintain.

**Source.** Part 1, § 1.1.

**Example the co-host raises.** Every provider publishes a client library, so why not let the
provider's request type be the request? The correction: every caller becomes coupled to one
provider, and prompt caching, compaction, and image budgeting have nowhere to live.

**Mechanism.**

- The caller builds one canonical request: a model reference, ordered system parts, ordered
  messages, tool entries, an optional tool choice, generation options, provider options, and
  HTTP options. It is intent, not a wire body.
- A route compiles it. Body construction checks the provider-native body against a schema;
  transport preparation is a separate step, so the body can be tested without a network.
- A message is a role plus a tagged union of content parts: text, media, tool call, tool
  result, reasoning, compaction, effort. Adding a part type is a compile error in every
  translator, which keeps lowering exhaustive.
- A tool definition is a name, a description, an input schema, and an optional output schema.
  The record key is the model-facing name. The request is immutable, so enrichment returns a
  new request rather than mutating a shared one.

**Takeaway, as spoken.** Describe the call once, in your own words, and compile it per
provider.

**Words.** 632.

## Beat 2 — The stream has to end on purpose

**Claim.** When the stream stops, the answer is finished.

**Source.** Part 1, § 1.2.

**Example the co-host raises.** A half-written tool call: the arguments arrive as text, the
connection ends, and the truncated JSON either fails to parse or parses at a convenient brace
and gets executed. The correction: a stream must contain a terminal event, and nothing may
follow it.

**Mechanism.**

- The canonical event union carries text, reasoning, tool input, tool calls, tool results,
  step boundaries, media, finish, and provider errors. Every consumer switches on the type.
- `requireTerminalEvent` fails a stream that ends without a finish or provider error, and
  fails one that emits anything after the terminal event. End of stream is never success.
- Tool input arrives as raw text deltas. The delta's parsed value is best effort, for
  display only. The authoritative input is one parse at the end; an empty string is treated
  as an empty object for zero-argument tools.
- Finish reasons are a closed set: stop, length, tool-calls, content-filter, error, unknown.
  The loop maps each to a decision. Unknown is treated as an incomplete stream, not a stop.
  The provider's raw value and content-filter detail survive alongside the normalized one.

**Takeaway, as spoken.** A stream is finished only when it says so.

**Words.** 635.

## Beat 3 — Some provider state is proof

**Claim.** Provider metadata is opaque, so the safe move is to strip all of it before the
next request.

**Source.** Part 1, § 1.4.

**Example the co-host raises.** A session runs on one model, the user switches models, and the
next request carries a signature the old model attached to its text. The new model did not
produce it. The correction: strip is not the rule. Decide per part.

**Mechanism.**

- Call-side metadata is model-scoped proof of generation. Only the producing model may replay
  it. Same provider is not enough.
- Readable reasoning may return to the model that produced it. After a switch it is dropped or
  downgraded to ordinary text, never presented as the new model's reasoning. An interrupted
  reasoning block is downgraded even for the same model.
- A hosted tool's result payload is provider-format data, not proof of authorship, so it is
  replayable across models of the same provider. Its call-side metadata is not. The runner
  never dispatches a hosted tool.
- The decision lives in lowering, because lowering has both the source model and the target
  model. Metadata is namespaced by provider so two providers cannot collide.

**Takeaway, as spoken.** Replay proof only to the model that produced it, and let results
travel no further than their provider.

**Words.** 624.

## Beat 4 — The door knows providers, not sessions

**Claim.** The model boundary should sit underneath the runtime, as the bottom layer of the
agent.

**Source.** Part 1, § 1.1 and § 1.4; Part 0, § 0.2 for the dependency direction.

**Example the co-host raises.** It is the lowest thing in the system and it talks to the
network, so why is it not the foundation? The correction: it is a peer, not a foundation. The
runtime depends on it; it depends only on the shared contracts and never imports the runtime.

**Mechanism.**

- The boundary knows nothing about sessions. It takes a request and options, returns a stream,
  and runs exactly one call per invocation. It cannot loop and cannot remember.
- Session concerns stay one layer up: session headers, cache key, image budgeting. Provider
  quirks stay inside the route: body builder, transport, decoder.
- Adding a provider is writing a route, not editing the loop. Cross-provider fallback rotates
  the route and replays the same canonical intent.
- The inability to loop is what creates the seam for a permission gate between the model
  asking and the tool running. Tool definitions travel; tool execution does not.

**Takeaway, as spoken.** The door knows providers, not sessions, and that is what keeps it
testable.

**Words.** 628.

**Expert.** Once, in beat four. Three turns, first person plural: why the boundary does not
sit at the bottom and get configured with session state, and what that buys for testing.

## Terms to define on first use

- **Provider** — the service that serves a model.
- **Canonical request** — one request shape that every provider lowers from.
- **System part** — one ordered piece of system text, not one string.
- **Content part** — one typed piece of a message; the union is exhaustive.
- **Tool definition** — name, description, input shape, optional output shape.
- **Route** — the provider-specific body builder, transport, and decoder.
- **Compile** — turn canonical intent into a schema-checked provider body.
- **Terminal event** — the finish or provider error that ends a stream.
- **Finish reason** — the closed set that says why a step ended.
- **Hosted tool** — a tool the provider runs itself.
- **Call-side metadata** — model-scoped proof that this model generated the content.
- **Lowering** — translating history into the provider's message shape.

## Do not say in this episode

- "turn" for a step.
- "the API" for the model boundary; say "the boundary" or "the door".
- "schema" in a spoken line; say "shape" or "data shape".
- "the model's response" when describing a stream; the stream is not a response until it has
  a finish reason.
- "retry" as if it were a new step; a retry is a new attempt for the same step.
