## Beat 1 — The toolkit is a prompt (689 words)

**Claim.** A tool description is a policy document the model reads before it decides anything,
and it is the cheapest prompt engineering in the system.

**Source.** 5.5, the built-in toolkit as prompt design.

**The question the co-host raises.** If the description is the model's only documentation, what
are the paragraphs actually doing? And later: why is the longest description in the toolkit
allowed to stay long when the text ships in every request?

**Mechanism.**

- The nine built-ins fall into four families: discovery (files and directories, contents,
  paths), mutation (a surgical replacement, a whole file, a multi-file envelope), the shell,
  and two tools that reach outside the repository.
- Descriptions do four jobs: state the output shape, name the preferred alternative, state the
  constraint the executor cannot enforce, and describe the failure the phrase prevents.
- The read and edit descriptions are a pair: read injects the line prefix, edits must omit it,
  and the edit tool can only fail a copied prefix rather than explain it.
- Some descriptions carry request-time facts, such as the resolved shell and operating system,
  or the current year.

**Takeaway.** Every sentence in a tool description either prevents a specific failure or buys
nothing.

**Hand-off.** The co-host turns to the tools whose descriptions carry the most weight.

## Beat 2 — The tools that can hurt you (660 words)

**Claim.** Three tools are dangerous, and the danger is not the tool; it is the contract you
left out.

**Source.** 5.6, patch, shell, and background shells.

**The question the co-host raises.** Which three, and why does a multi-file edit need special
treatment? Then: if a background command is still running, what stops the model from sitting
there asking whether it is done?

**Mechanism.**

- Patch selection is a session hook: for a model that does better with the envelope, edit and
  write are removed; otherwise patch is removed. The hook runs on every request kind, so the
  choice cannot flip mid-run and cannot invalidate a cached prompt.
- A foreground command gets a default timeout, and a timeout result names the limit and the
  remedy instead of failing bare.
- Output is bounded: the full text goes to a backing file and the model gets a tail plus a path.
- Background commands carry a no-polling instruction, one carve-out for the user who asks for
  the output, and a harness-owned synthetic notification when the job settles. Shell jobs record
  recovery metadata so a crash does not orphan the command.

**Takeaway.** A tool that can hurt you does not get a warning; it gets a contract. One editing
family at a time, a bounded command, and a notification instead of a wait.

**Hand-off.** The co-host asks what happens when the list itself is the problem.

## Beat 3 — One tool that runs code (683 words, EXPERT here)

**Claim.** You can delete the entire native tool list from the request and put one tool in its
place, and the model writes a program instead of a call.

**Source.** 5.7, code mode, one execute tool plus a catalog.

**The question the co-host raises.** Parallel tool calls already exist inside one step, so why
does the model need code?

**Mechanism.**

- What code adds is composition: a batch of parallel calls cannot consume another call's result
  in the same step, and a program can.
- The catalog is budgeted: every namespace is shown, then full listings are added one namespace
  per round, shortest first, until the token budget runs out; a synchronous search covers the
  rest and returns the exact path.
- The execute definition is static, and the catalog is an instruction source that renders full
  once and as a delta afterwards, so the churn does not invalidate the cached prompt.
- Core workflow tools opt out, everything else defaults in, the execute name is reserved, and
  the interpreter is confined: no imports, no direct filesystem, no timers, no file URLs.

**EXPERT.** Why one code tool can beat a long native list: the list is the wrong shape for a
pipeline task, and definitions ship in every request. Three turns, in and out.

**Takeaway.** When the work is composition, expose the toolkit as a single execute call and let
the model compose.

**Hand-off.** The co-host asks where the other tools come from.

## Beat 4 — Plugins as tool sources (592 words)

**Claim.** A plugin adds tools through the exact same door a built-in uses, and there is no
second execution path.

**Source.** 5.8, plugins as tool sources.

**The question the co-host raises.** Registering a tool is one thing; watching every call is
another. And later: why can the second hook not reject a call the way the first one can?

**Mechanism.**

- The tool domain exposes registration, reload, and list; a plugin tool is an ordinary
  registration afterwards.
- Observation is separate: a hook before the call may rewrite the arguments or reject the call,
  and a hook after the call may rewrite the result.
- The failure channel is asymmetric on purpose: after the tool has run, the side effect exists,
  so turning a completed call into a failed one would rewrite the record.
- A dynamic source such as an external tool server keeps one stable registration step and
  reloads in place, so a refresh cannot jump ahead of a later plugin; inner code mode calls run
  the before hook too.

**Takeaway.** One registration step to add tools, two hooks to observe them, and only the first
hook may reject.

**Hand-off.** The co-host sets up the artifact.

## Terms to define on first use

- **Tool description** — the paragraph that travels with a tool on every request, and the model's
  only documentation for it.
- **Editing family** — patch, or edit plus write. One is visible to a given model at a time.
- **Foreground and background command** — one the step waits for, one that returns immediately
  and notifies later.
- **Code mode** — one execute tool whose input is code, plus a rendered catalog of the other
  tools.
- **Catalog** — the budgeted, delta-updated listing of code mode tools in the prompt.
- **Tool hook** — a callback around a tool call: one before it runs, one after it returns.
